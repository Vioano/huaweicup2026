本轮目标同时降低未修改官方 E0 的 Makespan 和生成合法方案的端到端墙钟。
当前主构造为 `src/q1/bounded_tasks.py`，固定实现
`05f8fa0f7e52f5914f14815f6bdbcb851b631556`，参数

## 为什么改变构造

fixed64 全 500 格反馈暴露了结构问题：020 的 288 个独立分量被交错切成
110 个存在串联依赖的 Task，最后全落在一个核上。只优化切块大小或加核
无法消除这种构造造成的依赖。Pro r06 的链/分量构造建议给出了方向；本轮
用正式图和官方评价验证具体实现，未把 Pro 自报实验当作本机成绩。

1. **完整分量先分核。** 对官方 COPY 收缩后的计算图求弱连通分量，按各 Pipe
   工作向量平衡到核。同核完整分量并入一个 Task，避免人为切出跨 Task 边。
2. **归约树用独立子树前沿。** 分量不足且每节点至多一个后继时，找按工作量
   截断的最大子树反链。子树包分配给各核，剩余节点进入尾 Task。所有跨边
   均进入尾部，合法性可直接论证；更细前沿平衡负载，但会增加边界搬运。
3. **巨大 Task 沿独立分量边界细分。** 只对超过 4096 个计算节点的 Task，
   把内部独立分量装入目标 1024 节点的块；不可分的大分量完整保留。
   各块留在原核、原位置，保留原 Task 增广 DAG 的块间顺序。

四核 100 图中，97 图走完整分量、3 图走树前沿；27 图进入巨大 Task 处理，
实际增加 Task 的是 12 图，43 个原 Task 被拆、净增 210 个 Task；18 图仍有
不可分的大分量。阈值是工程启发式，不是容量证明或最佳阈值。32 图仍有 spill。

前一版不限制 Task 大小的全量尝试在 014 E0 超过 60 秒后停止；保留
12 成功、1 超时、86 未运行。新 014 完成 E0 用 26.23 秒。由于旧超时过程
没有阶段剖析，不能将差异归因于某个具体编译阶段，也没有旧方案 Makespan
可比较。不同批次的停止政策和失败原件均保留，未用成功新批覆盖旧批。

## 如何判断下一步值得优化哪里

静态下界包含计算关键路径、各 Pipe 负载、必要 DDR 服务及最早释放/最短
剩余路径约束。证明条件见 [Q1_LOWER_BOUNDS.md](Q1_LOWER_BOUNDS.md)，
它不收缩会错误添加 Task 内依赖的 COPY 桥，不把零 spill 当作最优证书。
以 E0 上界 U 和静态下界 L 比较，U/L−1 是相对最优差距的上界：
四核 8 图在 1% 内、15 图在 2% 内、23 图在 5% 内。020 为 0.31%，
045 为 1.18%，097 为 1.95%。这些结论依赖冻结语义与下界假设，尚非证明器验收；
大差距也不证明有等幅可实现收益。

优先处理共享输入/容量压力（044）及非归约树的单连通图。13 个未加速图为
005、016、024、047、048、051、064、069、071、075、082、085、086。
Fang 已报告 chain-wave 对 051 有效，但对 048/071 因等待门开销退化，见
[Issue 98 的完整反馈](https://github.com/huaweibei123/huaweicup2026/issues/98#issuecomment-5816412000)。
因此候选选择必须利用可解释结构与真实门控代价，不能事后逐图挑最好值再
冒称一条通用求解算法。当前没有宣称达到全局最优或完成全部核数验收。
