## 二、研究优先级需要调整

### 参数最小割暂时降为备选

本轮把上一轮的理想集切分代理接上了正式图与官方评估器。当前实现使用有限锚点、标量化偏好与重复 Dinic，**没有实现完整的高效参数流算法**。

在首组 7 个正式用例上，它没有超过旧三个构造的最好值。`case_002` 的构造约耗时 **5.75 秒**，最终 **115746 cycles**，明显不如下面的串行包路线。

这否定的是**当前这一版切分代理与构造方式的优先级**，不是否定理想集理论。源码、参数、结果都保留了，不因为它曾被推荐而继续扩大投入。

### 全局事件消元也暂时不作为前置工程

上一轮的 max-plus 端口消元，需要继续解决动态带宽、Cache、浮点结算与完整输出问题。

这轮选择了一个更直接的落点：

> **先把 max-plus 用在候选构造中的计算资源响应，不尝试替换官方事件模拟器。**

这样，数学压缩仍能帮助决策，却不需要先证明一个新评估器与 E0 全域等价。

DAG 聚类本身并不是新发明。例如 Yang、Gerasoulis 的 DSC 就研究聚类与调度，但背景是无界、完全连通处理器，其结论不能直接移植到本题的固定核数、共享 DDR 与固定 FIFO。这里的研究重点应当是本题特有的构造与验证，而不是把已有聚类思想重新命名。:chatgpt-content-reference{index="4"}

## 三、主构造：归属粗化，执行细化

这条路线最重要的区分是：

**“哪些操作应该留在同核”与“哪些操作应该永远放在同一个子图里”，不是同一个问题。**

前者保护数据复用；后者影响官方编译出的顺序。把两者绑死，会损失流水交错机会。

### 1. 先找可以安全收缩的串行包

在正确收缩 COPY 后的计算 DAG 中，只粘合满足以下条件的边：

\[
u\to v,\qquad
\deg^+(u)=1,\qquad
\deg^-(v)=1.
\tag{S1}
\]

所选边形成无分叉链。链的内部计算节点不会被外部计算依赖从中间插入，也不会从中间分叉出去。

**这个收缩保持计算商图无环。**若收缩后出现环，就能沿每条链内部的有向路径，把它还原为原计算图中的环，与原图为 DAG 矛盾。

但这个命题只保证**计算商图**。新增 COPY、Pipe FIFO、内存复用边仍由官方展开决定，不能把它升级成完整执行可行性保证。

原型还做了一项保护：先比较自己使用的计算邻接与官方 COPY 收缩邻接。遇到尚未支持的内部 COPY 桥接，会明确报不支持，不悄悄漏掉依赖。

### 2. 用小矩阵代替“包的总 cycles”

一个包如果包含不同 Pipe 上的操作，单个总工作量不能描述它如何占用 Cube／Vector。

本轮用三个输入时钟描述一个计算包：旧 M 时钟、旧 V 时钟，以及包外输入的共同释放时刻。输出为更新后的两个 Pipe 时钟和包完成时刻：

\[
\begin{bmatrix}
M'\\V'\\C
\end{bmatrix}
=
K_B\otimes
\begin{bmatrix}
M\\V\\r
\end{bmatrix},
\qquad
(K\otimes x)_i=\max_j(K_{ij}+x_j).
\tag{S2}
\]

矩阵的行、列在这里有明确含义，不是把图转成矩阵后随便求一个特征值。

构造方法也很直接：按规定的包内计算顺序，每个操作等待同 Pipe 前项、数据前驱与共同释放，再加上计算周期。每个完成时间始终是“三个输入加常数，再取最大值”的表达，因此能压成一个 **3×3 响应矩阵**。

**这个表示对固定计算 FIFO、共同输入释放的子模型是精确的，对官方完整 Makespan 不是。**它没有包含真实 DDR 等分争用、SPILL、内存额度来源、Cache，以及不同输入各自的到达时刻；也不是原问题下界。

在 `case_002` 中，**1798 个非 COPY 操作变成 397 个核心归属包，只有 3 种不同的计算响应矩阵**。

这里不能再过度压缩：397 个包仍保留各自的张量接口、原 ID 和依赖位置。**共享三种响应函数，不等于原问题只剩三个实体。**

### 3. 在宏图上决定核心归属

构造器按剩余计算路径生成宏块的共同拓扑参考序。对每个包，尝试各核心，估计：

- 输入到达与跨核等待；
- 该核 M／V 两个时钟的变化；
- 同一输入是否已被安排在该核读取。

然后选取一个核心，更新资源状态。

这是一个有意简化的构造代理。比如“已读取集合”目前不包含完整的容量与淘汰过程，不能解释成真实驻留集合。**最终每个候选都由原样 E0 判断。**

复杂度主要是图扫描、拓扑排序，以及每包尝试少量核心；没有枚举全部分配，也没有要求先训练成本模型。

## 四、真正有效的第二步：固定核心归属，再改变子图与顺序

### 1. 一个有用的实现级不变量

对于问题 2、3 的冻结构图，保持每个操作的核心归属不变，就保持了张量的生产核心、消费者核心和跨核 COPY 配对集合。因此：

\[
a_1(o)=a_2(o)\ \text{对所有操作成立}
\quad\Longrightarrow\quad
D_{\mathrm{partition},1}
=
D_{\mathrm{partition},2}.
\tag{S3}
\]

这里指的是 **SPILL 之前的切分新增搬运分量**。

证明按张量分别检查即可：原始输入的读取核心集合不变，中间张量的源核—目标核集合不变，最终输出的生产核心不变。

但必须保留三个边界：

**SPILL 量不一定不变；Cache 实际路径不一定不变；Makespan 更不一定不变。**问题 1 跨子图也需要 DDR 中转，因此不能套用这个不变量。三问的 Task 组织差异正是题面规定的。:chatgpt-content-reference{index="5"}

这个不变量让我们能把实验拆开：**先优化数据归属，再观察仅改变顺序能带来什么。**

### 2. 资源重入，是值得拆包的位置

考虑一条链先用 M、再用 V、随后返回 M。

把整条链放在一个子图里，官方可能把它的两次 M 使用都排在同 Pipe 的其他独立工作之前；中间等待 V 的时间就浪费了。

本轮做了一个使用原配置的公开输入微图：

| 相同图、相同核心、相同搬运统计 | 问题 2 | 问题 3 |
|---|---:|---:|
| 整条链保持一个子图 | 204 | 204 |
| 在返回 M 前拆开，让另一条独立 M 工作插入 | **104** | **104** |

链是 M1→V100→M1，另一条独立工作是 M100。没有增加等待、预取或重算；自动构造也复现了对应结果。

**这给出了一个明确反例：保持商图无环的安全粗化，仍然可能损害性能。**

### 3. 用有限参考窗口组织阶段交错

进一步，把粗包按连续同 Pipe 段拆开。在粗包的共同拓扑参考序上，选取一个有限窗口；窗口内按阶段索引和原包位置组织细包，再投影为各核子图顺序。

伪代码可以压缩为：

```text
先构造粗包分核方案
冻结每个原操作的核心归属

将粗包拆成连续同 Pipe 的阶段
对少量固定参考窗口：
    生成满足依赖的阶段拓扑序
    投影为各核的子图顺序
    输出原操作 ID 的 node_to_subgraph
    调用官方评估器
    保留已确认合法的最好方案
```

**参考窗口不是物理屏障，也不是实际并发包数或存储峰值的上界。**官方仍可能提前搬入后续数据。我们控制的只是允许提交的子图与顺序，不是执行时钟。

## 五、正式用例的收益与失败，已经可以分开解释

### 1. `case_002` 的消融说明：主要收益不是一个“高级矩阵名字”

以下均为本轮 E0 新结果，问题 2、四核：

| 构造 | Makespan |
|---|---:|
| 旧三个探测构造中的最好值 | 111212 |
| 使用同一新成本模型，但仍逐操作分配 | 104109 |
| 串行包，仍用标量计算成本 | 72650 |
| 串行包，使用两 Pipe 矩阵响应 | 71904 |
| 固定核心归属，按资源重入细化 | 71108 |
| 固定核心归属，32 包参考窗口细化 | **66376** |

这说明：

**第一层主要收益来自“哪些中间数据不应被轻易切到其他核心”。**旧逐操作方案的新增搬运为 5,078,016 bytes，链包方案降到 743,424 bytes。

**矩阵响应贡献了一部分额外改善，但不是全部改善。**在相同链包构造下，72650 到 71904 约改善 1.03%。

**最后的顺序改善与搬运改善可以分离。**71904 到 66376 的五项搬运统计完全相同，且都没有 SPILL，时间下降约 7.69%。

这些方案与完整结果在:chatgpt-content-reference{index="16"}[实验表](sandbox:/mnt/data/NPU_A_Structural_Prototypes_R3/analysis/RESULTS.md)中；关键结果还通过随包重新解压的官方原件，做了完整 JSON 复跑对照。

这个用例也能给出一个简单但严谨的质量证书：总 M 工作量为 240000 cycles，四核至少需要 60000。因此：

\[
T^\star\ge60000,
\qquad
0\le
\frac{66376-T^\star}{T^\star}
\le
\frac{66376}{60000}-1
\approx10.63\%.
\tag{S4}
\]

这是相对真正最优值的**差距上界**，不是证明 60000 可达，也不是说已经求出了最优解。

| case_071 | 15328 | **13443** | 改善 |

结果是 **4 改善、2 相同、2 退化**。这是预列验证组，不冒称这些 case 在全部历史讨论中完全未见。

因此，正确的交付不是“用新方法替换旧方法”，而是**保留少量机制不同的候选，用真实评估确认选择**。这个选择成本必须计入求解时间。

### 3. 窗口越大，也不一定越好

`case_044` 的原链包方案是 **74838 cycles**。固定相同核心归属后，参考窗口分别取 8、32、128 个包，得到：

**76410、89524、105715 cycles。**

五项搬运统计仍然相同，也都没有 SPILL。扩大窗口导致明显退化，不能解释成容量溢出，更不能根据“理论并行空间更大”判断它一定更快。

这不是仅在一个微图上工作的机制：

`case_002` 两核时，旧构造最好为 138426，固定归属窗口方案为 **126586**；五核时，旧构造最好为 117925，窗口方案为 **57102**。

## 六、问题 1 要另处理：合法合并还必须保护 Task 的释放时机

问题 1 每个子图就是独立 Task。过细的阶段拆分会引入 Task 等待，因此不能把问题 2 的方案直接照搬。

本轮实现了一个精确的**合法合并检查**：

在 Task 数据依赖图上，加上每核相邻 Task 的顺序边。对相邻同核 Task 的直接边进行收缩，保持 DAG 的条件是：

\[
\operatorname{contract}(A,B)\text{ 后仍为 DAG}
\quad\Longleftrightarrow\quad
\text{不存在经过其他节点的 }A\leadsto B\text{ 路径}.
\tag{S5}
\]

这是偏序中的覆盖关系。收缩产生的新环，恰好对应这种替代路径；每次合并后重新检查全局关系，而不是假定只影响两核。

**但合法性不等于收益。**

本轮构造了一个非常直接的反例：核心 0 的短操作 A 产生远端长任务 C 的输入，A 后面还有本核独立长任务 B。

| 方案 | 问题 1 Makespan |
|---|---:|
| A、B 分开，C 尽早被释放 | **6014** |
| 合法地合并 A、B | 11005 |
| 加入远端出口保护，不执行这次合并 | **6014** |

搬运统计相同，差别来自：**C 原来只需等待 A，合并后必须等待整个 A+B Task 完成。**

正式用例也体现了这种条件性：`case_002` 的链包种子为 122820，受保护合并后降到 **93126**；但 `case_051` 从 338092 合并成 385092，反而变差。

所以这条路线目前应当作为**有出口／输入门控意识的少量合并候选**，不应写成“Task 越少越好”。

| 三例各预热一对、正式三对 API 计时 | 约 **1.85×、1.27×、1.48×** | 不是完整 CLI 倍数，仍未达到 3×门槛 |

此外，在这些每池 8 条记录的诊断池里，若只取 E2 事件估计的第一名，会在 `case_002/010/026` 分别丢失约 **6.52%／26.27%／21.30%** 的池内最好成绩。排序路线在 `case_002` 也有约 6.52% 的损失。

这些是**小池 top-1 诊断**，不是重新执行了团队“至少 64 候选池”的发布验收。团队规范本身也要求把数值误差、短名单遗憾、完整输出兼容分开报告。:chatgpt-content-reference{index="7"}

据此，本轮主算法没有让 E2 决定哪些结构候选永远不进入 E0。**用数学结构先把候选数压小，比现在依赖一个误差仍大的代理去大规模筛选更可靠。**

## 八、已经做成可独立运行的原型，不只是候选成绩表

`src/solve.py` 会从原图生成有限候选，调用**原样官方 CLI**，保存每次完整结果、Trace、日志，再选取已确认合法的最好方案。

它不依赖 LLM 服务，不使用隐藏的离线答案，也不会拼接 E2 的 Makespan 与另一引擎的时间线。输出方案仍然只有官方要求的两个字段。:chatgpt-content-reference{index="8"}

下面是实际运行的单次端到端结果：

| 输入与模式 | 最终 E0 结果 | 完整墙钟 |
|---|---:|---:|
| case_002，旧三构造 | 111212 | 2.985 秒 |
| case_002，加入结构构造 | 71108 | 8.287 秒 |
| case_002，再加入一个固定窗口候选 | **66376** | **8.948 秒** |
| case_026，加入结构构造 | **28637，保留旧 cut2** | 7.693 秒 |

都使用 30 秒预算。**候选数量与实际 E0 调用次数不同，不能把这张表当成等评估次数的算法排名。**它证明的是：在这些已测用例上，收益不是靠无限离线搜索获得，选择与验证成本实际包含在内。

仍需保留工程边界：E0 子进程可以按剩余预算中断，但构造器目前是在候选之间检查时间；大图硬截止、全部 100 例与最坏耗时尚未验收。题面建议的单例 5～10 分钟目标没有被改成一个未经证明的全域承诺。:chatgpt-content-reference{index="9"}

本轮全部使用 CPU。没有 CUDA、Metal、Rust 或 C++ 的新性能成绩。当前小矩阵构造通常只占几十毫秒，**没有证据值得先为九项 max/add 单独建设 GPU 路径**；昂贵的官方展开与完整评估仍更值得优先优化。

## 九、后续最值得保留的研究方向

**第一优先级是“保护数据归属之后，选择性展开重入流水”。**当前证据说明，它可以同时避免细粒度跨核通信和过度粗化的 FIFO 损失。下一步应研究可检测的启用条件，例如重入工作量占比、响应同质性、外部依赖接口与同时就绪宽度。这样的触发器尚未验证，不能根据本轮成功例直接宣布泛化。

**第二优先级是粒度选择。**链包、小张量接口块和必要的细粒度候选互有胜负；应把“核心归属包”和“最终子图”作为两个独立层次保存，而不是寻找一套统一子图大小。

**问题 1 则继续沿 Task 释放边界研究。**覆盖关系给出精确的合法合并工具，出口和输入门控决定某次合并是否值得尝试。不能用少 Task、少搬运或少依赖边替代 Makespan 判断。

这轮尚未证明优于成熟强基线或同题头部队伍。**但已经有了一个实质进展：数学压缩不再只是论文中的解释，而是进入了构造程序，并产生了可复现的收益、明确的失败例和一个用例级质量证书。**
