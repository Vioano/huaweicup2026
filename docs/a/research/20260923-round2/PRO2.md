# 二、修订上轮假设：真正能控制的量，比“每核几个大子图”更丰富

## 2.1 队首不能越过，现在有源码和公开输入域反例

官方 `queue_if_ready` 明确要求待发射操作就是当前 `pipe_ops[cursor]`；当前操作完成之后，`advance_pipe` 才推进游标。**后面的操作即便独立就绪，也不能越过这个固定队首。**这次不是从 `PIPE_SLOTS=1` 推测出来的。

我构造了合法二部微图：源核先执行一个较长计算；目标核有一个依赖它的操作 R，以及一个独立操作 I。只交换目标核的公开子图优先级：

| 目标核顺序 | Q2 Makespan | Q3 Makespan |
|---|---:|---:|
| 先 R，后 I | 2018 | 2018 |
| 先 I，后 R | **1520** | **1520** |

完整图、计划、结果和时间线都保留。这个差异说明：**构造计算 FIFO 顺序本身，就是重要的优化自由度。**

## 2.2 Q2/Q3 的子图顺序是“展开前优先级”，不是运行时逐子图屏障

冻结代码先生成 raw Step1 顺序，然后按 `core_schedules` 中的子图 rank 做**稳定分桶排序**，再送入 Step2 和 Step3。Q2/Q3 每核仍只有一个合并 Task，不会因为子图数量增加，就支付 Q1 那种逐 Task 切换开销。

Step3 又明确把扩展序列在每条 Pipe 上的投影，作为固定顺序。

这给出一个重要的构造机制：

> **将计算操作细分为 singleton 子图，可以把选定的合法计算顺序编译进官方的 M/V FIFO；而实际 COPY、spill、内存复用依赖和开始时间，仍完全交给官方决定。**

这不是允许任意调度操作，更不是插入等待、预取或重算。我们提交的仍然只有题面允许的两字段。:chatgpt-content-reference{index="5"}

## 2.3 另外三项修订

**生成 ID 不能用一条规则概括三问。**Q1 是分开的 op/tensor 游标加共享避让集合；Q2/Q3 则从全图最大节点 ID 加一开始，用一个游标分配。上轮把 Q1 配方泛化到所有场景的风险，现在已经排除。

**内存约束要跟随实际实现。**冻结全局模拟使用 Step3 导出的内存复用依赖和固定 Pipe 顺序；不能另写一个“更理想”的全局实时内存调度器，再把它冒充 E0。返回的内存峰值也要保留其本地 Step3 来源。

**Q3 不只是 miss 完成后插入 Cache。**源码对所有 COPY_IN 完成都调用 `insert_cache`，包括 hit。若 hit 在飞行期间对应条目被淘汰，它完成后可能重新插入。

最后一项已经有正式 case 的完整事件证据，后面单独说明。

# 三、目前最强路线：独立分支 × 内部阶段，再进一步压成资源操作词

## 3.1 先区分“数据独立”和“资源独立”

我以 eligible 操作 DAG 的弱连通分量作为独立作业。

这里的“独立”只表示**没有计算数据依赖跨分量**。不同作业仍然可以共享输入，同时争用 DDR 和 L2；所以不能把各作业单独评估的时间相加或取最大，代替全局 E0。

但是，当每个作业整体放在一个核心时，跨核 COPY 同步边可以消失。这使我们能够把重点转向：

> 同一个核心上，多个作业的内部阶段应该怎样交错，才能兼顾共享输入驻留和 M/V 流水重叠？

---

## 3.2 一般构造：时间切块和仿射交错

时间切块有两个低维参数：每波包含多少作业，以及每个作业内部一段包含多少操作。

例如，不再按“作业 0 全做完，再做作业 1”，而是：

```text
这一波所有作业的第一个阶段
这一波所有作业的第二个阶段
……
下一波
```

相同波、相同阶段合成一个子图。每个作业内部的拓扑次序不变，跨作业没有 eligible 依赖，因此商图合法性有直接的单调阶段结构支撑。

另一种更细的构造是给作业 j 中的操作 v 一个**仅用于排序**的坐标：

\[
\theta(j,v)=P_j(v)+j\Delta,
\qquad
P_j(v)=\sum_{\substack{u\text{ 在作业内}\\\text{先于 }v}}\max(1,c_u).
\tag{R2-01}
\]

按这个坐标和原始 ID 排序，编译成公开子图优先级。**坐标随后丢弃，不作为真实时间提交。**

这把大规模排列搜索，缩成了少数阶段宽度、波次大小和相位斜率的选择。最后输出仍然需要覆盖全部操作；减少的是**搜索维度**，不是假装消除了线性大小的 JSON。

### 一个非常清楚的真实收益：case044 的 spill 消失

Q2、4 核，保持核心归属不变：

| 指标 | 整分量分核 | 阶段宽度为 4 的时间切块 |
|---|---:|---:|
| Makespan | 124268 | **68057** |
| 切图新增搬运 | 2791200 B | 2791200 B |
| spill 新增搬运 | 2887424 B | **0 B** |
| 核 0 的 Step3 L1 峰值 | 524192 B | **160000 B** |

这里不仅是“看起来复用更好”：**核心没换，切图新增搬运没变，改变同核阶段组织就消除了官方插入的 spill。**

但无 spill 不等于无 MEMORY_REUSE 边。那些依赖仍在准备产物里，不能删掉。

## 3.3 更强的特例：重入 M/V 资源操作词

实际扫描发现三个整图匹配的同质作业族：

- case008：108 个作业；
- case095：462 个作业；
- case084：1077 个作业。

每个作业的计算 Pipe 结构都是：

\[
M(a)\ \longrightarrow\ V_1,\ldots,V_s
\ \longrightarrow\ M(a),
\qquad
\sum_i c_{V_i}=b.
\tag{R2-02}
\]

这里没有真的合并 V 算子，只把它们视为一个阶段来构造顺序。

case008/095 的两次 M 各为 1158 cycles，V 阶段合计 2196；case084 则分别是 588 和 1152。它们都适合尝试一个很小的前视量：

\[
h=1+\left\lceil\frac ba\right\rceil.
\tag{R2-03}
\]

本轮三个族都得到前视 3 个作业。把作业 i 的首次和末次 M 分别记为 \(F_i,B_i\)，指定：

\[
\begin{aligned}
\mathcal W_M&=(F_0,F_1,F_2,B_0,F_3,B_1,F_4,B_2,\ldots),\\
\mathcal W_V&=(V_0,V_1,V_2,\ldots).
\end{aligned}
\tag{R2-04}
\]

尾部再排完尚未执行的 B。

**直觉是先给 V 阶段提供少量在制品，再交替执行新作业的首次 M 和旧作业的末次 M，避免 M 等待单个作业完成整个 V 阶段。**

实现不是把上述时间线交给理想调度器：程序将原 DAG 加上两个计算 Pipe 词的相邻边，检查无环，求一个拓扑优先级，随后编译为 singleton 子图。真正的运行时间继续由 E0 决定。

### 这个特例可以证明什么？

在**没有 COPY、同步、内存约束**的理想双执行器模型中，对独立、相同的作业，且 V 阶段不长于两个 M 阶段之和，上述词满足：

\[
2am
\le T^*_{\mathrm{ideal}}
\le T_{\mathrm{word,ideal}}
\le 2a(m+1).
\tag{R2-05}
\]

下界来自 M 总工作量。上界可以通过显式安排每隔两个 M 时长启动一个 V 阶段、配置有限启动和收尾段证明；备忘中给出了完整构造，包括一、两个作业的边界情况。

**这个上界不是官方模型上界。**实际 COPY、spill、内存复用和带宽争用都可能使它失效。它的价值是解释为何只需一个很小的前视词，而不是搜索所有作业排列。

### 官方结果

| case / 问题 / 核数 | 整分量 LPT | 仿射交错 | 解析资源词 |
|---|---:|---:|---:|
| 008 / Q2 / 4 | 123060 | 64686 | **63768** |
| 095 / Q2 / 4 | 524422 | 270604 | **269686** |
| 084 / Q2 / 4 | 629028 | **317988** | **317988** |
| 084 / Q3 / 4 | 629028 | **317988** | **317988** |

**case008 最有解释力：核心归属、全部搬运分项完全一致，spill 都为零。**每核 M 必需工作量是 62532 cycles，V 是 59292 cycles；从 123060 降到 63768，主要来自计算流水重叠，而不是少搬数据。

对这个已通过 E0 的方案，可以使用真实问题的计算工作量下界：

\[
LB=
\max\left\{
CP_{\mathrm{compute}},
\quad
\max_r\frac{\sum_{v\in r}\max(1,c_v)}K
\right\}.
\tag{R2-06}
\]

因此：

\[
0\le
\frac{T-T^*}{T^*}
\le
\frac{T}{LB}-1.
\tag{R2-07}
\]

case008 的资源词方案距离这个有效下界的相对差距上界为 **1.977%**。这比只报告“比某个弱基线快近一倍”更有说服力，但仍不是最优性证明。

该构造也跑了其他核数：case008 在 2、3、5 核下分别为 **125682、84303、52291**；并非仅在四核上有效。

# 四、耦合图不能只靠分支交错：强张量合并＋唯一最细无环闭包

当大部分工作都在一个弱连通分量内，上一条路线缺少可以交错的独立作业。这里真正有用的是一个结构性粗化方法。

先选少数张量大小阈值，把超过阈值的**内部张量**的生产者和消费者设为 must-link，使用并查集合并。然后对粗商图求强连通分量，将每个 SCC 整体合并。

关键不是“用 SCC 修一下环”这么简单，而是有一个准确结论：

> **固定初始 must-link 分区之后，商图 SCC 缩并给出的，是唯一最细的无环粗化。**

证明很短：一个 SCC 内任意两块都相互可达；若它们在最终分区中仍不同，这些路径投影到最终商图上仍构成双向可达的闭合游走，最终商图不可能无环。因此所有合法粗化都必须合并该 SCC；而 SCC condensation 本身就是 DAG。

这个结论提供了两点价值。

首先，合法修复不再是随意局部移动，而是有**最细性证书**的闭包。

其次，阈值降低时 must-link 只会增加，因此闭包形成嵌套粗化层级。当前原型只试四个固定阈值，尚未实现“只枚举层级变化断点”的增量版本；这是下一步可以进一步减少构图与评估次数的地方。

该路线在追加对照中的 case046、case048 上效果很明显，但不是普适解。**case002/Q2 中，简单 topo-64 方案为 78828，而强张量方案最好为 106130。**因此简单拓扑构造必须继续保留，不能为了理论结构整齐而移除。

我重新阅读了 Popp、Schlag、Schulz、Seemaier 的 *Multilevel Acyclic Hypergraph Partitioning*，特别是其无环收缩条件及证明。论文并不支持“同一块内任意收缩都安全”；本轮采用的是上面直接证明的 SCC 最细闭包，并没有声称实现了该论文完整的多层与模因算法。:chatgpt-content-reference{index="7"}

# 五、输入乘积路线的真正修正：先识别输入束，而不是要求每个作业只有两个 tensor

上一轮“每个作业使用两个输入”的模型，对真实数据太窄。

**真实图中，一个作业可能使用几十个输入，但其中许多输入被完全相同的一组作业消费。**先把这些输入的消费支撑合并，才会显露乘积结构。

令 H 的行为独立作业，列为核内计算部分的输入边界张量——通常是原 COPY_IN 的输出；X 是作业到核心的 one-hot 归属：

\[
H_{jt}=\mathbf1[j\text{ 使用 }t],
\qquad
X_{jk}=\mathbf1[j\text{ 位于核心 }k].
\tag{R2-08}
\]

当作业整体分核，Q2/Q3 在尚未插入 spill 的准备阶段，这部分入口 COPY_IN 字节为：

\[
D_{\mathrm{ingress}}(X)
=
\sum_t s_t
\sum_k \mathbf1[(X^\top H)_{kt}>0].
\tag{R2-09}
\]

**相同 H 列支撑可以合成一个加权输入束，对这个静态函数精确。**但不能合并真实 tensor、cache key、访问次数或取整后的服务时间。

这与 Çatalyürek、Aykanat 的超图通信建模中“按数据触达的分区，而非按操作对边数计费”的机制一致；其经典分布式 SpMV 模型还有输入所有者假设，不能把论文中的通信公式原样当成本题全局代价。:chatgpt-content-reference{index="8"}

随后，每个触达两个输入束的作业，在“输入束图”上作为一条边。通过二着色、完整二部连接和支撑闭合检查，识别真正的矩形坐标。

实际发现：

**case011：176 个输入边界张量压成 8 个输入束，显现 4×4 结构。**

**case080：279 个输入边界张量压成 9 束，显现 6×3 结构。**

100 例中，检测到 **14 个 case 含非平凡二维乘积分量，10 个覆盖全部作业**。其余不强行补成矩形。

这条路线目前有实际但有限的收益：case080/Q2 的二维分核方案从 **111314 降到 107030**，约改善 3.85%。然而，case037/Q2 的一个细切矩形方案达到 **96153**，远差于 **53320** 的分量方案。

**所以它值得作为专用构造器，但证据不支持把它作为全体图的主算法。**

| 095 | Q3 | 524422 | **270604** | 48.40% | 42.35 / 39.58 秒 |
| 021 | Q3 | 1550324 | 1550324 | 持平 | 1.92 / 2.07 秒 |

这里有三个不能省略的限制。

**第一，相同的是联合预算上限，不是每组恰好执行相同次数。**B0 有些有限候选族提前耗尽。我额外检查了共同调用数前缀：七项改善都保留；但 case063 的共同 12 次前缀中，结构为 **313398**，B0 为 **311656**，结构差约 **0.56%**，之后才恢复持平。

**第二，case021 不是“没有认真搜索”。**它的首个共同候选已经非常接近式（R2-06）的下界，因此两种方法都在一次 E0 后按证书停止：下界 **1548000**，结果 **1550324**，相对差距上界约 **0.1502%**。

**第三，新增解析资源词不在这个冻结版本里。**它后来把 case095 进一步降到了 **269686**，但不能追溯修改上表，把两个版本的最好数字混成一份算法成绩。

## 最大图的压力测试也暴露了时间—质量权衡

case014 的两策略都限于 300 秒、8 次 E0：

| 方法 | 最好 Makespan | 冷端到端 |
|---|---:|---:|
| B0 | 4523354 | 106.58 秒 |
| 结构方法 | **4462846** | 135.41 秒 |

最终改善约 **1.34%**；但在共同的约 106 秒内部时间前缀，结构方案仍略差，收益来自更晚的候选。

因此，正确结论是：

> **这套结构构造已经能在大图单例预算内工作，并获得更好的已确认方案；还不能声称它在任意较短时间窗口都更好。**

# 七、必须保留的失败与语义证据

## 7.1 “交错越密越好”已经被实际反例否定

case008/Q2 的仿射比例：

| 比例 | Makespan | spill 新增搬运 |
|---|---:|---:|
| 0.03125 | 218022 | 7962624 B |
| 0.0625 | 117124 | 3096576 B |
| 0.125 | **64686** | **0 B** |

这是非常适合写进方法分析的结果：**相位组织的收益与驻留容量阈值耦合，最激进的并行展开反而最差。**

同一构造在 Q2/Q3 也可能排序反转。case080 的某个仿射方案在 Q2 比分量方案更差，在 Q3 却更好。这进一步否定了“少搬运”“高命中率”可以直接当 Makespan 排序依据的想法。

## 7.2 在正式图中观察到了两类 Cache 后果

**在飞 hit 被淘汰后重新插入：**case080 中，某 key 在 **42333** 命中，**42345** 被其他完成事件淘汰，**42355** 随原 hit 完成重新插入。它不是只存在于人工 FIFO 单元闭包中的转移。

**spill 重命名后真实命中：**case044/Q3 的一个计划中，观察到 **93 次重命名 COPY_IN 通过 `logical_tid` 命中，总计 2,887,424 B**。保存了物理 tensor ID、logical ID、版本、操作、核心和真实访问路径之间的对应。

这补上了上轮“只验证到 cache key 层面”的缺口，但结论仍限定于这些已运行的实际图和计划。

## 7.3 精确压缩也可能不值得在线使用

我实现了一个保留完整准备顺序的优先级桶合并：相邻稳定桶在 raw Step1 中位置递增时可以合并；必须保留的下降点给出该顺序粗化域的最小分界数。

它把四个计划的子图数分别从：

```text
864 → 416
5120 → 1860
3696 → 1832
1098 → 236
```

四图各三对重复中，操作时间、搬运和缓存行为投影全部一致。**但完整 JSON 的子图诊断不同，所以这不是 E1 full 零差分。**

更关键的是，把额外前缀构造和检查成本算进去，四组端到端中位时间全部变慢。**因此我没有把它放进默认搜索器。**

这也是对上轮“数学压缩可能自动带来评估加速”的一次实质修正：压缩必须有摊销对象，否则只是把工作提前做了一遍。

# 八、工程上现在应保留什么，暂时不做什么

**保留 CPU 路线。**本轮没有使用 E1/E2、CUDA 或 Metal。标准库 Python 的结构构造加完整 E0 已能在所测大图上满足建议预算；没有必要先把不规则事件循环搬上 GPU。

资源词单候选在 case008 的“构造＋完整 E0＋归档”约为 **0.90 秒**，case084 约 **3.32 秒**；这两项是实验驱动内的单候选口径，不能冒充外层冷启动。真正的冷端到端数据已经单独列在对照表。

**下调上轮分层最小割和端口消元的实施优先级，但不宣称它们被实验击败。**本轮没有把完整 min-cut 方法与这些原型做同预算对照，因此不能说它一定更差。只是目前已有直接、便宜而且能被 E0 确认的计算词与阶段构造，更值得优先扩展。端口消元则仍受 binary64 逐事件结算等价性约束，不宜贸然进入精确评估器。

**Q1 不与 Q2/Q3 强行共用粒度。**本轮有 132 次 Q1 调用及真实收益、失败例，但最强的预冻结追加对照集中在 Q2/Q3。Q1 的细切会引入独立 Task 边界与切换，不能因为 singleton 在 Q2/Q3 合法有效，就直接照搬。

交给工程 Agent 的后续研究重点，应当只有三个：

| 优先研究项 | 已有基础 | 下一项真正需要验证的东西 |
|---|---|---|
| **资源词编译推广** | 同质 M→V*→M 原型、理想界、真实 E0 收益 | 长短两类作业或局部相同资源词，是否仍能用极少词候选覆盖好方案 |
| **相位与驻留联合构造** | 时间切块消除 spill、仿射密度反例 | 根据具体 spill 生命周期生成少量阶段边界，是否优于固定比例 |
| **强张量无环层级** | SCC 最细闭包与四阈值原型 | 只在闭包变化断点构造候选，是否能减少评估而不丢掉好尺度 |

原型包中，`solve.py` 保留了冻结对照版本；新增的 `word_cli.py` 单独提供资源词构造和 E0 确认。README 给出了原始数据提取、运行和完整结果复跑命令。

**这轮最值得写进论文的方法贡献，是“从真实官方展开语义推导可控制的计算顺序，再用结构识别将排列空间压成少量资源词和阶段参数”。**证据已经能区分流水重叠、spill 消除、输入复用、缓存后果和额外准备成本；下一步应沿这些已经产生真实收益的机制扩展，而不是继续增加未经官方验证的算法名称。
