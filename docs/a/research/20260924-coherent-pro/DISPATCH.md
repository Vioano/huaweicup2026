## 执行次序与可验收交付

### 第一步：共同底座的静态准备

1. **任务目标**：核定旧算法的可复用部分、现有后端支持域及最小共用接口；确定一个共同控制层写者。
2. **输入文件**：上述固定归档，当前各专项固定代码/任务卡，`docs/a/OFFICIAL_OBJECTIVES.md` 和官方源码身份；未知旧运行原件单列缺口。
3. **输出要求**：seed 支持/失败表、能力/真实调用表、精确接受及回退契约、见证索引、共同接口所有权与下一步最小任务卡。每项结论区分原文、源码核对、作者报告和本机实测。
4. **限制条件**：新增 solver/evaluator/native 运行为 0；不重写生产代码，不建立新常驻服务、不运行包内 Goal。原任务已有明确授权单独保留，不由这张建议扩张或取消。
5. **验收标准**：同一个 (G,q,k,C,H) 还需记录参考 runtime/入口和有序 plan 身份；三问支持与 fallback 调用可追到固定源码；缺数据明确未知；确认一个共同控制层写者，没有多个任务改同一 schema。
6. **截止时间**：本次调度先交静态结论；后续本人开始时回报首检查点，具体时限与运行额度由原任务卡冻结。Pro 的两小时/96次建议不自动生效。

### 第二步：先有可保留的合法结果，再接机制

共用外层维护已精确确认的 incumbent；各问现有算法提供 seed 或候选。非法、失败和未确认结果不能替换 incumbent。精确接受先比较 Makespan，额外 DDR 作为明确的次级比较；质量—时间取舍另表，不造官方加权总分。

搜索 frontier 与 incumbent 分开。探索可经过暂时劣解、可一次提出大型协同宏；不能把“正式输出不退化”实现成每一步只能贪心改善。评分缓存不自动合并未来动作能力不同的状态。

**接受规则只保护已经确认的方案质量，不能单独保证固定墙钟下质量不退化。** 所有在线构造、准备、检测、精评、fallback、超时收尾和合法落盘都计入端到端成本；预留恢复/落盘余量。先输出或可靠保存保底，余量不足则不发昂贵候选。旧基线本身失败时应保留失败类别并报告覆盖缺口，不能将未评分候选叫“精确保底”。

操作 receipt/rollback、父状态身份与当前证书够用即可。C 的结构可达定理需使用目标数据依赖和全部核顺序的联合拓扑序，且仅限声明的结构/编码域；无需把该证明路径逐步在线执行，也不能升级成 P_exec 连通或线性求解时间。

- **D3**：Fang 主做资源重入模板的适用条件/反匹配，Nikola 的 P2 专项保留独立对照。优先新图或新核数的预先预测，不继续围绕 case008 扫参数。计算模板一致不等于完整张量图同构。

每条先交固定正例/反例、一个预测与能推翻它的最小实验。批准运行时一次只派明确的图/plan/q/k/版本/命令/调用数/墙钟/RSS/停止条件，失败和回退计真实消耗。两台机器可各自并行研究，时延对照在各宿主机安排独占窗口；同机多个 session 不等于能同时开多个计时实验。
