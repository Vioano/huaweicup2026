# A 题：形式化与双层高速评估器任务契约

版本：v1.0（2026-09-23）  
用途：队长批准后交给 Codex，映射到组内已有任务图、Skill 和通信协议。  
性质：**队内工程标准，不是官方评分细则；不代表高速评估器已经实现或已证明正确。**

## 0. 已确定的目标与职责

本轮建立三种评估能力：

|代号|名称|用途|结果权威性|
|---|---|---|---|
|E0 / `oracle`|原版官方 Python 评估器|真值、回归、最终结果|该冻结版本上的官方输出|
|E1 / `exact`|热点重写的等效加速版|候选精筛和高可信搜索|在声明范围内通过一致性验收；最终仍由 E0 复核|
|E2 / `proxy`|重构的极速近似版|大规模候选探索、粗筛|估计；不可当作官方成绩或执行可行性证明|

业务链路：`候选 → E2 粗筛 → E1 精筛 → E0 最终确认`。

用户确定的人员分工：一位成员负责形式化，另一位成员负责高速 evaluator 探索。逻辑上分为 FORM、EXACT、PROXY、TEST 四个模块，并不要求四个人。EXACT 与 PROXY 可以由同一成员管理的不同 Agent 并行探索；TEST 由队长的独立 Agent 或非实现者复核，不增加一个未经确认的人类岗位。

**队长定义交付、接口、边界、验收；成员保留选语言、数据结构、优化方法和实验路线的自由。** 不把算法写死，也不要求模拟人类公司的多层角色。

- 题面 PDF，尤其第 3、8—14 页。
- 附件 `README.md`、`data/config.txt`、`code/` 下十个 Python 文件的入口和关键路径，以及两份 `docs/` 说明。
- 当前附件 ZIP SHA-256：`3112331344df7dcf2dcef2ff5f789669c0419e32cefbbc6e2742b9e36d5c43c9`。
- 全文件哈希和 100 个正式用例的规模记录：`audit/official_source_manifest.json`。
- 已运行两个人工小图、每图三个问题，共六次原版函数调用；记录在 `audit/smoke_results.json`。**这不是性能测试，不是完整代码审计，也不是 E1/E2 的验收。**

### 1.2 权威边界

题面与官方澄清定义竞赛要求；冻结代码定义当前要复现的实现行为。两者不一致时，记录而不偷偷调和：

- E1 的兼容行为依据冻结 E0，但不得把代码额外接受的输入自动说成题面合法输入。
- 正式实验保持官方配置，并用未改动的 E0 重算。
- 发现疑似错误时，提交最小复现、题面位置、代码位置和影响；由队长决定是否请求官方澄清。不得利用异常行为伪造好成绩。
- 新代码包或澄清到来后建立新版本，不覆盖旧版本，受影响测试和结论重新验收。

### 1.3 必须固定的环境信息

记录官方文件哈希、配置哈希、Python 版本、依赖、操作系统、CPU/GPU、线程/进程数、构建参数、随机种子。正式参考环境由队长指定；不得只因不同机器输出不同就任选一个结果。

`official_code_hash` 的可复算定义及当前值在 `audit/official_source_manifest.json` 中；原始图、方案、配置的身份默认使用文件原始字节 SHA-256，未经证明不做会改变顺序的语义归一化。

原版放只读目录，工作副本和优化实现放别处。Oracle 输出采用每个请求独立目录；并发运行不得使用会互相覆盖的默认结果路径。

## 2. 共用接口与版本规则

### 2.1 方案接口不改

原始图继续用题目 JSON。方案只能包含官方两字段：

```json
{
  "node_to_subgraph": {"11": 0},
  "core_schedules": [[0], []]
}
```

不要把置信度、模型参数、debug 字段塞进官方方案。它们放评估请求或报告中。核心数量由 `core_schedules` 外层长度确定；若请求另带核心数，适配器必须检查一致。

### 2.2 统一评估入口（待实现接口，不是现成命令）

```text
python -m team_eval evaluate \
  --engine oracle|exact|proxy \
  --problem 1|2|3 \
  --graph GRAPH.json --plan PLAN.json --config config.txt \
  --detail metrics|full --output RESPONSE.json

python -m team_eval evaluate-batch \
  --engine proxy --requests REQUESTS.jsonl --output RESPONSES.jsonl
```

同一个批次中每条请求有独立 `request_id`。响应可以乱序到达，但必须靠 ID 对应；不得靠行位置猜测。

供搜索器使用的常驻接口：

```python
prepare_graph(graph, config, problem) -> GraphContext
# 只缓存与候选方案无关的解析/索引；返回对象有版本与哈希。

evaluate(context, plan, detail="metrics") -> EvalResponse
# 包括所有仍依赖该 plan 的构造、局部展开、全局检查和模拟。

evaluate_batch(context, plans, detail="metrics") -> list[EvalResponse]
```

CLI 负责严格读入，包括重复 JSON 键检测；内存接口的调用前提必须明示。内部 prepared-task 接口可以自定，但不得把其成本藏出端到端计时。

### 2.3 响应的最小语义

机器字段契约见 `contracts/eval_request.schema.json` 和 `contracts/eval_response.schema.json`。

关键字段：

- 身份：`request_id`、`engine`、`engine_version`、`contract_version`、`official_code_hash`、`graph_hash`、`plan_hash`、`config_hash`、`problem`、`num_cores`。
- 状态：`ok / invalid / timeout / unsupported / error`。
- 检查深度：`input / plan / execution` 三项各为 `pass / fail / unchecked`。
- 数值性质：`official / matched_contract / estimate / none`。
- 输出：成功时带 `metrics`；失败不返回貌似成功的部分 Makespan。
- 成本：计时分解、内存峰值、是否回退及其次数、实际调用 E0 的次数。
- 证据：完整输出/Trace/反例的路径和哈希；E1 标明适用测试范围，E2 标明近似假设和风险标记。

超时和程序崩溃**不等于方案非法**。未知状态不能伪装成 `invalid`，也不能用 0、负数或 NaN 冒充有效指标。JSON 不允许非有限数。

### 2.4 兼容模式

`metrics` 为明确字段投影；`full` 为官方结果 JSON 的兼容输出。E1 至少最终支持这两档。E2 只需支持 `metrics`，不能生成伪官方 Trace；不支持的档位明确返回 `unsupported`。

E1 的 `full` 输出是解析后的 JSON 值一致，不要求缩进或对象键顺序相同；列表顺序默认有语义，不得随便排序后再比。仅路径/文件名等非语义元数据可以经过**预先冻结的白名单**归一化，不能忽略时间线、Cache 事件、ID 等“难对齐”字段。

### 2.5 共享中间表示的最低要求

必须分清 `原图`、`Task 边界图`、`Step2 spill 扩展图`、`Step3 执行图` 四层，不能都叫 graph 然后混用。

PreparedTask 至少要能表示：原始/生成 ID 对照、`logical_tid`、子图归属、扩展操作序、固定 `pipe_ops`、数据及内存复用依赖、跨核 COPY 端点、工作量与舍入语义、局部内存统计及来源。与 E0 对照用的检查点见第 4 节。

缓存键至少区分完整输入版本、problem、config、图/方案身份、引擎版本。不得因为“图同构”就重编号后命中缓存：ID、输入顺序、生成 ID 和 tie-break 可能影响官方启发式。

## 3. FORM：形式化标准

### 3.1 什么叫完成

**不是 PDF 摘要，也不是写一个带容量约束的优化式子。** 完成标准是：另一位成员只读形式化规范及其明确指向的待决项，就能知道候选方案如何被接受、拒绝、展开和计分，不需要自行猜测隐藏规则。

形式化同时提供两个视角：

1. 研究视角：决策变量、约束、目标、何处可能改进、哪些代价可以近似。
2. 实现视角：确定状态、更新顺序、数值语义、错误出口、可逐步比对的中间产物。

总体对象：

\[
E_v(G,P,C,q;R)\longrightarrow (\text{status},\text{result}),
\tag{F-01}
\]

这里 v 是官方代码版本，G 是原图，P 是方案，C 是固定配置，q 是问题编号，R 是锁定的参考运行环境。形式化必须保留“固定核内启发式”这一事实：候选方案并没有自由指定全部操作的精确启动时间。

### 3.2 八个必须覆盖的模块

|模块|必须回答的问题|主要代码入口|
|---|---|---|
|F-IO|字段、类型、重复键、ID、配置、错误与输入域|`contest_io`、`evaluation_validation`|
|F-PLAN|操作覆盖、COPY 排除、子图收缩无环、核心顺序、空核|`derive_multicore_plan`|
|F-TASK|A/B Task 组织、边界输入输出、多消费核计数、生成 ID、COPY 属性|两个/三个 `_build_scene_*_tasks`|
|F-LOCAL|Step1 精确排序；B 的稳定子图优先级重排；Step2 spill 与 backing；Step3 排布|`schedule_step1/2/3`|
|F-EXEC|固定 Pipe FIFO、虚拟字节额度复用边、组合图的环检测|`prepare_step3_execution`、`validate_task_order`、`validate_execution`|
|F-TIME|A 的 100/1000 等待、B 的 500 同步、ready/issue/retire 次序、同刻事件|`evaluate_scene_a/b`|
|F-RESOURCE|DDR 与 Cache 共享池、最短耗时、取整、浮点容差、FIFO 插入淘汰及键|`_op_duration`、`evaluate_problem_3`|
|F-METRIC|每个输出字段的定义、来源与适用范围；原图/切图/spill 统计；单核基准|结果组装、`singlecore_evaluate`|

模块边界不是要求逐行翻译 Python；必须给出足够明确的前后置条件、状态转移与确定性选择规则。

### 3.3 每条规则使用同一张“规则卡”

`rule_id / title / scope / kind / symbols_and_units / preconditions / transition_or_predicate / outputs / failure_behavior / tie_break_and_rounding / sources / positive_tests / counterexample_tests / implementation_sites / status`。

`kind` 区分：题面要求、实现行为、测试观察、推导结论、团队近似假设。不能混写。

来源必须有文件路径、符号名、行区间、该文件哈希；题面用页码/小节。公式逐一编号、量纲明确，空集合、零工作量、并列候选和失败情况均有定义。采用数学定义、确定性伪代码、状态转移和可运行测试即可；本轮不要求引入专用定理证明器，也不以重新实现完整官方程序作为 FORM 的前置验收条件。

每条影响接受/拒绝、顺序、时间、流量的规则至少对应一个正例；有分支/边界的规则再对应一个反例或边界例。纯 I/O 元数据可用模式测试覆盖，不要求机械凑微型图。

### 3.4 必须特别处理的实际代码细节

1. **基础校验通过不保证全局可执行。** A 还检查子图依赖与同核 Task 顺序合并后的图；B/题三检查本地执行依赖、固定 Pipe FIFO、跨核 COPY 合成的图。
2. **Step3 是语义的一部分。** 它固定 Pipe 顺序，并用可拆分虚拟字节额度产生 WAR/WAW 内存复用边。后续多核模拟遵守这些依赖；不能重新“尽早调度”成另一种更好的排布。
3. **计时不是未经取整的理想流体模型。** `_op_duration` 包含最短 1 cycle 和向上取整，共享池另有浮点状态、容差与整数化。必须写清舍入发生在哪一层。
4. **题三按 COPY_IN 的逻辑张量键处理 Cache。** 不能自行缩窄成“只有原始外部输入可缓存”，也不能默认合并同时未命中的请求。
5. **流量字段与物理 DDR 服务字节不可混同。** 当前题三的 `data_movement_bytes` 在 Task/Spill 展开时统计；不能擅自从 `scheduled_copy_bytes` 扣除 Cache 命中字节。`cross_task_traffic` 也不是同义字段。
6. **内存峰值的来源必须写清。** 当前返回的 `memory_peak_by_core` 来自 Step3 局部结果，不能悄悄换成另一套全局重新模拟峰值后声称完全等效。
7. 记录文档和实现差异。例如题面原图只允许二部边，而当前输入 validator 没有一概排除 Op→Op；内部展开图确实有直接 Op→Op 边。必须分域，不据此扩张竞赛合法输入。
8. 原始/重命名 tensor、同一逻辑数据、DDR backing、临时生成节点不能只凭名字合并；排序和 spill 并列选择依赖的插入顺序必须保留。

本条是审计优先清单，不代表已穷尽全部行为。证据与代码定位见 `audit/READ_AUDIT.md`。

### 3.5 FORM 交付物

- `formal/SPEC.md`：词汇、数学对象、八模块、状态机、指标字典。
- `formal/rules.jsonl`：规则卡，规则 ID 可稳定引用。
- `formal/coverage.json`：规则—代码—测试映射；未知不能计为已覆盖。
- `formal/ambiguities.md`：差异、未知、可能影响、复现和队长决定。
- `formal/change_impact.md`：移动/合并/拆分/重排如何影响 Task、ID、COPY、spill、FIFO、全局模拟以及缓存失效。
- 已交给 TEST 的手算/边界夹具与预期，附证据。

FORM 验收：八模块齐全；影响计分的必需规则均有来源和测试；关键未知要么解决，要么让相关 E1/E2 能力显式标为不支持。不能用文档页数或公式数量验收。

## 4. EXACT：热点等效加速版标准

### 4.1 任务范围

先对 E0 做分阶段 profiling，再选择热点。语言和技术不限；不得预先认定浮点、事件循环或某个 Step 一定占主要时间。保留 E0 只读。

性能记录至少区分：输入解析/校验、边界构图、Step1、Step2、Step3、全局检查、全局模拟、结果与 Trace 构造、序列化及磁盘写入。每个优化提交说明改动的规则范围、预期收益和风险。

### 4.2 等效定义

在冻结输入域、配置、版本、环境上，E1 应与 E0 同意成功/失败；成功时应产生相同的约定可观察结果：

\[
\operatorname{Obs}(E_1(x))=\operatorname{Obs}(E_0(x)).
\tag{F-02}
\]

`Obs` 必须预先固定：

- 评分层：Makespan、全部搬运分项、Cache 命中/未命中字节与次数、命中率、题型与核心数。
- 诊断层：Task/Op/跨核传输时间线、内存峰值、Step3 摘要、Cache 事件与最终项等 full 结果。
- 失败层：成功或拒绝一致、失败阶段和语义类别一致；不要求 Python 栈路径/异常全文逐字一样。尚未归类的异常原样保留为 error，不能乱贴 invalid。

**所有整数计时、字节、计数必须精确相等，不接受“误差小于 1%”。** 命中率优先由相同计数用原版 Python 输出层计算，full 模式的浮点输出同样必须匹配；不能用宽松 `isclose` 掩盖分歧。

实现可更换数据结构/算法，只要保持可观察行为。默认发布关注正式数据与 1—5 核；更广输入域单独声明。若使用定长整数而参考 Python 输入范围更广，越界时必须显式回退/不支持，禁止溢出或经浮点解析损失 ID 精度。对排序、生成 ID、同刻事件、浮点运算顺序、fast-math 等可能改变控制流的优化必须有针对性对照。

### 4.3 分层检查点

不要只比最后 Makespan。按需导出以下语义快照：

1. `plan_view` 与依赖对。
2. Task 图、边界 COPY、跨核 links、生成 ID。
3. Step1/子图重排序列。
4. spill 记录、重命名 tensor、Step2 扩展图。
5. Step3 `pipe_orders`、`execution_graph`、内存复用边。
6. 全局事件序列与结果。

可在调试副本/测试适配器中采集；原版最终 E0 不改。出现差异先定位首个分歧检查点，不先“调一个容差使结果过关”。

### 4.4 等效性声明与回退

通过有限测试只能写“在指定测试集和环境内零不一致”，不能写“已证明所有输入完全等效”。若真有局部证明，明确假设和证明范围。

未支持的输入或故障可回退 E0，但记录 `fallback_used`、原因、时间、调用数。不能靠大量隐式 E0 调用伪装 E1 的正确性或速度。原生快路径与含回退的整个服务分别报告。

### 4.5 增量与缓存

先做无缓存一致性，再做缓存。缓存命中、冷启动、反复乱序请求结果都必须一致；一个请求的 L2/在途 COPY/内存状态不得污染下一个请求。

不得假设“改 Core1/Core2 就只影响这两个核”。边界 COPY 的生产者/消费者、全局生成 ID、相邻核和共享带宽都可能受影响。根据 FORM 的变更影响表做失效；证明不了的范围宁可重算。复用局部 prepared Task 后仍需满足其实际依赖签名；全局模拟是否可复用另行证明。

### 4.6 E1 验收

- 必需一致性矩阵中零未解决差异；任一关键错误阻断对应范围发布。
- full 与 metrics 投影互相一致；validity 不能只做静态校验。
- 有 profiler 前后对照、冷/热/批量/全 CLI 计时和可复现脚本。
- **队内初始性能目标**：在冻结的中大图矩阵上，配对热路径速度比几何平均至少 3 倍；至少 90% 配对不低于 0.8 倍。小图和 full CLI 单独报告，不用它们的 I/O 差异刷倍数。
- 性能目标未达到但正确性通过，可发布为“正确候选/部分热点加速”，不能宣称达到高速验收。

## 5. PROXY：极速重构版标准

### 5.1 任务范围

允许彻底重构、向量化、GPU/CPU 批处理、近似时间推进、统计/学习成本模型、局部代价模型等。不限与 E1 同语言。目标不是“像官方”，而是**以低总成本保留足够好的候选给 E1**。

允许不复现浮点、部分启发式或完整事件流程，但必须在 `proxy/APPROXIMATIONS.md` 逐项写：近似/忽略了什么、为什么省时、预计偏差、失效场景、如何检测和回退。

### 5.2 哪些不能含糊

输入/方案结构检查仍须严格；例如缺操作、重复子图、基础子图环不能成为“预测很优”的合法方案。更深的执行合法性若没完整检查，响应明确 `execution: unchecked`。E2 的 `status: ok` 只代表估计完成，不代表官方可执行。

E2 不给未经校准的置信概率；可给风险标签、残差分层和 OOD 标记。不能把未知当作高置信优解，也不能仅因一个估计器不支持就删掉候选。

### 5.3 最重要的指标：粗筛造成的质量损失

固定同一图、同一问题、同一核数的一组官方可行候选 C。所有候选都必须先由 E0 得到真值，不能只评价代理筛出来的候选。

默认保留数与短名单为：

\[
m=\min(|C|,\max(8,\lceil0.1|C|\rceil)),\qquad S=\text{代理预测最好的 }m\text{ 个候选}.
\tag{F-03}
\]

每组池至少 64 个候选，避免“全留就零损失”。定义短名单遗憾：

\[
r(C)=\frac{\min_{p\in S}M_0(p)-\min_{p\in C}M_0(p)}{\max(1,\min_{p\in C}M_0(p))}.
\tag{F-04}
\]

它问的是“经粗筛以后，还能找到的最好方案比原候选池里最好方案差多少”，不是相对未知全局最优值的误差。

若 S 没有官方可行方案，整组失败，不从统计中删除。性能测试中的非法候选池另外报告；上述排名池只比较官方可行候选，混合池另测安全行为。

### 5.4 队内 v1 初始质量目标（不是官方要求）

|项|建议发布门槛/诊断目标|
|---|---|
|短名单质量|至少 95% 的测试池保留一条距该池 E0 最好值不超过 1% 的方案|
|短名单遗憾|中位数不超过 1%，P95 不超过 3%；逐场景与最差池单列|
|数值误差（校准 Makespan 模式）|绝对相对误差中位数不超过 3%，P95 不超过 10%|
|排序诊断|报告同池 Spearman、显著差异候选的成对顺序准确率；不能拿不同大/小图混合相关系数代替|
|非法/未知|结构非法不得返回通过；未做深层检查就明确 unchecked；高风险/未知不能硬淘汰|

相对误差定义：

\[
e(p)=\frac{|\widehat M_2(p)-M_0(p)|}{\max(1,M_0(p))}.
\tag{F-05}
\]

短名单目标优先于均值误差。如果排序过关但数值校准不过关，只可发布 `rank_only` 能力，用单独的 `rank_score`，不要把分数伪装成 cycles。近似的流量/Cache 指标单独标记，不能进入正式表格；hit_rate 的误差用百分点并报告分子分母。

任何门槛都须在看封存验收集之前冻结。无法达到时报告失败、缩小能力范围或提交队长审批的新版本；不能看完失败样本再悄悄调宽标准。

### 5.5 初始速度目标

在同一资源配置、同等工作量的候选批评估上：E2 相对 E1 吞吐至少 10 倍作为初始门槛；相对 E0 达到 50 倍作为研发目标。以测量为准，不承诺这些倍数必能达到。

必须包含所有 plan 相关构图、特征、设备数据传输与同步，不能只报告一个 GPU kernel 的耗时。CPU 和 GPU 不同资源的比较可报告系统优势，但不能标成相同资源算法加速。

### 5.6 防止代理把搜索带偏

线上粗筛保留当前已确认最优方案、预测优解、结构多样性候选以及少量不按代理分数选取的审计样本；初始将 10% 精评预算用于审计，作为队长可预先调整的参数。

对容量临界、跨核环风险、同时 Cache miss、强 DDR 争用、已知大残差类型，降低剪枝强度或直接交 E1/E0。不能承诺 E2 “收敛到了全局最优”。

把 E2 最看好的新候选交 E0 抽查，发现系统性乐观偏差即回传反例、更新校准/风险规则并重新测试。验收集不得用于日常调参。

## 6. TEST：独立测试与验证标准

### 6.1 测试方案生成器

至少准备三个独立于 E1/E2 内部代价模型的简单生成器，并留一个变化分布做封存测试：

- 固定/随机拓扑序的连续分块，再按顺序分核；作为可复現参考。
- 简单负载估计的列表调度，兼顾计算量而不调用 E1/E2 选方案。
- 共享 tensor/通信偏好的局部聚合，每次合并后校验合法性。
- 随机化拓扑序、不同粒度以及局部 move/merge/split/reorder，主要用于边界与分布压力测试。

“生成器自称合法”不作为证据。需要 E0 分类；保留非法和失败样本，不只保存漂亮成功结果。官方 stub 只算格式演示/随机来源，不算性能基线。

### 6.2 四层测试集

**T0：微型语义测试。** 正/反/边界夹具覆盖全部计分关键规则。至少包括下表各机制；具体数量按规则覆盖而非单纯凑数。

|机制|最少检查|
|---|---|
|JSON/配置|重复键、数值类型/布尔、ID 别名、缺字段、非法配置、未知 Pipe|
|原图/划分|原图环、覆盖缺失、重复归属、原 DAG 收缩后成环、空核|
|A 等待|同核 Task 等待、跨核前驱等待、多前驱取最大、组合顺序环|
|B 执行|部分跨核输入、固定 Pipe 队首阻塞、跨核 COPY 同步、执行组合环|
|Step1/2|并列排序、COPY 优先级、spill victim 并列、已有 DDR backing、反复 reload|
|Step3|虚拟额度拆分/合并、WAR/WAW、多消费者全部完成后复用、固定 FIFO|
|带宽|单/多在途、途中加入退出、同时完成、容量和整数周期临界、零 size/cycles|
|L2|首次 miss、随后 hit、同刻 miss、FIFO 非 LRU、逐项淘汰、零访问、逻辑 ID|
|统计|原图/切图/spill 分项、Cache 命中不改错搬运定义、full/metrics 一致|
|状态隔离|同一输入重复、乱序批次、并发请求、缓存冷/热、异常后继续|

超出题面正式输入保证的条件，可用于底层函数单元测试或非法输入测试，但必须标为非正式输入域。例如容量之外的 tensor 不能不加标注地称为合法竞赛图。

**T1：小图随机/对抗测试。** 提议首轮固定种子生成 1,000 个候选；先压小图规模控制 E0 成本，逐步增加。包括有效和故意无效候选、对抗局部改动以及过去反例。每次计入测试的输入保留内容哈希。

**T2：正式数据覆盖。** 发布目标覆盖 100 个正式 case、问题 1—3、2—5 核，每组合至少一条非平凡方案。另按规模/内存压力抽取至少 24 个 case 增加不同生成器与粒度。单核基准按官方独立入口固定，并做与适当单图单核方案的对照。禁止仅测试“整图一个子图”的退化方案后宣称全场景等效。

T2 是发布覆盖目标，不要求形式化和早期探索等它全部跑完。若资源预算不足，队长预先批准覆盖子集；报告只能声明该子集通过，未覆盖能力回退 E0。

**T3：代理封存候选池。** 按原始图/图家族划分开发、校准、验收，不能把同一图的不同方案随机拆成训练/测试而声称跨图泛化。可用约 60/20/20 的图级拆分作为起点；有同族图则按族分组，未知家族要说明限制。

初次验收至少 12 个独立候选池，每池至少 64 个候选，覆盖三个问题和四种核数；这个规模只能算初步证据。发布优先扩至 24—60 个池，每池 128 个候选，并在不同生成器、局部邻域和正式图规模层分开报告。所有池成员都由 E0 建立真值；预算不够就减少池数并缩小结论，不只给入选者打标签。

### 6.3 变形测试的边界

不要默认以下性质：重编号不改变 Makespan、交换核心编号不改变结果、加核必更快、合并子图必更好、加 L2 必更快。官方启发式和事件顺序可能让它们不成立。

这些变换可生成差分样本，但各自都重新交 E0 标注。只有已由规则证明的性质才可以作为断言。请求顺序不应污染结果、同版本相同输入的确定性则需要专门测试。

### 6.4 反例包

每个失败保存：原图、方案、配置/官方代码哈希、环境、种子、E0 与 E1/E2 输出、错误/超时信息、首个不同检查点、失败规则 ID、复现命令和附件哈希。

缩减反例须保留引发差异的行为，避免为了缩图重编号、删 COPY/内存边而把问题换掉。保存未缩减原始样本和缩减结果。

E1 不一致是正确性阻断；E2 超阈值是近似失效，不同标签、不同处理。原版自身失败/不确定的行为另列，不硬当一个已定义真值。

## 7. 性能与混合流程验收

### 7.1 公平计时

同一比较记录：图、方案、problem、核数、配置、机器、进程/线程、输出模式、输入是否已解析、缓存策略、是否包含预编译/加载/特征构造、是否含设备同步。

四种口径分别报告：

1. **冷端到端**：启动到获得结果，包含所有首次开销。
2. **常驻候选评价**：同一图已载入，评价新的不同方案；仍计全部方案相关工作。
3. **批量吞吐**：固定批量 1/16/64/256，计整个 batch 的完结时间；不能预先缓存所有答案。
4. **完整 CLI**：相同结果、日志和 Trace 输出工作量；不把省略输出当作核心模拟加速。

GPU 计时必须等待实际完成。训练/离线数据构建、图预处理、JIT/编译、预热均分别报告；存在可摊销开销时同时报告冷成本与明确批次数下的摊销成本。

每个配对建议预热一次、正式至少五次；长任务可在测试清单中预先约定三次。报告中位数、P95、配对速度比几何平均、最慢/失败比例、峰值 RAM/VRAM；不要仅报告最好一次。

### 7.2 混合流程必须整体胜出

总成本不是 E2 kernel 时间：

\[
T_{\mathrm{hybrid}}=T_{E2}(\text{候选池})+T_{E1}(\text{短名单})+T_{E0}(\text{确认与审计})+T_{\mathrm{组织/传输}}.
\tag{F-06}
\]

在同一候选池上比较：全部 E0、全部 E1、E2→E1→E0。记录总时间、调用次数、短名单规模、最终由 E0 确认的最好 Makespan；E2 自己报的分数不算最终胜负。

研究搜索器时再加一组固定墙钟/同资源预算比较，检查混合方案是否真的改善最终官方结果。不要预先强求必须改善所有 case，需报告退化与适用范围。

### 7.3 门槛版本化

本文件的 3 倍、10 倍、1%/3% 等为队内初始设计值，尚无完整 profiling/误差实测保证。队长可以在看封存集之前据资源预算调整并冻结新版本。更改后旧结果保留，不能追溯性地把过去失败改写为通过。

## 8. 分工、依赖与交接

### 8.1 启动顺序

```text
SOURCE_FREEZE + CONTRACT_FREEZE
        ├─ FORM：规则、检查点、手算夹具
        ├─ TEST：E0 适配器、基线生成器、反例框架
        └─ EXACT：profiling、选择第一个热点

FORM 首批规则 + TEST 首批夹具
        ├─ EXACT：逐热点改写、逐层差分
        └─ PROXY：近似路线与批量接口实验

全套覆盖 + 性能/代理排名评测
        → MIXED_PIPELINE
        → 独立审核
        → 按能力范围发布
```

FORM 不必写完全部规范才允许 profiling；E1 也不必完工才允许 E2 原型。接口和已确认规则分批冻结，变更用版本与影响分析，不让所有人互相等待。

### 8.2 角色绑定

- 队长/Codex：来源冻结、接口/验收批准、已有协议适配、独立 TEST Agent、实验资源与发布决策。
- 成员 F：FORM 主责；给 E1/E2 解释规则和反例，不代替独立验收签字。
- 成员 E：EXACT 与 PROXY 主责，建议两个隔离实现分支；不得单方面改 comparator、金标准或放宽门槛。
- 审核者：由队长指定，可为其独立 Agent；基于可复现结果核验，不以实现者口头“过了”作为通过。

### 8.3 任务载荷，不是新的通信协议

本包 `TASKS.json` 的字段是本轮业务载荷。Codex 先读项目现有 Skill/组内通信协议，把这些任务映射到现有字段与任务图。**不猜测此前协议字段，不另建传输系统，不绕过既有权限或确认。**

一个交接至少包含：任务 ID、输入/接口版本、当前产物及哈希、验收命令、测试结论、已知限制、阻塞、下一步。消息只传摘要和可定位产物，不把整段聊天当共享状态。

阶段状态语义：待开始、可执行、工作中、阻塞、待审核、已验收；具体状态字符串沿用已有协议。产物只有通过独立审核才进入共同认可状态。

### 8.4 注意力与修改边界

FORM Agent 重点读取题面、代码、规则/差异和语义反例；EXACT Agent 读取相关规则、热点、快照、回归；PROXY Agent 读取整体语义、允许近似范围、开发集与筛选目标；TEST Agent 独立读取公共契约、E0 和冻结测试清单，不沿用优化器的私有估计标签。

实现者可提交接口变更建议，不可直接改公共 schema、金标准或官方目录。跨模块改动须列受影响规则/测试/缓存版本，队长批准后再合入。

## 10. 给 Codex 的直接执行指令

读取本文件、`TASKS.json`、`audit/READ_AUDIT.md` 和现有项目协作 Skill/通信协议。先核对附件源码哈希，绑定成员 F 与成员 E；测试与最终签收由队长独立控制。

不要执行未经用户批准的付费算力租赁或改动正式配置。按真实依赖把 FORM、profiling、Oracle 适配器和简单候选生成并行发出；不要等待完整论文或追求最优切图。

先实现共有请求/响应契约与两组已有 smoke 的复现，再按规则覆盖扩充。E1 以输入输出一致性为硬门槛；E2 以短名单质量损失和端到端速度为核心门槛。所有优化结论须有版本化证据，不把本任务书中的研发目标写成实测结果。
