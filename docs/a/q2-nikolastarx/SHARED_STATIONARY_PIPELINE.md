# Shared-input stationary pipeline (experimental P2 constructor)

`src/q2_nikolastarx/shared_stationary_pipeline.py` provides `build(graph, cores, config)` and `build_from_index(index, cores, config)`. It is an isolated static constructor. No production router selects it, and construction makes no E0, E1 or E2 call. Applicability is the strict repeated-independent-component recognizer in `shared_input_wave._recognize`; unsupported structures raise `UnsupportedStructure`. No case ID controls the plan.

The earlier `shared_stationary_wave` constructor emitted a **stage-major** priority order. The official 044/K5 pilot reduced added COPY bytes from 930,400 to 188,672 but increased Makespan from 43,795 to 72,955 cycles. This new constructor keeps full-stage ownership of each shared input but emits **job-major priority within each core**: finish one component's locally owned stages before beginning the next component. This is meant to make that component's cross-core outputs available earlier. It is a scheduling hypothesis, not an official timing claim.

The stage partition is a deterministic dynamic program minimizing the largest normalized per-pipe compute work over contiguous stage intervals. A candidate core interval is admitted only if its distinct external inputs, counted in their memory pools, plus a conservative data-derived reserve fit the configured L1 and UB capacities. The reserve is the sum of the two largest *complete produced-tensor footprints* among jobs for each pool. This accounts for possible overlapping job state without embedding a case number or fixed byte threshold. It may exclude feasible partitions; it does not establish a zero-spill result, because official lifetimes, copies and reorder are different. No feasible partition means `UnsupportedStructure`.

Each stage is a predecessor closure, so every operation belongs to one stage. Dependencies stay inside a job or advance to a later stage. The per-core order retains stage order within each job, and stages have contiguous core owners. The constructor checks coverage, calls `derive_multicore_plan`, and checks that each recognized shared external input has one core owner. Diagnostics include stage bounds, per-core external bytes, the two-job reserve, raw priority lifetime peaks, compute work and transfer estimates excluding spills. Raw peaks and transfer estimates are diagnostics, not official upper bounds or scores. Step2/Step3 may insert copies, reorder work and serialize on shared DDR.

Static validation on frozen official `case_044.json`, K5, 2026-09-26: construction took 0.0295 seconds in one local Python process, bounds `[0,17,24,28,39,51]`, external L1 bytes per active core `[77536,313344,294912,255488,11648]`, two-job produced L1 reserve 198144 bytes, with L1 capacity 524288 bytes. The no-spill transfer estimate is external input 952928, cross-core output plus input 129536, terminal output 22528, total 1104992 bytes. Raw priority L1 peaks were `[61152,314112,295296,257024,17792]` bytes. These are one static construction and estimate; **no official E0 result exists for this constructor**. The prior 72,955-cycle result belongs only to `shared_stationary_wave`.

Validation command: `python3 -m unittest tests.test_q2_shared_stationary_pipeline -v`. Three synthetic tests cover job-major order, intra-core and cross-core precedence, shared input ownership, data-derived capacity rejection, renaming invariance and unsupported template rejection. For `n` stages, `k` active cores, `P` pipe classes and `E` aggregate external-input incidences across stages, the current direct implementation takes up to `O(k n² P + n² E)` time because interval input sets are recomputed; it is intended only for recognized templates of moderate stage count. The one official 044 static construction was under five seconds, but no broad runtime guarantee or official benefit has been established.
