# P2 接收闭包交换：第一版机制验证

依据：C01 原问答与 `PRO_C01_REVIEW.md`。当前实现没有新的正式成绩，保留既有统一算法的全量基线。

## 诊断与构造

`prepared_trace_contract.capture` 在官方 `_build_scene_b_tasks` 的既有准备边界读取每核完整执行图、FIFO、内存依赖和跨核连接；`audit` 对照已有 E0 trace，逐操作核对身份、时长、覆盖及发射等式。全部一致才回溯结束于 Makespan 的紧路径，列出其跨核连接。暴露延迟只固定该次运行的其他门槛和时长解释等待，不是改动后可兑现的节省量。

`receiver_closure_exchange.construct` 从正暴露延迟的连接中最多取 8 个种子。固定唯一生产者所在核，把目标核对该 tensor 的全部计算消费者 X 一起搬回生产者核；必要时交换一个相邻计算包 Y，避免任一 Pipe 的全局最大计算工作量上升。X 与 Y 总计最多 16 个操作，每个方向最多 2 个插入位置，合计每种子最多 4 个构造。位置先满足目标核直接前后继，再检查原始依赖加完整核内顺序的全局无环性。

候选须满足受限 singleton、无 logical tensor alias、唯一原始计算生产者、完整覆盖以及受限零 spill 证书。排名依次用种子的暴露延迟、固定 FIFO 计算下界、必需 COPY 字节及稳定顺序。最后只返回一个候选；这些代理都不保证官方 Makespan 改善。没有实施窗口必要工作量检查，也没有用“覆盖所有旧紧路径”作为安全剪枝。失败或无候选只表示本次受限构造未找到方案。

构造最多检查 32 个完整候选。其耗时取决于原图/计划索引、全图无环与容量证书、下界及 COPY 计数的重复计算，不能把 8 个种子称为常数时间求解器。该版本优先验证交换机制是否有实际收益，尚未做增量优化。

## 首个试验边界

`scripts/q2_receiver_contract_probe.py` 冻结已有 069/K5 的图、配置、选中方案、E0 结果和全部相关源码哈希。该用例来自已保存的瓶颈诊断；构造模块没有 case ID 或历史成绩分支。

试验限 1 worker、30 秒活动时间、512 MiB 子进程树 RSS、1 次官方每核 Step1/2/3 prepare、1 次 RCX 构造、0 次 E0/E1/E2 最终调度评分、0 重试；异常时另有受限子进程清理。**prepare 包含官方局部模拟工作，不计成“没有运行官方程序”。** 重新申请资源窗口后才能 run，冻结文件本身不授予运行许可。先比对准备后的流量和全部 trace 门槛，任一不符就在构造前停止。

保存准备快照、诊断、候选和闭合运行回执。新候选的 Makespan 保持空值，直至另行安排官方评分。正式成绩仍须由同一冻结算法覆盖 100 题 × 1–5 核，不能从这个试验或历史候选拼成新 benchmark。
