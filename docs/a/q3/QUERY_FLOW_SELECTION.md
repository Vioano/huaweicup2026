# Query-flow 统一入口的保守选择规则

`src.q3.query_flow_solve` 是待正式冻结的独立入口。它每格先运行 fresh `forest_solve.evaluate_candidates`（至多 3 次官方 P3），再用输入结构守卫构造一次 R8 query-flow 候选；无 case 编号分支。构造不适用或计划字节相同则跳过。适用的 按官方语义推导的 compute+FIFO 下界若不低于 incumbent 的 P3 Makespan，候选不评分；下界不适用则不据此排除。其后最多 1 次 P3，严格改善才依次对旧、新**各自原计划**做至多 1 次官方 P2。相同图、核数、原配置、官方语义下，旧配对为 `(m20,m30)`，新配对为 `(m21,m31)`，同时满足 `m31<m30`、`m21<=m20`、`m21*m30>=m20*m31` 才替换。最后一项用整数交叉乘积表示 `G_new>=G_old`，无需四舍五入比值。

这是当前固定算法的**保守取舍**，比用户的全量均值目标更强：可能放弃显著的单格 M3 收益，不能声称全局 Pareto 最优或单格 G 必须严格上升。完整目标仍由同一固定算法的全部 100 图×1–5 核及逐图均值判定；已有 071/K5 R8 官方配对只是一格正例。最终五核 `mean(B/M3)>5`、`mean(G)` 改善、冷求解墙钟和成本必须由完整证据另验。

入口最多 4 次 P3 加 2 次 P2，共 6 次 E0；每次调用前把计划和 started 账落盘，失败占用槽位、不重试。P3、P2 使用原官方配置各自对应的参数，且 P2 结果仅作为配对门槛，最终 result 原件始终是入选计划的 P3。候选、配对、ledger 和 receipt 保存在新的 evidence 目录；输出计划仅含 `node_to_subgraph` 与 `core_schedules`。构造、筛选、在线评分和回退全部计入完整 solver 墙钟，内置耗时只作分项，正式报告用外层进程计时，并独立记录冷/热缓存状态。此入口本身不增添直接 Task/prepare 调用。

当前阶段只做代码集成与注入式 mock 决策测试；未运行真实 R8 构造、官方评分或全量 benchmark。正式运行前仍需固定提交 SHA、入口、参数、调用预算与独立结果目录，并核验计划合法性、证据落盘、运行异常和全量覆盖；本文不授权新批次。
