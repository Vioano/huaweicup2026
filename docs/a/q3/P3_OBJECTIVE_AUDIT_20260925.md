# 第三问题意与当前研发口径复核

2026-09-25，用户要求立即核对社区提出的“第三问加速比定义与 L2 是否被忽略”。本次直接提取原 PDF 文字并查看物理页4、5、6的完整渲染；原件 SHA-256 为 `2c0849000e137c978fb980b9c6855b2f1a23d6d4bbf46d80a6669e2249101dbe`，未修改原件。本记录优先于把成绩台辅助单核比误当第三问目标的历史口头汇报。

## 原题要求

原题第6页第三问在场景B基础上引入共享只读L2，要求“研究其容量和带宽对多核切图与调度的影响”，建立模型、设计算法。固定容量1MB（官方配置实际1048576B），带宽250B/cycle，独立于DDR的60B/cycle。

正文要求全部测试图、1–5核、无L2与只读Cache两配置对比曲线，以及同核数比值：

`CacheGain(i,k) = Makespan_noL2(i,k) / Makespan_readOnlyCache(i,k)`。

附录逐图报告两配置的Makespan、总额外搬运量和Cache字节命中率。平均值按逐用例比值取算术平均，不以总时间之比代替。第4页§1.4仍将Makespan列为最重要指标；不得通过故意做差无L2基线方案来增大比值。

题面没有把两配置“必须同plan”写成硬要求。为隔离L2硬件效果，本队做同图、同核数、同计划SHA的P2/P3配对；这是受控实验设计和成绩台Cache配对协议。可另列各自优化的P2/P3算法对比，但必须交代两端算法/预算，不能把软硬件共同差异全归于Cache。

## 官方语义与可提交自由度

- `multicore_cut_evaluate_problem_2.py` 的 `evaluate_scene_b`：无L2、共享DDR的场景B。
- `multicore_cut_evaluate_problem_3.py` 文件头明确为P2执行模型增加只读FIFO Cache；命中不会刷新FIFO顺序。`cache_eligible`只允许COPY_IN，命中走独立CACHE_READ池，未命中走DDR并在完成后装入。
- P3第323–325行的两个带宽池相互独立；第680–682行按 `hit_bytes/(hit_bytes+miss_bytes)` 计算命中率；第685–692行明确返回scene B、problem3、read_only与实际缓存参数。
- 求解器只能提交 `node_to_subgraph`、`core_schedules`，通过切图/归核/顺序改变共享访问时机、驻留和争用；不能修改官方Cache策略、容量或带宽来提高正式成绩。
- 研究容量/带宽影响需要机制模型与证据；正式成绩使用冻结配置。任何额外参数敏感性实验都须另标探索结果，不能混入正式固定配置曲线。

## 当前成果的准确状态

当前固定source `c2d628ba0fe8dce4630e5f9c0a5c8fb810fcd41a` 的100图×1–5核批次实际使用官方P3只读Cache，500 solver/915在线E0全部成功，独立只读原件/候选/账本校验500/500通过。执行场景与提交格式正确，已有M下降成果有效。

但其1–5核均值 `1.19940677/2.31031039/3.25485138/4.08274181/4.73569570` 的分母是P3 Makespan，分子是固定官方单核基线；这些是**辅助的相对单核加速比，不是第三问CacheGain**。该批500条 `cache_pair` 全为空，尚无配套完整500格无L2原件，不能据此宣称第三问实验已经完整。

当前通用计算/FIFO构造主要直接压低P3绝对M，L2语义由官方评价体现；它们可以作为共享硬件下的合法基线，但计算松弛中的局部拆分证书本身不研究1MB容量和250B/cycle带宽，也不能说明收益来自L2。本session此前汇报过度突出单核比，研发重点需要校正，不将已有通用构造或真实结果一概作废。

1. 后续P3主报告并列无L2/只读L2曲线、同核数CacheGain与绝对M，保留求解墙钟、额外搬运、spill和字节命中率。相对官方单核比继续明确标为辅助指标。

3. P3专项研究围绕共享输入的读取时机、FIFO重用距离与缓存工作集、超容量失效、DDR/Cache独立带宽竞争展开。优先与Fang现有容量/wave研究共享证据；通用关键路径改进继续以改善完整P3目标为条件，不因单核比好看自动取得优先级。
4. CacheGain不高可能因为无L2方案已很好、工作量由计算主导或缺乏可复用输入；不得通过劣化基线/挑选用例/换分母夸大收益。命中率高不自动意味着M更好。
