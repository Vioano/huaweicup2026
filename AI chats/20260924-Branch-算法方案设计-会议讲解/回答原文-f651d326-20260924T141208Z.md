可以先说：

> 以后大家需要知道自己研究的是整个系统哪一层、结果属于哪种证据、为什么这个方向值得继续。

然后明确最终目标：

- 首要还是 **Makespan**
- 其次是额外搬运
- 最终要看 **1–5 核平均加速比**
- 同时求解器自身不能走暴力指数搜索路线，题面建议单例约 5–10 分钟内完成。:chatgpt-content-reference{index="0"}

# 第 1 页之后：目前进度
## 2–6 分钟｜我们已经做到哪里

### 先讲“官方语义”
重点只讲一句链：

> 我们提交的不是最终执行时间表，只提交切图和 core schedule。真正的完整执行，是官方根据我们的 plan 自动编译出来的。

然后口头跑一遍：

> plan  
> → Task/COPY 构造  
> → Step1 定序  
> → Step2 spill  
> → Step3 Pipe/FIFO  
> → 全局共享 DDR/Cache 事件模拟  
> → Makespan。

官方题面也是把评估分成“构造 Task/边界搬运 → 核内调度 → 多核全局模拟”三大阶段。:chatgpt-content-reference{index="1"}

### 再讲当前算法进度
不要报太多数字，只讲几个性质：

- Q1 已经有 bounded search、Task profile、release-aware split/merge 等；
- Q2/Q3 已经看到**非常强的结构化收益**；
- 比如 Q2 case008，结构化资源词从 123060 降到 63768，而且核心归属、搬运量、spill 都没变，收益主要来自流水顺序。:chatgpt-content-reference{index="2"}
- 但不是所有 case 都稳定，当前仍存在明显退化。

### 最后讲 evaluator
一句话：

> 我们现在已经不再把官方 Python 当成只能慢慢跑的黑箱，exact batch、native replay、缓存化、并发这些基础设施正在成熟。

所以当前状态可以总结成：

> **“局部强机制已经出现，但全局稳定性和统一算法还没闭合。”**

# 第 2 页：官方评估数据流
## 6–9 分钟｜统一所有人的数据流心智模型

你可以指着图说：

> 一张 case JSON 进来，我们的算法针对 q 和 k 输出一个 plan。  
> plan 送入对应的 Q1/Q2/Q3 evaluator。  
> evaluator 再把它变成真正执行程序。

特别提醒：

> 我们优化的直接对象是 plan，但我们真正关心的是 plan 经过官方映射后产生的行为。

然后解释三个指标：

- Makespan：最重要；
- 额外搬运：次要；
- 多核 speedup：由固定单核 baseline 除以多核 Makespan 得到。:chatgpt-content-reference{index="3"}

补一句重要的：

> 官方单核 baseline 不是我们的单核最优算法，而是官方把整图作为一个 Task 做核内调度的固定基准，所以出现 speedup 大于核数是允许的。:chatgpt-content-reference{index="4"}

# 第 3 页：Coherent 框架
## 9–15 分钟｜讲核心链条

这一页是会议重点。

不要逐词解释得太深，先讲逻辑。

### 第一步：官方映射
> 我们先不急着求最优解，而是把“plan 到 result”整个官方过程当成研究对象。

### 第二步：primitive 编辑
> 我们对方案做最小可解释改动，比如 split、merge、move、reorder。

### 第三步：局部响应 / 离散雅可比
> 看一个小改动之后，官方映射的哪些层发生了变化。

不是只看 Makespan，还看：

- COPY
- Step1
- spill
- FIFO
- release
- DDR
- Cache

### 第四步：耦合度 / guard
> 我们想测一次小改动会传播多远，以及什么时候会跨过某个离散切换边界。

比如：

- 从不 spill → spill；
- Cache hit → miss；
- 一个关键 output release 被推迟。

### 第五步：敏感方向
> 如果小编辑经常引起很大收益，这就是高杠杆方向。

然后进入第二排：

### 行为等价商 / 最小充分状态
> 很多不同 JSON 可能最后编译成同一种行为。  
> 如果能把它们归成同一类，我们搜索的是“真正不同的行为”，而不是不同 JSON。

### 映射族 / 多核尺度轴
> Q1/Q2/Q3、1–5 核、容量、带宽，其实都可以看成一族相关映射。

### 峰值机制
> 极端好的方案不是终点，它是研究入口。

### 局部评估器集
> 如果官方映射在某些 regime 内比较稳定，可以用局部 evaluator 快速估计；不确定就拒答，回到 E1/E0。

### primitive + macro
> 最后把研究出来的高价值机制变成宏操作。

### 算法蒸馏
> 研究阶段允许复杂透明，最后压成比赛能跑得快的 solver。

收尾一句：

> **整个框架的核心不是“找更复杂的算法”，而是先搞清楚这个搜索空间真正的结构。**

# 第 5 页：多核与峰值机制
## 18–22 分钟｜讲今天最重要的新观察

先讲多核轴：

> 我们之前容易把 2 核、3 核、4 核、5 核当成四个 benchmark。  
> 现在更希望把它们看成同一问题沿 k 变化。

所以可以研究：

- 3 核好方案怎么转成 4 核；
- 哪个 guard 在 4→5 核时翻转；
- 哪类机制跨核数稳定。

然后讲峰值。

这里一定强调：

> **峰值不等于好参数。**

峰值更像：

> 图结构 × 算法操作 × q × k × 当前 regime

共同形成。

可以直接讲 case008：

> 现在已经存在 4 核 7× 以上的 peak witness。  
> 但我们不是要收藏这个数字，而是研究为什么偏偏这张图能激活这个机制。

然后讲峰值研究路线：

> Winner  
> → 找邻近劣解  
> → 比较完整官方映射行为  
> → 找关键变化  
> → 找图结构条件  
> → 提炼 macro  
> → 去别的图验证。

一句话总结：

> **我们不是研究“哪个参数最好”，而是研究“什么结构条件下，什么策略为什么会突然特别好”。**

# 第 6 页：三层研发组织
## 22–26 分钟｜告诉大家后续怎么配合

### 左边：离线结构研究
负责：

- guard
- quotient
- graph features
- peak-to-mechanism
- sufficient state

这层主要产出**知识**。

### 中间：在线求解器
负责：

- primitive
- macro
- search
- continuation

这层主要产出**方案**。

### 右边：Evaluator
负责：

- E0/E1
- native replay
- cache
- parallel evaluation

这层主要产出**真值和搜索吞吐**。

重点讲：

> 这三层不是三支独立队伍，而是一个闭环。

闭环是：

> 结构研究发现机制  
> → solver 实现机制  
> → evaluator 验证  
> → 失败案例再反馈给结构研究。

现有三路研究其实已经开始出现这种趋势：目前最有效的路线都在区分“核心归属、子图粒度、官方展开顺序”，并用 E0 去验证少量真正有结构意义的候选。:chatgpt-content-reference{index="5"}

# 第 7 页：统一汇报颗粒度
## 26–29 分钟｜定团队规范

这里你最好讲得强一点。

### 第一条
以后报结果必须说：

> case / q / k / baseline / plan identity / evaluator

不能只说：

> “我这个算法快了 30%。”

### 第二条
证据等级要区分：

- E0
- E1
- EMP
- HYP

尤其不能把有限样本观察写成普遍规律。

### 第三条
任何 peak 都要带邻近反例。

因为：

> 单独看 winner 很容易产生事后解释。

### 第四条
任何新想法尽量问自己：

> 这是 primitive？  
> guard？  
> macro？  
> evaluator？  
> 还是 graph feature？

这样所有人的成果才能进入同一个框架。

# 最后 1 分钟｜收尾

你可以用这段话：

> 我们今天最大的变化，不是得到了一套最终算法，而是开始有一套统一的研究语言。  
> 接下来我们不会只问“这个参数能不能让某个 case 更快”，而会问：
>
> **它改变了官方映射的什么？  
> 为什么在这张图上有效？  
> 这个机制能不能跨图、跨核数、跨问题复用？  
> 最后能不能蒸馏成 solver 的 macro？**
>
> 如果这些问题能回答清楚，我们现在看到的那些局部高峰值，就有机会变成稳定的整体算法。
