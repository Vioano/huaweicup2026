**A：**

可以。先把芯片名、NPU、Cache、Pipe 这些术语暂时拿掉，这道 A 题最核心的问题其实非常清楚：

> **给你一张很大的计算任务依赖图和 2～5 个相同的处理核心，你要决定“哪些计算放在一起、每一组放哪个核、各核按什么顺序执行”，使整张图尽可能早地算完。**

但是这里有一个关键麻烦：**为了并行而把图切开，本身会产生通信；为了减少通信把图粘在一起，又可能损失并行度、撑爆缓存。** 所以这不是普通的“平均分任务”，而是一个**计算、通信、缓存和流水线高度耦合的图调度问题**。题面自己也明确说，三个核心决策是“切图、核心分配、同核执行顺序”，三者不能孤立优化。

我建议把它理解成下面这幅心智模型。

## 一、题目到底给了你什么？

它给你的本质上是一张 DAG——有向无环图。

但它不是普通的“任务节点图”，而是一个 **Tensor–Op 二部图**：

- Tensor 节点：数据；
- Op 节点：对数据进行的操作；
- 箭头：数据依赖。

比如最简单的一条链：

```
DDR 中的 A
   ↓
COPY_IN
   ↓
L1 中的 A
   ↓
MATMUL
   ↓
L1 中的 C
   ↓
COPY_OUT
   ↓
DDR 中的 C
```

题面第 1 页的矩阵乘例子正是在表达这个过程：一块矩阵数据先从 DDR 搬进核内，再由 Cube 计算，最后写回 DDR。

形式上计算图写成

$$
G=(V,E),\qquad V=T\cup O,\qquad T\cap O=\varnothing .
\tag{1}
$$

其中 $T$ 是 Tensor，$O$ 是操作。

所以你拿到 JSON 后，其实是在看：

```
tensors = 数据块
ops     = 算子
edges   = 谁依赖谁
```

而不是在看一个完整神经网络模型。

---

# 二、你真正能控制的东西，其实只有两个

这是理解本题最重要的一点。

比赛已经把很多底层工作替你固定好了。

你最后只需要输出：

```
{
  "node_to_subgraph": {...},
  "core_schedules": [...]
}
```

也就是说，你只需要做两个决策。

### 决策 1：切图

给每个计算 Op 一个 `sgid`：

```
Op 101 → 子图 0
Op 102 → 子图 0
Op 103 → 子图 1
Op 104 → 子图 2
...
```

也就是定义一个映射：

$$
p:O_{\mathrm{compute}}\rightarrow
\{0,1,\ldots ,K-1\}.
\tag{2}
$$

这里 $K$ 甚至都不是题目固定的。

**你自己决定切多少块。**

题目明确说子图数量“不作限制”。

---

### 决策 2：把子图排到核心上

比如四核：

```
Core 0: [0, 7, 10]
Core 1: [1, 4]
Core 2: [2, 5, 8]
Core 3: [3, 6, 9]
```

也就是说，你同时决定：

1. 子图在哪个 core；
2. 同一个 core 上谁先谁后。

所以完整方案其实就是：

$$
\text{原 DAG}
\longrightarrow
\text{Partition}
\longrightarrow
\text{Placement}
\longrightarrow
\text{Ordering}.
\tag{3}
$$

而评估器拿到这两个输出以后，会替你完成剩下的一切：插 COPY、核内排序、cache 换入换出、多核离散事件模拟。

这使得这道题和传统“自己写完整调度 simulator”很不一样。

# 三、你优化的到底是什么？

最重要的是 **Makespan**。

也就是：

> 从所有核开始执行，到最后一个操作完成，总共用了多少 cycle。

可以抽象写成

$$
M=\max_{o\in O} C_o ,
\tag{4}
$$

其中 $C_o$ 是操作 $o$ 的完成时间。

你的主要目标就是：

$$
\min M.
\tag{5}
$$

此外还有一个次要指标：

$$
D_{\mathrm{extra}}
=
D_{\mathrm{scheduled}}
-
D_{\mathrm{original}},
\tag{6}
$$

即因为你的切图和调度**额外制造出来多少 DDR 搬运**。

所以如果极端一点：

```
所有 Op 都塞进一个子图
```

通信可能很少。

但是：

```
Core 0: 干活
Core 1: 摸鱼
Core 2: 摸鱼
Core 3: 摸鱼
```

多核完全没利用起来。

另一极端：

```
每个 Op 都切成一个子图
```

并行度可能非常高，但会变成：

```
算一点
↓
写 DDR
↓
另一个核读 DDR
↓
算一点
↓
再写 DDR
...
```

结果 DDR 被打爆。

所以核心矛盾就是：

$$
\boxed{
\text{parallelism}
\quad\leftrightarrow\quad
\text{communication + memory pressure}
}
\tag{7}
$$

这就是整题最本质的一条式子。

# 四、为什么它不是简单的“图均分成四份”？

因为每个 core 不是一个普通 CPU。

一个 core 里面其实有四条主要 Pipe：

```
PIPE_M       Cube / 矩阵计算
PIPE_V       Vector / 向量计算
PIPE_MTE2    搬入
PIPE_MTE3    搬出
```

Cube 和 Vector 可以同时工作，多个 Pipe 也可能并行。

于是可能发生：

```
时间 →
Cube:    ██████████████
Vector:      ██    ██
MTE2:   █  █    █
MTE3:          █   █
```

也可能是：

```
Cube:    ██████████████
Vector:
MTE2:
MTE3:
```

第二种情况下，即使这个核“总工作量看起来不少”，硬件利用率实际上很差。

所以你不能只看：

> Core 0 10000 cycle，Core 1 10000 cycle。

还得看任务里面的 Pipe composition。

这实际上已经带一点 **heterogeneous-resource scheduling inside a homogeneous multicore architecture** 的味道：

核是同构的，

但核内部资源不是同构的。

---

# 五、最大的坑：所有核共享同一个 DDR

四个核心并不是各有一条 60 bytes/cycle 的 DDR。

而是**所有核心加起来只有 60 bytes/cycle**。

例如：

```
Core 0 COPY_IN
Core 1 COPY_IN
Core 2 COPY_IN
Core 3 COPY_IN
```

它们同时读 DDR 时不是

```
4 × 60 = 240 bytes/cycle
```

而是大约一起瓜分：

$$
B_i\simeq\frac{60}{n_{\mathrm{active}}}.
\tag{8}
$$

所以你甚至会遇到一种很反直觉的现象：

> **多开一个核，反而让所有核都变慢。**

这也是为什么“负载均衡”远远不够。

你还必须关注**通信在时间轴上的重叠**。

例如两个方案搬运总字节数完全相同：

### 方案 A

```
t = 0:
Core0 COPY
Core1 COPY
Core2 COPY
Core3 COPY
```

DDR 瞬间拥塞。

### 方案 B

```
t = 0    Core0 COPY
t = 500  Core1 COPY
t = 900  Core2 COPY
...
```

DDR 峰值竞争可能小很多。

因此这是个**动态 bandwidth contention scheduling problem**，而不仅仅是 graph partition。

# 六、为什么切图会制造通信？

假设原来：

```
A
↓
Op1
↓
tensor X
↓
Op2
```

如果 Op1 和 Op2 在同一个子图里：

```
Subgraph 0
┌────────────┐
│ Op1 → X → Op2 │
└────────────┘
```

X 可以直接在核内流动。

但如果切成：

```
Subgraph 0           Subgraph 1
   Op1                   Op2
    ↓                     ↑
    X ────────────────────┘
```

那么 evaluator 可能需要自动插入：

```
Op1
↓
X
↓
COPY_OUT
↓
DDR
↓
COPY_IN
↓
Op2
```

题目第 3 页图 2 专门画的就是这个机制。

所以从纯图论角度来看：

> **cut edge 不是免费的。**

而且 edge 的代价不是“1”。

它取决于 Tensor size。

因此很自然可以把某些依赖看作加权边：

$$
w_{ij}\sim s_{ij},
\tag{9}
$$

其中 $s_{ij}$ 是跨边 Tensor 的 byte 数。

这就是我们前一个 chat 里讨论“不要一上来就套算法”的原因之一：

普通 balanced graph partitioning 的目标通常是：

```
负载均衡 + cut weight 最小
```

但这里只描述了问题的一部分。

---

# 七、还有一个特别重要的结构：数据复用

假设一个大输入 $X$ 被很多计算使用：

```
           → A
         /
X ─────→ B
         \
           → C
```

如果 A、B、C 被切到三个 task：

```
X → Core 0
X → Core 1
X → Core 2
```

同一份 X 可能被反复搬三次。

题面也特别把“共享输入被多个子图重复读取”列为重要优化方向。

所以这道题实际上不仅有 producer-consumer locality，还有：

> **consumer-consumer locality。**

这一点如果以后做数学抽象，我甚至认为 **hypergraph** 可能比普通 graph 更自然：

```
一个 Tensor
连接
一群 consumer
```

因为共享一个输入的数据复用关系，本质上不像普通 pairwise edge。

这正是前一个 chat 里那种“先寻找数学结构，再决定算法”的思路非常适合发挥作用的地方。

# 八、场景 A 和场景 B，到底差在哪里？

这是三问里面最关键的变化。

---

## 问题 1：Scene A

一句话：

> **子图就是 Task；Task 与 Task 之间的数据一定经过 DDR。**

哪怕：

```
Subgraph 1 → Subgraph 2
```

两个都放在 Core 0：

```
Core 0:
SG1 → SG2
```

中间的数据依然不能直接留在 L1。

必须：

```
SG1
↓
COPY_OUT
↓
DDR
↓
COPY_IN
↓
SG2
```

而且 Task 之间还有额外等待：

- 同核 Task 切换：100 cycles；
- 跨核前驱：1000 cycles。

所以 Scene A 中：

> **切图本身就是昂贵操作。**

因此问题 1 最直观的冲突是：

```
大子图
  ↓
通信少
  ↓
并行度差 / cache 压力大

小子图
  ↓
并行度高
  ↓
DDR 通信巨大
```

---

# 九、问题 2：Scene B

Scene B 的规则发生了非常大的变化。

> **同一个 core 上的所有子图被合成一个 Task。**

于是：

```
Core 0:
SG1 → SG2 → SG5
```

SG1 的结果可以一直留在 L1/UB 里，被 SG2 使用。

不用再：

```
L1 → DDR → L1
```

只有真正跨 Core：

```
Core 0: SG1
          ↓
        DDR
          ↓
Core 1: SG4
```

才需要 COPY_OUT / COPY_IN。

因此 Scene B 的优化问题已经明显不同于 Scene A。

Scene A 更像：

> **subgraph partition + task scheduling**

Scene B 更像：

> **graph partition / core placement + persistent local-memory scheduling**

这也是一个很值得写进论文的方法论点：

**不能简单拿 Problem 1 的最优算法原封不动套 Problem 2。**

---

# 十、但 Scene B 也不是“同核越多越好”

因为如果你希望：

```
SG1 的 Tensor X
```

一直活到：

```
SG7
```

那么中间执行 SG2～SG6 的时候：

```
X 不能释放
```

于是它一直占着 L1 / UB。

所以可能出现：

```
理论上复用了 X，省掉一次 DDR
```

但同时：

```
X 长时间占 300 KB L1
↓
其他 tensor 放不下
↓
开始 spill
↓
COPY_OUT
↓
COPY_IN
↓
DDR 流量反而更多
```

题面明确指出了这个反效果。

所以 Scene B 中又多了一层经典 trade-off：

$$
\text{reuse benefit}
\quad\leftrightarrow\quad
\text{live-range memory pressure}.
\tag{10}
$$

如果你熟悉编译器，这其实已经非常像：

> register allocation / live range / spilling

只不过这里的“寄存器”变成了几百 KB 的 L1/UB tensor storage。

# 十一、问题 3 又加了一个全局 L2

Problem 3 = Problem 2 + 一个所有核共享的只读 Cache：

```
        L2 Cache
       /   |   \
Core0     Core1    Core2
```

容量：

```
1 MB
```

带宽：

```
250 bytes/cycle
```

并且它的带宽**不占 DDR 的 60 bytes/cycle**。

所以如果多个核反复读取同一个输入：

没有 L2：

```
Core 0 ← DDR X
Core 1 ← DDR X
Core 2 ← DDR X
Core 3 ← DDR X
```

有 L2 后可能变成：

```
DDR → X → L2
             ├→ Core0
             ├→ Core1
             ├→ Core2
             └→ Core3
```

于是 Problem 3 要研究的是：

> **调度如何主动创造 Cache reuse？**

而且 L2 还是 FIFO，不是理想 cache。

因此执行顺序也会改变命中率：

```
X X X X Y Y Y
```

和

```
X Y Z A ... X
```

很可能表现不同。

这已经变成一个：

> **spatial locality + temporal locality + multicore scheduling**

联合问题。

# 十二、现在把整道 A 题压缩成一个抽象模型

给定一个计算 DAG：

$$
G=(V,E),
\tag{11}
$$

你决定：

### 第一层：聚类

$$
V\longrightarrow\{S_1,S_2,\ldots,S_K\}.
\tag{12}
$$

### 第二层：Placement

$$
S_k\longrightarrow \mathrm{Core}(S_k).
\tag{13}
$$

### 第三层：Ordering

$$
S_{k_1}\prec S_{k_2}\prec\cdots
\tag{14}
$$

然后官方 evaluator 定义了一个很复杂的函数：

$$
M
=
F(G,P,A,\Sigma;\text{hardware config}),
\tag{15}
$$

其中：

- $P$：partition；
- $A$：core assignment；
- $\Sigma$：core schedule。

你最终实际上是在解：

$$
\boxed{
\min_{P,A,\Sigma}
F(G,P,A,\Sigma)
}
\tag{16}
$$

并兼顾：

$$
D_{\mathrm{extra}}.
\tag{17}
$$

非常重要的一点是：

**你不需要自己准确构造一个解析的 $F$。**

官方已经直接把 $F$ 写成 Python evaluator 给你了。

# 十五、一个具体例子，你马上就能感受到它为什么难

假设有：

```
           B ─────────┐
          ↗            ↓
A → Op1 → X → Op2 → Y → Op4
          ↘
           Op3 → Z ────┘
```

Op2 和 Op3 可以并行。

最简单的方案：

```
Core 0: Op1
Core 1: Op2
Core 2: Op3
Core 3: Op4
```

看起来并行度最大。

但 X 必须同时：

```
Core0 → DDR → Core1
              ↓
             Core2
```

可能大量复制。

另一方案：

```
Core0: Op1 → Op2
Core1: Op3
Core2: Op4
```

少了一部分通信。

再一种：

```
Core0: Op1 → Op2 → Op4
Core1: Op3
```

通信又变少。

但现在 Op4 可能得等 Op3：

```
Core0:
█████████.............██████

Core1:
       ███████████████
```

于是 Core0 中间产生 idle。

所以每个决策都在改变：

```
并行
通信
关键路径
缓存生命周期
Pipe 利用率
DDR 峰值
```

而且这些不是可加的独立项。

# 十六、题面甚至埋了一个很有意思的“非单调性”

直觉会认为：

> 两个子图合并总应该更快，因为减少了通信。

但题目明确警告：

> 当子图规模过大时，核内调度启发式可能产生大量 cache spill；因此合并超过一定程度后，甚至会出现**负收益**。

也就是说：

$$
T(A\cup B)
<
T(A)+T(B)
\tag{18}
$$

经常成立，

但**不保证成立**。

甚至可能：

$$
T(A\cup B)
>
T(A)+T(B).
\tag{19}
$$

这件事非常重要。

因为它意味着不能简单地：

```
不断 merge 最大通信边
```

直到剩 N 个分区。

真正的 objective landscape 里面会有很多局部结构。

# 十七、所以我现在会把 A 题定义成什么？

如果要用一句相对专业但准确的话，我会称它：

> **带共享内存带宽竞争、异构核内流水线、有限私有缓存和数据局部性的 DAG 多核联合分区与调度优化。**

再翻译成人话：

> **怎么把一张 AI 计算图聪明地撕成几块，再把这些块聪明地扔给几个 NPU core，使它们尽可能一起忙、尽可能少互相传数据、尽可能不把 cache 撑爆，而且不要一起抢 DDR。**

# 十八、从“比赛到底让我们交什么”来看，就更加简单

### Problem 1

做 Scene A scheduler。

输出：

- 1～5 核平均加速比曲线；
- 每个 case Makespan；
- extra data movement；
- Python 程序。

### Problem 2

把算法升级到 Scene B：

```
同核跨子图数据可以驻留
```

重新做一遍。

### Problem 3

Scene B 再加共享只读 L2：

比较：

```
No L2
vs
L2 Cache
```

再研究为什么、什么时候 L2 有效果。

这道题有四层：

```
第一层：图
        谁依赖谁？

第二层：局部性
        哪些东西应该放在一起？

第三层：并行调度
        哪些东西应该分开同时算？

第四层：硬件动态

        会怎样改变前面两个判断？
```

**真正的难点恰好是第二层和第三层互相矛盾，而第四层又让这个矛盾变成非线性的。**

> Asked at: 2026-09-23 05:10

你一下讲太快了，我们一点一点讲。首先看题目，第一页PDF。它的背景是不是就让我们知道有“调度多核NPU平台”这回事？题目中把NPU简化为n个同构的核心。从这里开始讲解多核调度算法，需要将该计算图划分为若干子图。什么意思？调度对象为什么是一张计算图？为什么调度算法是将计算图划成子图？

**A：**

对，你现在的理解是对的。我们先只停留在第一页，不往后跑。

第一页前半段的背景作用，基本就是让你建立这么一个场景：

> 现在一个 AI 计算任务太大，单个 NPU 核心扛不住，所以硬件上做成了多个 NPU 核心。既然有多个核心，就产生了一个新问题：**这一大堆计算到底怎么分给这些核心去做？**

题目于是把真实复杂硬件抽象成了：**有 N 个同构的 NPU 核心，外加大家共享的 DDR 主存。** 每个核心内部还有自己的计算单元和私有缓存。

你现在真正卡住的是后面这句话：

> “待调度对象是一张有向无环计算图。多核调度算法需要将该计算图划分为若干子图……”

我们就拆这句话。

---

## 1. 为什么“调度对象”是一张计算图？

因为一个神经网络的计算，本来就天然可以表示成“很多计算步骤 + 它们之间的数据依赖”。

比如先别想神经网络，我们想一个很简单的表达式：

```
y = (a + b) × c
```

这个计算不能乱做。

你必须先算：

```
a + b
```

得到一个中间结果，然后才能乘 c。

所以它可以画成：

```
a ─┐
   ├→ 加法 → 中间结果 ─┐
b ─┘                   ├→ 乘法 → y
c ─────────────────────┘
```

这里已经有一个“图”了。

节点表示：

- 数据；
- 或计算操作。

箭头表示：

> **后面的计算依赖前面的结果。**

所以图里的箭头不是随便连的，而是在说：

> “这个东西不算完，后面那个东西不能开始。”

这就是为什么“调度”首先要看计算图。

因为调度不能只看“有哪些任务”，还必须知道：

> **哪些任务可以同时做，哪些任务必须等别人做完。**

题目第一页也是这么定义的：操作节点表示计算或搬运，张量节点表示输入、中间结果和输出；箭头表示节点之间的数据依赖。

---

## 2. 为什么是“有向无环图”？

“有向”很好理解，因为依赖有方向。

例如：

```
A → B
```

表示 B 依赖 A。

不能反过来说 A 依赖 B。

“无环”也很重要。

如果出现：

```
A → B → C → A
```

那就麻烦了。

因为：

- A 要等 C；
- C 要等 B；
- B 又要等 A。

所有人都在等别人，谁都不能先开始。

所以这种依赖关系不能有环。

因此，计算任务很自然地表示成 DAG，也就是“有向无环图”。

---

## 3. 那为什么“多核调度”要先把计算图划分成子图？

现在才进入真正关键的一步。

假设你的完整计算图是：

```
A → B → D
 \       ↑
  → C ───┘
```

你现在有两个核心：

```
Core 0
Core 1
```

你必须回答：

> A、B、C、D 分别让哪个核心来算？

一种方法是：

```
Core 0: A, B
Core 1: C, D
```

实际上，这就相当于你把原图切成了两块：

```
子图 1:
A → B

子图 2:
C → D
```

然后：

```
子图 1 → Core 0
子图 2 → Core 1
```

所以“划分子图”本质上是在做：

> **把一整张大计算任务，打包成若干个比较大的工作块。**

然后再把这些工作块分配给不同核心。

---

## 4. 为什么不直接“一个操作分给一个核心”？

这是一个很关键的问题。

理论上你当然可以直接说：

```
Op1 → Core0
Op2 → Core1
Op3 → Core0
...
```

但题目没有选择这么建模，而是增加了“子图”这一层。

因为现实中，**一串彼此紧密相关的操作往往应该一起执行。**

例如：

```
Op1 → Tensor X → Op2
```

如果 Op1 和 Op2 放在一起，那么 Op1 算出来的 X，可以直接留在这个核心自己的缓存里，然后马上给 Op2 使用。

但如果把它们拆开：

```
Core0: Op1
Core1: Op2
```

那 X 就得从 Core0 那边传到 Core1。

而 NPU 核心之间并不是可以免费瞬移数据。

很可能要：

```
Core0 缓存
   ↓
DDR
   ↓
Core1 缓存
```

这就产生了额外数据搬运。

所以你可以先形成一个非常简单的直觉：

> **子图就是一组希望“绑在一起执行”的计算。**

为什么绑一起？

因为这样可能：

- 少搬数据；
- 多复用缓存；
- 减少通信。

---

## 5. 但为什么又不能把整个图都当成一个子图？

因为那样就失去多核的意义了。

假如整张图全部打包成：

```
Subgraph 0
```

然后交给：

```
Core 0
```

那 Core 1、Core 2、Core 3 都没事干。

所以你想切开一些，让不同核心并行。

例如原来：

```
        → B →
A →
        → C →
```

如果 B 和 C 互不依赖，就可以：

```
Core0: B
Core1: C
```

同时执行。

因此这里马上出现了这道题最基础的矛盾：

> **切得少：数据更容易留在一起，通信少，但并行度低。**

> **切得多：可以让更多核心同时干活，但子图之间的数据通信变多。**

第一页最后那句话其实已经在暗示这个核心矛盾：

> 要在多核并行度、核内缓存容量以及共享主存的数据搬运带宽之间权衡。

---

## 6. 所以“切图”不是为了数学上好看，而是在决定任务粒度

你可以先把“子图”这个词完全换成：

> **任务包**

于是整句话就好懂了：

> 给你一个大型 AI 计算任务，它内部有很多有依赖关系的小计算。你需要把这些小计算打包成若干任务包，然后把这些任务包分给多个 NPU 核心执行。

题目原文说的：

> “将计算图划分为若干子图，将子图分配到各核心，并确定每个核心上的子图执行顺序”

其实就是三步：

```
完整计算任务

↓ 第一步：怎么打包？

子图1  子图2  子图3  子图4

↓ 第二步：哪个核负责哪个包？

Core0: 子图1, 子图4
Core1: 子图2
Core2: 子图3

↓ 第三步：每个核先做谁？

Core0: 子图1 → 子图4
```

题面第一页确实就是在定义这个问题。

所以到这里，你暂时只需要抓住一句话：

> **计算图描述“整个任务内部谁依赖谁”；切成子图，就是决定哪些计算绑成一个任务包；多核调度，就是再决定这些任务包交给哪个核心、按什么顺序做。**

下一步最自然的问题其实就是：**“一个子图内部到底是什么？为什么子图内部的数据可以更方便复用，而跨子图就会有代价？”**
 这个正好对应第一页下面那个矩阵乘法示意图，我们可以接着只讲那张图。

可以继续拆这两个基础点

**Q：**

> Asked at: 2026-09-23 05:22

我继续问一个拆分子图和核心的问题，子图有没有可能算到一半？比如说，按照你这个方法，Core零算子图一算到一半的时候，需要Core一的子图二给一个中间数据给他，他才能继续算完子图一。会不会出现这种情况？

**A：**

会出现你说的这种“局部算到一半，后面等别的核的数据”的结构，但**要区分“计算图上允许这种依赖”与“这道题的具体执行规则允许不允许这样跑”**。这里正好是场景 A、B 的一个重要区别。

先从纯计算图角度看。完全可能有这样的划分：

```
子图 1（Core 0）：

A → B → C
    ↑
    │
    X

子图 2（Core 1）：
D → X
```

这里子图 1 中的 `A` 不需要 Core 1 的数据，所以直觉上你会想：

```
Core 0: 先算 A
Core 1: 同时算 D → X

然后 Core 0：
拿到 X
↓
继续算 B → C
```

从一般的 DAG 并行计算角度，这当然是很自然的。也就是说，**一个子图内部可以有某个操作依赖另一个子图产生的数据**；跨子图依赖本身就是允许的，题目还要求这些依赖形成的“子图依赖图”必须仍然是 DAG。

但是——这道题专门规定了运行时怎么处理它。

### 在场景 A：不会这样“算一半再等”

场景 A 里有一个很强的规则：

> **一个子图就是一个 Task。**

而 Task 是 CPU 一次下发给某个 NPU 核心统一调度的最小执行单元。

更关键的是，场景 A 规定：一个 Task 的激活要等待它的前驱 Task。跨核前驱完成后还要再等固定延迟。

所以刚才这个例子如果属于场景 A：

```
SG2 → SG1
```

哪怕 SG1 里面的 `A` 本身完全不依赖 SG2，评估器也不会让 SG1 先跑 `A`。

它更像：

```
Core 1:
SG2 全部完成
    ↓

Core 0:
SG1 才整体被激活
A → B → C
```

所以在场景 A 中，你可以暂时把子图理解得比较“原子化”：

> **有跨子图前驱没结束，这个子图就先别启动。**

因此你说的这种

> “SG1 先算一半 → 等 SG2 → 再继续 SG1”

**在场景 A 的跨子图层面基本不会发生。**

---

### 但场景 B 就不一样了

场景 B 有一个很大的改变：

> 同一个 Core 上的所有子图会合并成一个大的 Task。

只有**跨 Core**的数据才需要 COPY_OUT / COPY_IN 和同步信号。

而这时评估器是在更细的 **Op 层面**判断是否 ready：

一个操作只有在：

- 所属 Task 已经激活；
- 自己的前驱完成；
- 如果有跨核输入，对方的数据已经传过来；

之后才可以执行。

所以场景 B 下真的可能出现：

```
Core 0:
A █████
       等 X ......
                  B █████
                         C ███

Core 1:
D █████ → COPY_OUT X
```

也就是说 Core 0 可以先执行一些不依赖 X 的工作，然后到了需要 X 的操作那里才卡住。

不过这里最好不要说：

> “子图 1 算到一半停了。”

更准确的说法是：

> **Core 0 上那个合并后的 Task 已经执行了一部分操作；其中某些后续操作由于跨核数据依赖暂时还不能 ready。**

因为到了场景 B，真正的运行单位已经不再是单个子图了，而是“这个 Core 上所有子图合成的 Task”。

---

所以你现在可以记一个非常重要的区别：

```
场景 A：

子图 ≈ Task ≈ 一个比较整体的调度块
有前驱子图没完成 → 整个子图先不启动

场景 B：

一个 Core 上多个子图 → 合并成一个 Task
Task 内部可以执行已经 ready 的操作
某个操作缺跨核数据 → 那个操作等，但别的独立操作仍可能继续
```

这其实也回答了一个更深的问题：**“子图”并不天然等于“不可中断的程序函数”。** 它首先只是你对计算图做出的一个分组；究竟这个分组在硬件上多“原子”，是由题目给定的 Task 和同步机制决定的。

你接下来很可能会自然问到一个关键问题：**那我们切子图时，是否允许一个子图内部有多个“入口”，分别依赖不同的外部子图？**——答案是允许的，而且这会直接影响切图策略。

**Q：**

> Asked at: 2026-09-23 05:40

切图方案和子图调度方案分别是什么意思？我看这个切图方案还有规范，比如说子图间插入数据搬运节点和子图重复读取同一数据。子图调度方案又是什么意思？

**A：**

对，这里最好把题目里的两个输出彻底分开。你可以先把它们理解成两层决策：

> **切图方案回答：“哪些计算算作同一个任务块？”**
>  **子图调度方案回答：“这些任务块分别给哪个核心，按什么顺序执行？”**

题面实际上就是这么规定的：第一步切图，第二步再把子图分配到核心并确定各核执行顺序。

我们一点点来。

---

## 1. 什么叫“切图方案”？

假设原始计算图里有 6 个计算操作：

```
Op1 → Op2 → Op4
  \         ↑
   → Op3 ───┘

Op5 → Op6
```

先不管具体数据节点。

所谓**切图方案**，就是给每个计算操作贴一个“子图编号”。

例如：

```
Op1 → 子图 0
Op2 → 子图 0

Op3 → 子图 1

Op4 → 子图 2

Op5 → 子图 3
Op6 → 子图 3
```

于是你就相当于说：

```
子图 0 = {Op1, Op2}
子图 1 = {Op3}
子图 2 = {Op4}
子图 3 = {Op5, Op6}
```

这就是“切图”。

在最终输出文件里，对应的就是：

```
"node_to_subgraph": {
    "Op1": 0,
    "Op2": 0,
    "Op3": 1,
    "Op4": 2,
    "Op5": 3,
    "Op6": 3
}
```

当然实际 JSON 用的是操作节点的整数 id。题目规定 `node_to_subgraph` 必须恰好覆盖所有非 COPY_IN/COPY_OUT 的计算操作。

所以：

> **切图阶段还完全没有说哪个 Core 来算。**

它只是在回答：

> 哪些 Op 应该绑在一起形成一个子图？

---

# 2. 为什么切图以后会“插入数据搬运节点”？

这个地方非常关键。

假设原来有：

```
Op1
 ↓
Tensor X
 ↓
Op2
```

现在如果你把它们放在同一个子图：

```
┌──── 子图 0 ────┐
│                │
│ Op1 → X → Op2  │
│                │
└────────────────┘
```

那么 X 是**子图内部数据**。

评估器知道：

> 这是同一个任务块内部产生、内部消费的数据。

所以不需要因为“切图”额外把 X 搬出去。

---

但如果你这样切：

```
子图 0             子图 1

Op1                 Op2
 ↓                   ↑
 └──── Tensor X ─────┘
```

那么 Tensor X 就跨越了子图边界。

这时候评估器会根据场景规则，自动补充相应的数据传输。

例如场景 A 下，本质上会变成：

```
子图 0

Op1
 ↓
X
 ↓
COPY_OUT
 ↓
DDR
 ↓
COPY_IN
 ↓

子图 1

Op2
```

你**不用自己把 COPY_OUT / COPY_IN 放进切图方案里**。

你只告诉评估器：

```
Op1 属于 SG0
Op2 属于 SG1
```

评估器一看：

> “哦，这条数据依赖跨子图了。”

于是它自动补数据搬运。

题目第 3 页明确说，切图方案只给出计算节点到 sgid 的映射，跨子图边界的数据搬运由评估程序自动重建。

所以“切边”是有代价的。

---

# 3. 那“子图重复读取同一数据”是什么意思？

这个可以用一个特别简单的例子。

假设有一个输入 Tensor $X$，同时被三个操作使用：

```
             → Op1
            /
DDR 中的 X → Op2
            \
             → Op3
```

如果：

```
Op1、Op2、Op3
```

都在同一个子图里，那么可能只需要：

```
DDR
 ↓
COPY_IN X
 ↓
核内缓存
 ├→ Op1
 ├→ Op2
 └→ Op3
```

一份数据被三个操作共享。

---

但如果你把它切成三个子图：

```
SG0: Op1
SG1: Op2
SG2: Op3
```

那么在场景 A 里，每个 Task 都是独立的。

结果很可能需要：

```
DDR X → SG0
DDR X → SG1
DDR X → SG2
```

同一份 X 被读三遍。

这就是题目说的：

> 同一份数据如果被多个计算节点使用，而这些节点被切到多个子图，每个子图都可能各自从 DDR 读取这份数据。

所以这里你应该开始有一点“切图直觉”了：

如果很多操作共享一个特别大的输入：

```
X = 500 KB
```

你可能倾向于把这些操作聚到一起。

因为否则：

```
500 KB × 3
```

之类的重复读取会非常贵。

当然，聚得太多又会损失并行度——这就是后面的优化问题。

---

# 4. 那什么是“子图调度方案”？

好了，现在假设切图结束，我们已经得到：

```
SG0
SG1
SG2
SG3
SG4
```

现在你有 3 个 NPU Core：

```
Core 0
Core 1
Core 2
```

接下来要决定：

> 谁去哪？

比如：

```
Core 0: SG0, SG3
Core 1: SG1
Core 2: SG2, SG4
```

这就已经开始是**子图调度方案**了。

但还不够。

因为 Core 0 有两个子图：

```
SG0
SG3
```

还得告诉评估器：

```
先 SG0
再 SG3
```

所以最后写成：

```
Core 0: [SG0, SG3]
Core 1: [SG1]
Core 2: [SG2, SG4]
```

对应 JSON：

```
"core_schedules": [
    [0, 3],
    [1],
    [2, 4]
]
```

题目就是这样定义的：`core_schedules` 是二维整数数组，外层下标就是 core id，内层列表就是这个 core 上的 sgid 执行顺序。

---

# 5. 所以切图和调度之间是什么关系？

你可以把完整过程想成：

```
原始计算图
    │
    │ 切图方案
    ↓
SG0 SG1 SG2 SG3 SG4
    │
    │ 子图调度方案
    ↓

Core0: SG0 → SG3
Core1: SG1
Core2: SG2 → SG4
```

所以：

### 切图方案决定

```
哪些 Op 属于同一块
```

### 子图调度方案决定

```
每一块放在哪个 Core
以及在这个 Core 上什么时候轮到它
```

二者不是一回事。

---

# 6. 为什么“放在哪个 Core”不直接算在切图里？

因为这两个问题的物理意义不一样。

例如你已经切出来：

```
SG0
SG1
```

假设它们之间有很大的数据依赖。

你可以：

```
Core0: SG0 → SG1
```

也可以：

```
Core0: SG0
Core1: SG1
```

**切图完全一样。**

但是 Core 分配不一样。

于是执行代价也可能完全不一样。

尤其场景 B 里，这个差异特别大：

- 如果 SG0、SG1 在同一个 Core，数据可以保留在 L1/UB；
- 如果 SG0、SG1 在不同 Core，就需要走 DDR。

所以：

> **“切没切开”是一层决策；“切开以后是不是仍放在同一个核”又是另一层决策。**

这个区别后面会非常重要。

---

# 7. 子图调度方案还有一个约束：不能违反依赖

例如：

```
SG0 → SG2
```

说明 SG2 依赖 SG0。

如果两者都放 Core 0，你不能写：

```
Core 0: [SG2, SG0]
```

因为这相当于让后继先执行。

所以同一个 core 上的顺序必须满足子图之间的数据依赖。

题目规定：

> 每个 sgid 必须且只能出现一次，而且同核的调度顺序不能违反子图依赖。

---

# 8. 还有一个很容易混淆的地方

“子图调度顺序”并不意味着：

> 子图里面每一个 Op 的精确执行顺序也是你指定。

不是。

你指定的是：

```
Core 0:
SG0 → SG3 → SG5
```

但 SG0 内部如果有：

```
Op1
Op2
Op3
Op4
```

到底：

```
Op1 → Op3 → Op2 → Op4
```

还是别的合法顺序，是**官方的核内调度器**继续帮你决定的。

题目明确说，评估器会：

1. 根据你的切图构建 Task；
2. 自动补跨边界搬运；
3. 调用核内调度算法决定 Task 内操作顺序；
4. 最后做多核模拟。

所以你控制的是一个比较高层的调度。

---

# 9. 现在可以用一个具体小例子把两个方案连起来

假设原图：

```
        Op2
       ↗   \
Op1 ──      → Op4
       ↘   /
        Op3
```

### 第一步：切图方案

我们决定：

```
SG0 = {Op1}
SG1 = {Op2}
SG2 = {Op3}
SG3 = {Op4}
```

这一步只回答：

> 谁和谁是一组。

---

### 第二步：由于切图产生边界

原来：

```
Op1 → Op2
```

现在变成：

```
SG0 → SG1
```

所以这条依赖成为**跨子图依赖**。

同理：

```
SG0 → SG2
SG1 → SG3
SG2 → SG3
```

于是得到一个“子图级 DAG”：

```
        SG1
       ↗   \
SG0 ──      → SG3
       ↘   /
        SG2
```

这就是题目所谓的：

> 跨子图依赖形成的子图依赖图必须仍然是 DAG。

---

### 第三步：子图调度方案

如果有 2 核，可以：

```
Core 0:
SG0 → SG1 → SG3

Core 1:
SG2
```

或者：

```
Core 0:
SG0 → SG2

Core 1:
SG1 → SG3
```

或者其他合法安排。

这就是调度。

---

# 10. 你现在可以把题目中的两个输出翻译成人话

### `node_to_subgraph`

是在说：

> **“这些算子怎么打包？”**

### `core_schedules`

是在说：

> **“这些包怎么分给机器干？”**

所以最简心智模型就是：

```
Op
 ↓
组成 Subgraph
 ↓
Subgraph
 ↓
分给 Core
 ↓
决定同核顺序
 ↓
官方评估器模拟真正执行
```

这里还有一个很重要的细节，下一步非常值得讲：

> **“切成两个子图”和“把两个子图放在两个不同核心”不是同一回事。**

尤其在场景 A 和 B 里，这两个动作造成的数据搬运规则完全不同。只要这个点吃透，后面的题目结构就会突然清楚很多。

可以继续看这两个关键区别

**Q：**

> Asked at: 2026-09-23 05:48

如果这样安排，Core 一是不是要等到 Core 零搞完 SG 零，它才能开始做 SG 一？

**A：**

对，**在我们刚才那个例子里，是的**。但原因不是“SG1 被放在 Core1”，而是因为原来的子图依赖图里有：

```
SG0 → SG1
```

这条箭头表示：

> SG1 需要 SG0 产生的数据。

所以即使调度方案写成：

```
Core 0: SG0 → SG2
Core 1: SG1 → SG3
```

Core 1 也不能一开机就直接执行 SG1。它必须等 SG0 提供所需的数据。

可以画成时间关系：

```
时间 →

Core 0:  [   SG0   ] [ SG2 ... ]
               │
               │ 数据依赖
               ↓
Core 1:  ......等待...... [ SG1 ] [ SG3 ]
```

这里最关键的一点是：

> **等待来自计算图的依赖，不是来自“核心编号”或者 `core_schedules` 本身。**

假设另一种情况，SG0 和 SG1 完全没有依赖：

```
SG0        SG1
```

那么完全可以：

```
Core 0: [ SG0 █████████ ]
Core 1: [ SG1 ███████   ]
```

两边从一开始就同时干。

---

而在我们这个例子里，子图依赖图是：

```
        SG1
       ↗   \
SG0 ──      → SG3
       ↘   /
        SG2
```

因此：

- SG1 必须等 SG0；
- SG2 也必须等 SG0；
- SG3 必须等 SG1 和 SG2。

所以即使我们把它分配成：

```
Core 0: SG0 → SG2
Core 1: SG1 → SG3
```

实际可能更像：

```
时间 →

Core 0: [ SG0 ] [       SG2       ]
             \             \
              \             \
Core 1:        [ SG1 ] ......等SG2...... [ SG3 ]
```

这里 SG3 虽然在 Core1 上排在 SG1 后面，但**SG1 做完也不代表 SG3 马上就能做**，因为它还要等另一个前驱 SG2。

---

再多一个你现在很值得注意的小点：

## 场景 A 里，等待得更严格

场景 A 中，一个子图就是一个 Task。跨核情况下，SG1 要等 **SG0 整个 Task 完成**，再加上题目规定的跨核前驱等待，才可以激活。题目规定场景 A 的跨核前驱等待为 1000 cycles。

所以大致是：

```
Core0: [ SG0 完整执行完 ]
                     │
                     │ + 跨核等待
                     ↓
Core1: ............... [ SG1 ]
```

所以对场景 A 来说，你刚才说的：

> “Core1 是不是要等 Core0 搞完 SG0，才能开始 SG1？”

**就是非常准确的理解。**

但一定要加上这个条件：

> 因为存在 `SG0 → SG1` 的依赖。

不是所有不同核上的子图都互相等。

**Q：**

> Asked at: 2026-09-23 11:46

问题目标是什么意思？提出高效且效果良好的多核切图与调度方法，给定计算图和核心数量后，能够在合理时间生成符合要求可执行的多核切分与调度方案，并尽可能缩短总体任务执行时间，额外适于搬运。方法需要联合确定各操作节点子图归属、子图核心分配以及各核心上子图执行顺序。我能不能理解成就是要给出一个切图调度策略，输入的是它的那个，输入是它的那个一个大的 JSON 文件，输出是切好了子图并且映射好，并且给出那个，就是那个调度的顺序方案。但是什么叫在合理时间内生成？怎么判断这个时间是不是合理？是按照算法的复杂度来算的吗？

对，你这个理解已经非常接近题目的准确含义了。

这段“问题目标”其实就是在定义：**你们到底要写一个什么算法程序。**

你可以把整个任务先压缩成：

```

一张完整计算图 JSON
+ 核心数量 N

        ↓

        ↓

2. 每个子图分配给哪个 Core

```

也就是你前面说的：

> 输入一个大的 JSON，输出一个已经“切好图 + 映射到核心 + 排好执行顺序”的方案。

这正是题目说的三个联合决策：

- 各操作节点的子图归属；
- 子图的核心分配；
- 各核心上的子图执行顺序。

不过有一个小修正：**你输出的不是“切好的新计算图 JSON”本身。**

你实际上只输出方案，例如：

```
{
  "node_to_subgraph": {
    "101": 0,
    "102": 0,
    "103": 1
  },

    [0],
    [1]
  ]
}
```

然后官方评估器根据你的方案，自己重建跨子图的数据搬运、核内操作顺序等。

## “在合理时间内生成”是什么意思？

这个地方题目其实给了非常明确的解释。

在问题 1 的脚注中，它写道：

> “高效地”代表算法应该避免使用暴力迭代搜索机制，**以单个用例能在 5～10 分钟内给出结果为佳。**

所以这里的“合理时间”并不是一个纯数学意义上的复杂度要求，比如：

> 必须是多项式时间。

题目没有这么规定。

它给的是一个非常工程化的标准：

> **对一个测试 case，你的算法最好在大约 5～10 分钟内生成一个高质量方案。**

---

## 那算法复杂度重要吗？

重要，但它更像是**解释为什么你的方法能够在合理时间运行**，而不是官方直接拿渐近复杂度给你判分。

比如你设计一种方法：

```
枚举所有可能的切图
×
枚举所有核心分配
×
枚举所有执行顺序
```

那么虽然理论上一定可以找到最优解，但搜索空间会爆炸。

比如光是把 $m$ 个操作分成不同子图，就已经有巨大的组合数量；再乘上核心分配和顺序排列，基本不可能对真实大图暴力搜索。

因此题目明确说：

> 避免暴力迭代搜索。

它想要的是类似：

```
读取计算图
↓
分析结构
↓
快速产生初始切图
↓
快速分核
↓
进行有限次数的改进
↓
输出
```

而不是：

```
尝试方案 1
尝试方案 2
尝试方案 3
……
尝试 10^100 个方案
```

---

## 所以“高效”和“效果良好”其实是两个不同要求

“高效”说的是：

> **你求解这个调度方案本身不能花太久。**

“效果良好”说的是：

> **你生成的方案放进官方 evaluator 以后，Makespan 要尽量短，额外数据搬运要尽量少。**

这两个目标不能混在一起。

比如算法 A：

```
运行 1 秒
但是调度结果很烂
```

不够好。

算法 B：

```
搜索 3 天
得到极好的调度
```

也不符合题目希望的实际场景。

比较理想的是：

```
几分钟
↓
生成一个很好的调度方案
↓
官方 evaluator 得到较低 Makespan
```

---

所以你现在可以把整道题的最上层理解成一句非常准确的话：

> **我们要写一个“调度方案生成器”。**

它不是直接去执行神经网络，而是：

```
计算图 JSON
      ↓
调度算法
      ↓
调度方案 JSON
      ↓
官方模拟器
      ↓
Makespan / 搬运量
```

而比赛真正考察的，就是：

> **你的“调度方案生成器”能不能在几分钟级时间里，给出足够好的方案。**

所以这里不是单纯的算法复杂度题，而更像是典型的**组合优化 + 启发式算法工程问题**：理论复杂度告诉你哪些路线根本不可行，实际 5～10 分钟的 wall-clock runtime 则是题目真正给出的工程约束。

可以继续把这两个判断分开

**Q：**

> Asked at: 2026-09-23 11:48

它这个高效和效果良好，嗯，就是我理解是要在两个指标上优化，一个是给方案的速度要快，一个是这个方案给出来后在官方那个评估器上评估的指标要好。嗯，第二点比较好理解，因为所有人的拿到了官方的程序都是一样，但第一点的话，有点不太理解。那第一点不是跟每个人自己电脑的性能有关系吗？比较客观的标准，我能想到也就是复算法复杂度，但是即使算法复杂度相同，那不同人电脑性能跑出来的效果肯定不一样啊。

**A：**

对，你这个疑问非常关键，而且你抓到了题目里“高效”这个词的一个本质问题：

> **如果不统一硬件，单纯比较“跑了多少秒”确实不公平。**

所以这里最好不要把“高效”和“Makespan 好”理解成两个完全对称的评分指标。它们其实性质不同。

题目对“高效”的解释是：应避免暴力迭代搜索，**单个用例最好能在 5～10 分钟内给出结果**。这里用的是“为佳”，而不是“必须在统一机器上低于某个秒数”。

因此我更倾向于把它理解成：

> **“高效”主要是一个可计算性 / 工程可行性要求，而不是像 Makespan 那样的统一数值评分指标。**

---

你可以把这两个东西分成：

### 第一类：求解器本身的效率

也就是：

```
计算图 JSON
    ↓
你的算法
    ↓
调度方案 JSON
```

这一段花多少时间。

这个时间确实依赖：

- CPU；
- 内存；
- 并行线程数；
- 是否用了 GPU；
- Python / C++；
- 实现优化程度。

所以两个算法即使理论复杂度相同，实际速度也可能差很多。

---

### 第二类：生成出来的方案质量

```
你的方案 JSON
    ↓
官方 evaluator
    ↓
Makespan
额外搬运量
```

这个就相对客观得多。

因为只要：

- 输入 case 相同；
- 配置相同；
- evaluator 相同；

同一个方案得到的 Makespan 就一样。

这也是题目的核心性能指标。

---

## 所以第一项更像“约束”，第二项更像“目标”

可以把题目的精神抽象成：

$$
\text{在求解时间可接受的前提下，尽可能降低调度结果的 Makespan。}
\tag{20}
$$

而不是：

$$
\text{求解时间}+\text{Makespan}
\tag{21}
$$

两个东西直接加起来优化。

因为它们单位都完全不一样：

- 求解器运行时间可能是秒/分钟；
- Makespan 是 NPU 时钟周期。

题目也没有给一个权重把二者合成单一目标。

---

## 你说“那是不是主要看算法复杂度？”——一半对

算法复杂度确实是最客观的一部分。

例如两个方法：

### 方法 A

枚举所有可能的切图、分核和排序。

哪怕你有非常强的电脑，随着图规模增长，搜索空间都会爆炸。

这种方法从算法结构上就是不合适的。

### 方法 B

先线性扫描计算图，构造若干启发式特征，再做有限次数局部搜索。

即使换一台稍慢的电脑，它通常仍然能在合理时间内完成。

所以题目说“避免暴力迭代搜索”，其实是在表达：

> **方法应该具有合理的尺度扩展性，而不是靠硬件把指数搜索硬顶过去。**

---

但只报告大 $O$ 也不够。

比如两个算法都是：

$$
O(m^2),
\tag{22}
$$

其中 $m$ 是计算节点数量。

一个可能每一步只做简单整数运算；

另一个每一步都调用一次完整的官方 evaluator。

实际运行时间可能差几十倍甚至几百倍。

所以比赛论文里更完整的做法通常是同时给：

```
理论：
算法复杂度 / 搜索空间 / 迭代次数

实验：
CPU 型号
内存
Python 版本
线程数
每个 case 实际求解时间
```

这样别人至少知道：

> “你是在什么机器上得到这个时间的。”

---

## 更重要的是：题面似乎没有把“求解时间”列为必须提交的统一评估指标

题目要求提交的核心实验结果是：

- 平均加速比；
- Makespan；
- 总额外数据搬运量；
- 问题 3 还有 Cache 命中率；
- 可复现 Python 程序。

而脚注只是说单个用例 **5～10 分钟为佳**。

这说明至少从题面来看，“5 分钟”和“7 分钟”的差异，并不像：

```
Makespan = 500000
vs
Makespan = 600000
```

那样是一个明确的官方性能比较指标。

所以我会把它理解为：

> **你不能为了多优化一点 Makespan，搞一个每个 case 搜索几十小时甚至几天的算法。**

但如果：

```
队伍 A：2 分钟
队伍 B：4 分钟
```

只要两者都在合理范围内，我不会理解成 A 就天然比 B 的算法优秀一倍。

---

## 甚至可以把题目的真正优化问题理解成“预算内搜索”

比如赛题隐含给你一个计算预算：

```
每个 case 大约几分钟
```

然后问：

> **在这几分钟预算里，你能找到多好的调度？**

这其实比单纯看渐近复杂度更接近实际。

例如：

```
算法 A：
10 秒得到不错方案

算法 B：
第 10 秒和 A 一样
继续搜索 3 分钟
得到更好方案

算法 C：
需要 3 小时才能超过 B
```

那么 B 很可能就是更符合这道题精神的方案。

所以后面我们在设计算法的时候，真正值得关注的其实是：

> **单位搜索时间能换来多少 Makespan 改进。**

这已经很接近 anytime algorithm 的思想：先快速得到合法解，然后利用剩余计算预算不断改进。

---

因此你刚才的理解可以稍微修正成：

> **不是“两个同等地位的评价指标”，而是一个硬件相关的工程可行性约束 + 一个统一的方案质量目标。**

也就是：

```
首先：
算法不能慢得离谱，
不能靠暴力穷举。

在这个前提下：

真正拼的是
官方 evaluator 上的调度质量。
```

而且这其实对我们后面选算法很重要：我们没必要太纠结“我的 Mac 比别人快，所以能不能多跑一点”，更应该关注**算法在固定计算预算增加时，解质量怎样增长，以及它的尺度扩展性如何**。

可以继续把这个判断落到实践上

**Q：**

> Asked at: 2026-09-23 11:50

那如果我说我能，我我我找到一种方法，在A一百GPU上几秒钟就可以求解出来，那这样一般人又用不上A一百这么好的芯片，怎么办？假如我真的找出这种方法，而且 make span 还行，能写上去吗？

**A：**

可以写，而且从题面本身看，**没有规定必须在统一型号的 CPU/GPU 上运行，也没有禁止使用高性能 GPU**。题面只说算法应避免暴力迭代搜索，并以“单个用例能在 5～10 分钟内给出结果为佳”，同时要求提交可复现的 Python 程序。

但你论文里不能直接写：

> “本算法几秒即可求解，所以非常高效。”

而应该写成：

> “在 NVIDIA A100 GPU 上，本算法单例求解时间为 X 秒。”

因为这个“几秒”是**算法 + A100 硬件**共同产生的结果。

真正比较严谨的做法，是把三件事分开。

第一，**算法本身的计算结构**。比如它需要多少轮迭代、每轮做什么、理论复杂度怎样、是否存在指数级枚举。这个部分与机器型号相对独立。

第二，**实际 wall-clock 时间**。明确报告硬件：

```
GPU: NVIDIA A100
CPU: ...
RAM: ...
Python / CUDA: ...
```

然后说：

```
A100 上：3.8 s / case
```

这完全没有问题。

第三，最好再回答一个更有说服力的问题：

> **不用 A100 会怎样？**

例如你再拿普通 CPU 或你自己的 Mac 跑一次：

```
A100：      4 s
普通 GPU：  23 s
CPU：       95 s
```

这就非常漂亮，因为它证明：

> A100 只是把算法加速了，而不是算法必须靠 A100 才能活下来。

---

反过来，如果情况是：

```
A100：5 秒
普通电脑：3 小时
```

那也不是说不能写。

但这时候你最好不要把结论写成“本算法具有优异的普适求解效率”，而应该更准确地说：

> **该算法具有较高并行性，在高性能 GPU 上能够快速求解。**

然后讨论它的硬件依赖。

这甚至可能成为你方法的一个特点：如果你的算法本身特别适合 GPU massive parallelism，那这完全可以是一项方法设计。

---

还有一个更极端的情况。

假如你的算法实际上是：

```
生成 1000 万个随机调度方案
↓
全部扔到 A100 上暴力并行
↓
选最好的
```

A100 确实 5 秒跑完。

这时虽然“墙钟时间”很好，但它可能仍然和题面“避免暴力迭代搜索机制”的要求存在张力。

所以：

> **高性能硬件不能把一个本质上的暴力穷举自动变成一个算法上“高效”的方法。**

但如果你做的是：

```
利用图结构
↓
构造候选
↓
GPU 并行评估 / 局部优化
↓
快速得到高质量解
```

那就完全不同了。

---

所以我会把“高效”拆成两个维度：

题目真正更希望看到的是前者有道理，同时后者在现实机器上也可接受。

因此如果你真的找到一种 **A100 上几秒、Makespan 还很好** 的方法，我当然会建议写进去。更强的论文写法不是藏掉 A100，而是**把硬件条件透明报告，再补一个尺度扩展或跨硬件实验**。这样评委看到的不是“氪了一张 A100”，而是：

> 这个算法为什么能并行、随着图规模怎么增长、换硬件以后性能怎样退化、A100 究竟加速了哪一部分。

这就很扎实。

**Q：**

> Asked at: 2026-09-23 11:51

那如果它就是强依赖这种高性能芯片，只不过虽然它呃计算成本就就是找芯片的成本高，但是它实际计算速度极快，在某些特定的情况下，就是用这种方法是最优的。比如说你需要求解一百个JSON图里面的最佳切图方案，那就是用这个很很快。那用其他方法就是很慢，怎么办？

**A：**

可以，而且你这个情况其实应该换一种评价框架：**不要问“这个算法脱离 A100 还能不能活”，而要问“在什么资源模型和任务规模下，它是不是最合适的方法”。**

题面本身只要求方法能在合理时间内产生高质量方案，并特别说应避免暴力迭代搜索、单例最好在约 5～10 分钟内给出结果；它并没有规定所有队伍必须用同一种硬件。

所以如果你的方法就是：

> “这是一个强 GPU 依赖的调度求解器。它利用 A100 的大规模并行性，在批量处理大量计算图时极快。”

这完全可以成立。

关键是你不要把它包装成：

> “在任何机器上都比别人高效。”

而应该明确它是一种**条件最优/场景优势明显的算法架构**。

---

比如你说的一百张 JSON 图，就非常典型。

假设方案 A 是普通 CPU 启发式：

```
每张图 2 分钟
100 张 = 200 分钟
```

你的 GPU 方法：

```
启动 / 租用 A100：5 分钟准备成本
每张图：2 秒
100 张：200 秒 ≈ 3.3 分钟
```

那么整个批处理时间就是

$$
T_{\mathrm{batch}}
=
T_{\mathrm{setup}}
+
\sum_{i=1}^{M}T_i .
\tag{24}
$$

这里 $M$ 是图的数量。

假设：

$$
T_{\mathrm{setup}}=300\text{ s},
\qquad
T_i=2\text{ s},
\qquad
M=100,
\tag{25}
$$

那么

$$
T_{\mathrm{batch}}
=
300+100\times2
=
500\text{ s}
\approx8.3\text{ min}.
\tag{26}
$$

这时候即使“获取 A100”本身有固定成本，它在批量任务里被摊薄了。

这叫 **amortization（摊销）**。

---

所以你这个方法甚至可以形成一个很漂亮的论文论点：

> **针对大批量多计算图调度场景，高性能 GPU 的固定资源获取成本可以被大量实例摊销，从而显著降低平均单实例求解时间。**

平均每张图的总时间可以写成

$$
\bar T(M)
=
\frac{T_{\mathrm{setup}}}{M}
+
T_{\mathrm{solve}}.
\tag{27}
$$

当

$$
M\rightarrow\infty
\tag{28}
$$

时，

$$
\frac{T_{\mathrm{setup}}}{M}\rightarrow0,
\tag{29}
$$

于是平均成本逐渐接近纯求解时间。

这个数学结构就非常清楚了：

> **小批量可能不划算，大批量极其划算。**

---

而且这里还有一个容易混淆的地方。

## “贵”不等于“不高效”

你其实有至少三个不同维度：

### 1. Wall-clock latency

多久能得到答案？

比如：

```
A100：2 秒
CPU：120 秒
```

你的方法显然低延迟。

### 2. 计算资源消耗

用了多少 GPU-hours / CPU-hours？

这个可能 A100 更贵。

### 3. 金钱成本

租一张 A100 一小时多少钱？

这个又是第三个量。

所以不能把：

> “需要昂贵芯片”

直接等价成：

> “算法低效”。

现实中经常恰恰相反：

> **为了极低延迟，愿意花更多算力。**

例如在线编译、数据中心调度、实时规划，本来就可能这样做。

---

更进一步，你甚至可以把这个问题写成一个多目标选择：

$$
\min
\left(
T_{\mathrm{solve}},
\;
C_{\mathrm{compute}},
\;
M_{\mathrm{NPU}}
\right),
\tag{30}
$$

这里：

- $T_{\mathrm{solve}}$：产生调度方案需要多久；
- $C_{\mathrm{compute}}$：求解器本身的计算成本；
- $M_{\mathrm{NPU}}$：最终方案在官方 NPU 模拟器上的 Makespan。

注意这里有两个完全不同的“时间”：

```
求解器自己花多少时间
≠
生成出来的 NPU 调度方案执行多久
```

这是很重要的。

你甚至可能得到：

```
算法 A：
求解 1 秒
NPU Makespan = 1,000,000

算法 B：
A100 求解 20 秒
NPU Makespan = 700,000
```

那么在很多实际部署环境中，B 完全可能更值得。

因为一次离线调度结果可能被重复执行很多次。

---

这里又出现一个非常重要的摊销。

假设一个神经网络调度方案只求一次，却会执行一百万次。

那么你为了求一个更好的 partition，多花 10 分钟根本不算什么。

设方案生成一次耗时为 $T_{\mathrm{plan}}$，之后执行 $R$ 次，每次硬件运行时间为 $T_{\mathrm{exec}}$，那么总成本近似是

$$
T_{\mathrm{total}}
=
T_{\mathrm{plan}}
+
R\,T_{\mathrm{exec}}.
\tag{31}
$$

当 $R$ 很大时，哪怕规划阶段贵一点，只要能稍微降低 $T_{\mathrm{exec}}$，收益都可能非常巨大。

这其实是你这个想法最强的现实理由。

---

不过有一个边界必须注意：

如果你的方法是：

> “A100 上暴力枚举所有 partition，因为 A100 快，所以几秒找到最优。”

那题面那句“避免使用暴力迭代搜索机制”会成为一个明显问题。

哪怕它现实中真的快，论文也必须正面解释：

- 搜索空间到底多大；
- 为什么 GPU 可以处理；
- 图规模增长后是否爆炸；
- 是否属于穷举；
- 有没有结构化剪枝；
- 可扩展到多大实例。

但如果你的方法是：

```
利用图结构缩小搜索空间
+
GPU 并行生成候选
+
GPU 并行评估
+
局部改进
```

那么这就非常合理。

甚至可能成为一个**GPU-native scheduling algorithm**，而不是“普通算法放到 GPU 上加速”。

---

还有最后一个很重要的措辞问题。

如果你不能证明找到的是全局最优，不要写：

> “最佳切图方案”。

应该写：

> “当前算法找到的最优方案”
>  或
>  “高质量可行方案”。

只有如果你能给出例如上下界：

$$
LB\le M^\star\le UB
\tag{32}
$$

并且最后

$$
LB=UB,
\tag{33}
$$

才能严格说你证明了全局最优。

---

所以你这个假想情况，我会非常愿意保留：

> **一种强依赖高端 GPU、但对批量计算图调度具有极高吞吐量的方法，本身完全可以是一条很有价值的路线。**

甚至对 A 题来说，这可能比“所有普通笔记本都能跑”的启发式更有研究味道。真正需要做的不是弱化它的硬件依赖，而是**把适用场景、资源条件、批量规模、扩展性和方案质量讲清楚**。

而你刚才说的“100 个 JSON 一起求”，其实已经让我想到一种很值得探索的方向：**把很多候选切图或者很多不同 graph 的局部 move 同时批量化到 GPU 上评估**。这可能会和这道题官方 evaluator 的结构产生非常有意思的结合。

**Q：**

> Asked at: 2026-09-23 11:58

来，我们继续看场景A和场景B，以及下面的三个问题。先只看场景A、B这两个给出的不同约束条件是什么？

**A：**

可以。我们这一步只看 **场景 A 和场景 B 的硬件/执行规则差异**，先不进入下面三个问题。

最核心的一句话是：

> **A 和 B 的区别，不是核心数量不同，也不是计算图不同，而是“子图之间如何同步、数据能不能留在核内继续复用”不同。**

### 场景 A：没有核间同步机制

题目规定：

- **一个子图就是一个 Task**。
- 子图之间的依赖由 CPU 主控通过 Task 调度来保证。
- 即使两个子图被安排在**同一个 Core** 上，前一个 Task 结束后，核内缓存状态也会被清空。
- 因此，只要数据跨越子图边界，就必须经过 DDR 中转。
- 所以同核子图通信和跨核子图通信，在数据搬运这个意义上没有本质区别，题面写成 $C_{\text{inner}}=C_{\text{cross}}$。

可以想成：

```
Core 0:

SG0
 ↓
写回 DDR
 ↓
Task 结束，核内缓存清空
 ↓
再从 DDR 读回来
 ↓
SG1
```

哪怕 SG0 和 SG1 都在 Core 0，也不能直接把 SG0 的中间 Tensor 留在 L1/UB 给 SG1 用。

所以场景 A 的关键词是：

> **子图边界 = Task 边界 = 核内数据不能跨过去。**

---

### 场景 B：存在核间同步机制

规则变成：

- **同一个 Core 上的所有子图可以合并进一个 Task。**
- 同核的前序子图产生的数据，可以继续留在 L1/UB 中，直接给后面的子图使用。
- 因此，同核子图之间不一定需要经过 DDR。
- 只有真正跨 Core 的依赖，才需要源 Core 把数据写入 DDR，然后目标 Core 再读入，并配合同步信号。

例如：

```
Core 0:

SG0
 ↓
Tensor X 留在 L1
 ↓
SG1 直接使用 X
```

不必再：

```
L1 → DDR → L1
```

所以场景 B 中，同核通信更便宜，题面写成 $C_{\text{inner}}<C_{\text{cross}}$。

---

不过 B 多了一个新的代价：

如果 SG0 产生的数据要一直留到 SG3 才使用，那么这个 Tensor 在 SG1、SG2 执行期间也一直占着 L1/UB。

所以：

```
少了一次 DDR 搬运
```

不一定纯赚，因为同时可能：

```
Tensor 长时间驻留
→ 占缓存
→ 其他数据放不下
→ 产生缓存压力
```

题面也明确提醒，同核子图之间的数据驻留会持续占用私有缓存。

---

所以你现在可以先记成这个最简版本：

|   | 场景 A | 场景 B |
| --- | --- | --- |
| 一个 Task 包含什么 | 一个子图 | 同一 Core 上可以有多个子图 |
| 同核子图之间能否保留数据 | **不能** | **可以** |
| 同核子图通信是否走 DDR | 要 | 通常不用 |
| 跨核通信 | DDR | DDR + 同步 |
| 主要新问题 | 切得越碎，DDR 搬运越多 | 数据复用与缓存占用之间权衡 |

所以本质上：

> **A 把“子图边界”看得很硬；B 把“Core 边界”看得更硬。**

在 A 中，你只要切成两个子图，就已经产生很强的隔离。

在 B 中，切成两个子图本身不一定贵；**只要它们最后还放在同一个 Core 上，就仍然可以共享核内数据。**

这个区别吃透以后，下面问题 1 和问题 2 为什么要分别设计算法，就会非常自然。

**Q：**

> Asked at: 2026-09-23 12:32

问题三，讲解一下。共享L2资源下的多核切除与调度。

**A：**

可以。问题 3 其实最好理解成一句话：

> **在场景 B 的基础上，再给所有 Core 增加一个共享的只读 L2 Cache，然后研究这个 L2 会怎样改变最优的切图和调度。**

题目明确说，问题 3 沿用场景 B，只是额外加入一个所有核心共享的只读 L2，容量为 1 MB，带宽为 250 bytes/cycle，而且它的带宽和 DDR 带宽彼此独立。

先看没有 L2 的场景 B。

假设有一个输入 Tensor `X`，它在 DDR 里，而且 Core 0、Core 1、Core 2 都要用它：

```
             Core 0
               ↑
               │
DDR 中的 X ────┼──→ Core 1
               │
               ↓
             Core 2
```

没有 L2 的时候，三个 Core 都要去 DDR 读 `X`。

于是可能发生三次：

```
DDR → Core 0
DDR → Core 1
DDR → Core 2
```

而且这些 DDR 访问还会一起争抢那条总带宽。

---

问题 3 加入 L2 后，结构变成：

```
                共享 L2
               /   |   \
              /    |    \
         Core 0  Core 1  Core 2
               ↑
               │
              DDR
```

第一次有人需要 `X` 的时候，如果 L2 里面没有：

```
DDR → X → Core
```

同时 `X` 会进入 L2。

之后别的 Core 再读同一个 `X`，如果 `X` 还在 L2 里，就可以：

```
L2 → Core
```

而不用再次访问 DDR。

题目的模拟规则就是这样：`COPY_IN` 发射时先查共享只读 Cache；命中时走 Cache 带宽，未命中时访问 DDR，数据读完后再放入 Cache。

所以 L2 的核心价值是：

> **多个 Core 对同一个输入 Tensor 的重复读取，可以被共享 Cache 吸收。**

这和场景 B 里“同一个 Core 内复用 L1/UB”是两个不同层次。

你可以这样记：

```
L1 / UB：
每个 Core 私有
主要解决“同核复用”

L2：
所有 Core 共享
主要解决“跨核共享输入的重复读取”
```

所以问题 3 并不是简单问：

> “加一个 L2 后快多少？”

而是在问：

> **既然现在跨核重复读取可能被 L2 缓存，那么我们原来在场景 B 里的切图和分核策略是不是应该改变？**

比如在问题 2 里，你可能因为 `X` 很大，会倾向于把多个使用 `X` 的计算都放在同一个 Core：

```
Core 0:
SG1
SG2
SG3
```

因为这样可以避免：

```
Core0 ← DDR X
Core1 ← DDR X
Core2 ← DDR X
```

但有了 L2 以后，也许可以大胆一点：

```
Core0: SG1
Core1: SG2
Core2: SG3
```

因为：

```
第一次：DDR → X → L2

之后：
L2 → Core1
L2 → Core2
```

这样你可能获得更多多核并行，同时又没有付出那么大的 DDR 代价。

所以问题 3 的本质矛盾发生了变化：

> **问题 2：跨核会破坏数据局部性，所以要谨慎分核。**

> **问题 3：共享 L2 可以部分补偿跨核造成的重复读取，因此可能允许更激进的并行。**

---

不过 L2 不是无限大的。

题目规定：

```
容量：1 MB
```

而且淘汰策略是 FIFO。

所以如果调度顺序是：

```
读 X
读 A
读 B
读 C
读 D
……
很久以后再读 X
```

那么等第二次需要 X 时，X 可能已经被挤出 L2。

于是：

```
Cache miss
→ 再去 DDR 读
```

因此问题 3 里面，**执行顺序也会影响 Cache 命中率**。

比如：

```
SG1 用 X
SG2 用 X
SG3 用 X
```

连续执行可能很好：

```
X 第一次 miss
后面两次 hit
```

但如果调度成：

```
SG1 用 X
SG4 用 A
SG5 用 B
SG6 用 C
...
SG2 用 X
```

X 可能已经被 FIFO 淘汰。

所以这道题开始多出一个新的优化因素：

> **时间局部性。**

---

因此问题 3 要你研究的其实是三件事同时怎么权衡：

```
多核并行度
    ↑
    │
    │
跨核重复读取 ←→ L2 Cache 复用
    │
    │
Cache 容量与访问顺序
```

你还是要决定原来的三件事：

1. 哪些 Op 属于哪个子图；

3. 每个 Core 上子图按什么顺序执行。

```

```

## 你的第一个想法：把脚本条件完全形式化

我认为这是**非常值得做，而且优先级很高**的。

因为我们现在读 PDF，理解的是：

> “大概有哪些约束？”

但真正做算法时，我们需要知道：

> “对于任意一个候选方案，究竟满足什么条件才合法；它究竟经过什么确定过程变成一个 Makespan？”

最理想的做法，是把官方 evaluator 拆成五层形式化规范。

第一层是**静态合法性**，比如：

```
每个非 COPY Op
→ 恰好属于一个 sgid

每个 sgid
→ 恰好出现在一个 Core 的 schedule 中

子图依赖图
→ 必须无环

同一个 Core 上的顺序
→ 不能违反依赖
```

第二层是**场景转换规则**：

```
Scene A
每个 SG = 一个 Task
跨 SG 都要产生边界数据搬运
Task 有 100 / 1000 cycle 等待

Scene B
同 Core 所有 SG = 一个 Task
同核数据可驻留
跨核才 COPY
同步延迟 500 cycle

Problem 3
Scene B
+ 共享 FIFO L2
```

第三层是**单个 Task 内部怎么被调度**。题目附件其实已经把它分成了 Step 1/2/3：

```
Step 1
确定一个核内拓扑顺序

Step 2
检查 L1 / UB
不够就 spill / reload

Step 3
在 M、V、MTE2、MTE3 四条 Pipe 上排执行
```

PDF 也明确描述了这三个阶段。

第四层是**全局离散事件模拟器**：

```
哪些 op ready
↓
哪些 Pipe 空闲
↓
哪些 COPY 正在争 DDR
↓
完成哪些事件
↓
释放哪些 Tensor
↓
推进到下一个事件时刻
```

官方的事件循环顺序甚至已经固定下来了。

第五层才是输出：

```
合法 / 非法
Makespan
extra movement
cache hit rate
trace
```

最后我们就可以把整个官方评估器抽象成一个确定函数：

$$
\mathcal E(G,P,C)=
\bigl(
\mathrm{valid},
M,
D,
H,\ldots
\bigr),
\tag{34}
$$

其中：

- $G$：输入计算图；
- $P$：我们的切图与调度方案；
- $C$：官方固定配置；
- $M$：Makespan；
- $D$：数据搬运；
- $H$：问题 3 的 Cache 指标。

这个形式化工作不是为了把 PDF 重写一遍。

它真正有价值的地方在于：**我们可以开始研究 $\mathcal E$ 的结构。**

例如：

> 移动一个 Op 从 SG1 到 SG2，到底会改变 evaluator 哪些部分？

如果能回答这个问题，就可能不用每次把整个 evaluator 从头跑一遍。

## 不过“完全等效”会比想象中难一点

我刚刚检查了实际代码，有一个需要特别注意的地方：

**DDR 带宽模拟内部不是全整数逻辑。**

它会维护剩余工作量，使用浮点数，并有类似 $10^{-9}$ 的比较容差、`ceil` 以及同时完成事件的处理。

所以如果我们用 Rust/C++ 重写，不能只做到：

> “数学上看起来一样。”

而要做到：

> **事件顺序、tie-breaking、浮点比较、排序顺序全部与 Python evaluator 一致。**

否则极端情况下：

```
官方：

我们的：

A 比 B 早一个极小量
```

```

↓
Pipe 发射顺序
↓
DDR contention
↓
整个后续 timeline
```

最终 Makespan 可能不同。

所以“完全等效 evaluator”必须通过非常严格的 differential testing。

## 一、先把三层评估器的身份固定下来

你的两条路线可以保留，但必须与官方评估器形成清晰的权威关系。

| 名称 | 做什么 | 对结果的要求 |
| --- | --- | --- |
| **E0：官方原版** | 提供参考结果、最终确认 | 冻结代码与配置，不修改 |
| **E1：等效加速版** | 重写热点，进行精细筛选 | 在约定输入范围内，与 E0 的可观察结果一致 |
| **E2：极速近似版** | 大规模探索、快速粗筛 | 可以近似，但要证明不会经常筛掉真正的好方案 |

整体流程是：

```
大量候选方案
    ↓
E2：极速粗筛
    ↓
少量候选方案
    ↓
E1：精细评价
    ↓
最终候选
    ↓
E0：官方确认
```

正式实验仍然使用官方配置、由官方评估程序产生指标。题面明确要求正式结果使用附件中的固定配置评估。

这里有两个重要修正。

**第一，E1 的目标是“可观察行为一致”，不是内部实现逐步照抄。** 它可以换数据结构、缓存中间结果、改写算法，只要最终接受或拒绝的判断，以及约定输出不变。

**第二，E2 的核心目标不是“平均数值误差很小”，而是“用它筛选以后，仍然留下足够好的方案”。** 一个预测器平均误差不大，但总把最值得保留的候选排到后面，对搜索反而有害。

## 二、形式化的验收标准：能够据此实现，而不只是能够据此理解

我建议给负责形式化的队友这样定义任务：

> **将题面和官方代码整理成一份具有明确输入域、状态、转移规则、确定性选择规则、输出和失败条件的规范。另一位成员读完以后，不需要自行猜测评估器的关键行为。**

这不要求使用专用定理证明器，也不要求先写出第二个完整评估器。但不能只交一份“题意概述＋若干约束公式”。

### 1. 必须覆盖这八部分

| 模块 | 必须形式化的内容 |
| --- | --- |
| 输入与配置 | JSON 字段、类型、ID、重复键、配置来源、非法输入 |
| 切图与调度合法性 | 操作覆盖、子图归属、子图依赖、核心分配、同核顺序 |
| Task 构造 | 场景 A、B 的组织方式，边界 COPY 如何生成、如何计数 |
| 核内展开 | Step1 排序、Step2 换出换入、Step3 的执行顺序和依赖 |
| 全局可执行性 | Task 顺序、Pipe 顺序与跨核依赖组合后是否产生等待环 |
| 时间与同步 | Task 激活、跨核等待、操作发射、同时完成事件、时间推进 |
| 共享资源 | DDR 争用、L2 查询与淘汰、数值舍入、缓存容量 |
| 输出指标 | 每个结果字段的定义、统计来源，以及失败时如何返回 |

题目给出的评估过程本身就不仅是“检查约束”，还包含自动重建数据通路、固定核内调度、插入换入换出和全局模拟。因此，形式化必须描述**方案如何变成执行过程**，不能只有静态合法性条件。

### 2. 每条规则必须能追溯到代码和测试

统一使用这样的规则卡：

```
规则 ID
适用场景
规则类型：题面要求 / 实现行为 / 推导 / 近似假设
输入与前置条件
数学条件或状态转移
输出或失败行为
并列选择、排序与舍入规则
来源：文件、函数、行区间、文件哈希
正例测试
反例或边界测试
当前状态：已确认 / 有分歧 / 未知
```

例如，“同核同 Pipe 串行”不是写一句话就结束，还要进一步回答：

**多个操作都满足依赖时，谁先进入 Pipe？已经固定的队首操作在等待跨核输入时，后面的操作能否越过它？**

这类问题会直接影响高速版是否等效。

### 3. 有几个细节，必须作为形式化的重点

我这次实际核对附件代码后，发现尤其不能漏掉下面三点。

**基础切图校验通过，不等于最终可执行。** 附件还会检查更深层的组合依赖：场景 A 合并 Task 顺序；场景 B 和问题三合并本地依赖、Pipe FIFO 与跨核 COPY，检查是否出现等待环。

**Step3 不只是计算一个局部时间。** 它还会输出固定的逐 Pipe 顺序，并增加内存空间复用产生的依赖。高速版不能改成“重新找一个更早的执行顺序”，然后仍声称等效。

**问题三的搬运统计，不能由我们按直觉重定义。** 当前实现的 `data_movement_bytes` 在 Task、换入换出展开阶段统计；不能自行把 Cache 命中字节从这个字段里扣掉。Cache 命中统计是另一部分。

这些观察的函数与行号已放进。它们也说明：**形式化应该同时保留“题面想描述什么”和“当前代码实际怎样计算”，发现差异就登记，不要偷偷替官方修正规则。**

```

    完整语义规范

rules.jsonl
    可被 Agent 查询和引用的规则卡

coverage.json
    规则 → 源码 → 测试的对应关系

ambiguities.md
    题面、说明与代码之间的分歧或未知

change_impact.md
    改一个方案后，哪些中间结果必须失效、重算
```

最后一份尤其重要。它直接服务于高速 evaluator 的缓存和增量更新。

例如，把一个子图从 Core1 移到 Core2，**不能直接假定只有这两个核心受影响**。其他核心上的边界 COPY、生成节点 ID、跨核依赖以及共享带宽竞争，都可能改变。必须根据依赖关系判断可以复用什么。

## 三、E1：把“完全还原”写成可执行的验收条件

E1 的要求可以概括为：

$$
\operatorname{Obs}\!\left(E_1(x)\right)
=
\operatorname{Obs}\!\left(E_0(x)\right).
\tag{35}
$$

这里的输入包括图、方案、配置、问题编号和冻结版本；“可观察结果”不能只含最终 Makespan。

### 1. 一致性分三个层次检查

| 层次 | 要比较什么 |
| --- | --- |
| **接受与拒绝** | 官方能成功的是否成功；官方拒绝的是否拒绝；失败阶段与语义类别是否一致 |
| **指标** | Makespan、全部搬运分项、Cache 命中与未命中字节/次数、命中率 |
| **完整诊断结果** | 操作与 Task 时间线、跨核传输、内存峰值、Cache 事件与最终内容等 |

**整数周期、字节数、计数的容差全部为零。** 少一周期也是不一致，不允许使用“相对误差很小”放过。

完整 JSON 比较不要求缩进或对象键顺序相同，但默认要求数组顺序及其内容一致。不能为了让测试通过，把 Cache 事件排序后再比较，或者忽略“难以复现”的字段。

另外，**超时、程序崩溃和方案非法必须分开**。不能因为自己的实现超时，就宣布这个方案不可执行。

### 2. 不能只比较最终分数

应当能够逐层比较：

```
方案解析
    ↓
Task 与边界 COPY
    ↓
Step1 操作序列
    ↓
Step2 spill 与扩展图
    ↓
Step3 Pipe 顺序与内存依赖
    ↓
全局事件模拟
    ↓
最终结果
```

发现差异时，保存**第一次发生分歧的位置**。这样形式化负责人和实现负责人才能迅速定位：究竟是规则理解错、节点生成顺序错，还是浮点与同刻事件处理出了问题。

### 3. 性能标准也要提前定义

我给 E1 设定的**队内初始目标**是：

> 在冻结的中大图测试矩阵上，相同资源条件下，常驻候选评价的配对加速比几何平均达到 **3 倍**；同时至少 90% 的配对没有明显退化——速度比不低于 0.8。

这是研发目标，不是我已经测得的结果，也不是官方要求。第一轮 profiling 后，队长可以在正式验收前调整并冻结。

正确性通过但速度未达目标，可以保留为“正确的部分加速实现”；不能包装成已经完成高速方案。

### 4. 关于“保证完全等效”的措辞

必须区分：

> **“在声明的测试集、版本和环境内零不一致。”**

与：

> **“对所有可能输入，已经数学证明完全等效。”**

前者可以通过工程测试建立；后者需要额外证明。任务书要求做到前者，并持续扩展覆盖，不能把有限测试说成普遍证明。

## 四、E2：以“筛选损失”为核心，而不是只看预测误差

你的混合思路成立，但 E2 的验收必须真正对应它的用途。

假设对同一张图、同一问题、同一核数，准备一批候选。先用 E0 把**整批候选**的真实成绩算出来。

然后让 E2 粗筛，例如从 128 个候选中留下预测最好的约 10%。

我们最关心的是：

> **短名单里最好的真实方案，比原候选池里最好的真实方案差多少？**

定义“短名单遗憾”：

$$
r=
\frac{
\displaystyle\min_{p\in S} M_0(p)
-
\displaystyle\min_{p\in C} M_0(p)
}{
\displaystyle\max\!\left(1,\min_{p\in C}M_0(p)\right)
}.
\tag{36}
$$

其中，完整候选池是 $C$，E2 留下的短名单是 $S$，官方 Makespan 是 $M_0$。

这个指标不是相对未知全局最优的差距，而是**粗筛这一步损失了多少本来已经找到的质量**。

### 我给出的初始验收门槛

以下均为队内设计值，需要在封存测试前冻结：

| 项目 | 初始标准 |
| --- | --- |
| 保留近优解 | 至少 95% 的测试候选池，短名单中保留一条距该池最好成绩不超过 1% 的方案 |
| 筛选损失 | 短名单遗憾的 P95 不超过 3%，并单列最坏情况 |
| Makespan 数值误差 | 提供校准周期估计时，相对误差中位数不超过 3%，P95 不超过 10% |
| 极速目标 | 相同资源、完整批评估成本下，相对 E1 吞吐达到 10 倍 |
| 安全行为 | 未完成的合法性检查必须标明；不能把未知当成已验证可行 |

**筛选质量优先于数值拟合。** 一种方法如果排序很好，但预测值没有准确校准，可以作为排序代理发布；只是不能把任意分数称为实际 cycles。

同时，不能把不同大小图的预测值混在一起，算一个漂亮相关系数就结束。真正的排序测试应当在**同图、同问题、同核数的候选池内部**完成。

### E2 必须交一份“近似清单”

例如：

```
近似了什么？
忽略了什么？
为什么能节省时间？
预计在哪些场景下偏乐观或偏保守？
如何识别风险？
何时直接交 E1？
```

这份清单让它成为一个可管理的近似模型，而不是“跑得很快、结果好像差不多”的黑盒。

在实际搜索中，还要保留当前已经确认的最好方案、结构多样的候选，以及少量不按 E2 排名选择的审计样本。否则搜索可能逐渐走向 E2 最容易误判的区域。

## 五、交叉测试：你说的简单切图算法是必要的，但不能只有这一类测试

你的想法应该落实为：

> **候选生成器独立于 E1、E2，参考标签由 E0 产生。**

前期不追求最优，先有几种结构不同、能稳定产出方案的算法。

建议至少包含三类：按拓扑序连续分块的简单方案；按粗略计算负载分核的方案；偏向共享输入和减少通信的聚合方案。再加入随机粒度、局部移动、合并、拆分与重排，用于制造差异和边界情况。

官方 stub 可以作为随机或格式测试来源，但题目明确说它不是性能基线。

### 测试集应分成四层

| 测试层 | 作用 |
| --- | --- |
| **微型语义测试** | 用小图隔离某条规则：等待、spill、并列事件、FIFO、容量边界 |
| **随机与对抗测试** | 寻找正常基线不容易触发的错误 |
| **正式数据覆盖** | 检查实际规模、三个问题、不同核数与不同划分粒度 |
| **封存候选池** | 独立检验 E2 的误差、排序与粗筛损失 |

两点特别重要。

**不能只测试“看起来还行”的合法方案。** 缺操作、重复子图、子图收缩成环、全局执行等待环、零大小张量、容量临界、并列 spill 选择，都应该进入测试。

**E2 验收时不能只给留下来的候选跑 E0。** 否则永远不知道它丢掉了什么。完整候选池都必须有参考成绩。

另外，不要默认“多核一定更快”“合并一定更好”“交换 ID 后成绩不变”之类性质。它们可以用来生成测试变体，但必须分别跑 E0，不能未经证明直接写成断言。

### 已经准备了两个可立即复跑的锚点

任务包中放了两个人工小图和六份原版输出，每个图分别运行三个问题。

其中一个共享输入小图在问题三中得到的是：**两个 COPY_IN 都 miss，而不是一个 miss、一个 hit**，因为两次查询都发生在数据进入 L2 之前。

这说明为什么要测具体时序，不能只依据“共享输入应该命中”的直觉实现。

这六次测试已运行并复跑通过，但只是接口和基础语义烟测，**不代表高速版已经实现或验收**。

## 六、统一接口：成员可以换实现，但不能换输入输出含义

我把公共接口定义成两种使用方式。

### 文件入口

```
evaluate(
    engine,
    problem,
    graph,
    plan,
    config,
    detail
)
```

### 搜索器常驻入口

```
prepare_graph(graph, config, problem)
    → 图上下文

evaluate(context, plan)
    → 单个评估结果

evaluate_batch(context, plans)
    → 一批评估结果
```

`prepare_graph` 只能提前处理与候选无关的部分。**凡是依赖具体切图方案的构图、spill、特征和模拟成本，都不能从单次候选评价时间中藏掉。**

响应必须带上这些信息：

```
请求 ID、引擎与版本
图 / 方案 / 配置 / 官方代码哈希
问题编号、核心数

状态：成功 / 非法 / 超时 / 不支持 / 程序错误
输入检查、方案检查、执行检查各做到哪一步

指标及其性质：官方结果 / 一致性契约结果 / 估计
分阶段时间、内存、是否回退、官方调用次数

诊断产物、风险标记、证据路径
```

详细 JSON Schema 已放进任务包。原始方案仍然只保留官方的 `node_to_subgraph` 和 `core_schedules`，不要混入这些团队字段。

### “极速”必须按完整流程衡量

最终比较的是：

$$
T_{\text{混合}}
=
T_{E2\text{粗筛}}
+
T_{E1\text{精筛}}
+
T_{E0\text{确认与审计}}
+
T_{\text{组织与传输}}.
\tag{37}
$$

不能只报告 GPU 内核耗时，也不能只报告缓存了全部答案以后的查询速度。

至少分别报告冷启动、常驻新候选、批量吞吐、完整命令行输出四种时间。使用 GPU 的比较必须包括必要的数据传输和完成同步；不同硬件的结果可以展示，但要明确是不同资源配置。

## 七、按你们的协作方式，实际分工这样落地

| 负责人 | 主责 | 不应单方面改动 |
| --- | --- | --- |
| **形式化队友** | 规则、状态语义、源码映射、边界夹具、变更影响 | 官方代码、测试判据和验收阈值 |
| **高速 evaluator 队友** | E1 热点加速与 E2 极速重构，可管理两个 Agent 分支 | 官方语义、金标准、公共接口 |
| **队长的 Codex／独立测试 Agent** | 来源冻结、候选生成、差分测试、封存验收、集成与签收 | 不经记录地修改标准或删除失败样本 |

这里不需要额外增加一个人类成员。关键是**实现者不能独自修改测试、解释失败、然后给自己宣布通过**。

启动顺序也不用完全串行：

> 冻结来源和接口后，形式化、官方适配器与测试生成器、profiling 可以同时开始。形式化先发布第一批已确认规则；E1 按热点逐步替换；E2 同时开展近似原型。最后再进行全矩阵验收与混合流程集成。

每次交接必须有版本、产物、复现命令、测试结论、已知限制和下一步，而不是只发“我做完了”。

任务包里的 `TASKS.json` 已经拆好了这些工作，并明确它们只是**待 Codex 映射和派发的业务任务**，没有假设你们现有通信协议的具体字段。

**最终验收不看“写了多少公式、重写了多少代码”，而看三件事：规则能不能追溯；E1 能不能在声明范围内保持一致；E2 能不能以显著更低的总成本，把真正好的候选留给后续精评。**
