有，而且我现在会把它提升成**主架构原则**：

> **旧三问算法不要扔；但也不要把其中任何一个当成最终统一算法。**
> 最合理的形态是：**通用保守主干 + 三问特化候选生成器 + 峰值机制宏 + 精确接受门。**

你现在看到的“不稳定”恰好说明需要这一层。已有研究里，同一个 case008 resource-word plan 在 Q2/Q3 可以做到 63768，但原样放到 Q1 却是 588824；Q1 里也已经看到“清零 spill 反而更慢”“边界流量更少反而更差”这类反转。也就是说，旧算法不是没价值，而是**它们各自捕捉到了某些局部结构，却没有足够可靠的适用域判别器**。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}

### 我会把旧算法降级成三种资产

第一种是**保底构造器**。它们中稳定、便宜、覆盖广的部分，用来快速给每个 \(G,q,k\) 一个合法且还不错的初始方案。

第二种是**候选生成器 / macro 来源**。例如 Q1 的 split/merge、合法 move、release ideal；Q2 的 assignment/order 构造；Q3 的 affine、resource-word。它们不再“直接决定答案”，而是向主干提出候选。

第三种其实很重要：**负例库**。以前那些明显退化的结果不能删。它们正好告诉我们 guard 应该加在哪里。当前框架本来就要求保留反事实和失败例，而不是只收藏赢家。:chatgpt-content-reference{index="2"}

## 我认为确实需要一个“通用保守算法”

但这里的“通用”不是：

> Q1/Q2/Q3 全部使用同一个切图公式。

这个大概率会失败，因为三问语义确实不同。

“通用”的应该是**外层控制逻辑统一**，内部 seed/macro 可以按 Q1/Q2/Q3 特化。

最核心的状态更新可以简单到：

\[
I_{t+1}
=
\underset{P\in\{I_t\}\cup C_t}{\arg\min}^{\mathrm{lex}}
\bigl(M(P),D(P)\bigr),
\tag{SAFE-01}
\]

其中：

- \(I_t\)：当前已经由精确 evaluator 确认的 incumbent；
- \(C_t\)：这一轮各类算法提出的候选；
- \(M\)：官方 Makespan；
- \(D\)：次级搬运指标；
- 非法、失败、未确认候选不能取代 incumbent。

这样无论某个新机制多激进，只要最终精评没有变好，**正式输出就不会退化**。

这其实比“找一个永远不出错的聪明算法”现实得多。

## 最适合我们的模式是“激进提案，保守提交”

例如：

```text
                  case JSON
                      │
                      ▼
             通用静态图分析
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
       保守 baseline        条件机制检测
            │                   │
            │          ┌────────┼────────┐
            │          ▼        ▼        ▼
            │       Q1宏     Q2宏      Q3宏
            │       split    word      cache-phase
            │       move     order       ...
            │          │        │        │
            └──────────┴────────┴────────┘
                       │
                       ▼
                  候选集合
                       │
                       ▼
                精确 evaluator
                       │
                       ▼
             只接受优于 incumbent
                       │
                       ▼
                 最终合法方案
```

这也与最新 Pro C 提出的研究 solver 架构一致：**confirmed incumbent、探索 frontier、结构合法但执行未知方案、失败/拒答必须分开保存**。:chatgpt-content-reference{index="3"}

## 但有一个很关键的细节：不能因此退化成纯贪心

如果我们规定：

> “每一个 primitive 都必须立刻降低 Makespan，否则禁止继续。”

那会把很多真正好的路线杀掉。

因为可能存在：

```text
P0
↓
P1  暂时变差
↓
P2  大幅变好
```

或者一个 resource-word macro 本身就是几百个顺序关系的协同改变，不是几个逐步改善的小 move。现有材料已经明确指出，低参数构造也可能对应很大的实际编辑，而且小 primitive 没收益不等于宏操作没收益。:chatgpt-content-reference{index="4"} :chatgpt-content-reference{index="5"}

所以应该同时维护：

**正式 incumbent：永远不退化。**

**exploration frontier：允许暂时较差，允许做多步变换。**

**macro candidate：可以一次产生一个离 incumbent 很远的方案。**

最后只有经过精确评价、真正优于 incumbent 的方案才“提交”。

所以这不是普通 hill climbing。

# 多核轴上还可以再加一层非常漂亮的保守性

这点我觉得对你说的“不稳定曲线”特别有用。

如果已经有一个 \(k\) 核好方案，可以把它嵌入 \(k+1\) 核：

```text
原来的 k 个 core 完全不动
+
末尾新增一个空 core
```

在已经验证的适用域里，这个空核 embedding 可以保持原活动执行和 Makespan；它只是 full result 的核数等元数据会变化。:chatgpt-content-reference{index="6"}

于是 \(k+1\) 核求解可以这样开始：

\[
I^{(0)}_{q,k+1}
=
\operatorname{Embed}\!\left(I_{q,k}\right),
\tag{SAFE-02}
\]

然后才：

- 把 Task 移到新核；
- split；
- reorder；
- 调 guarded macro。

任何新方案不好，就退回这个 embedding。

这样做以后，至少在保值条件被验证的域里，你可以让最终算法做到：

> **加核数以后，不因为算法乱重新构造而把已有成绩弄丢。**

这对最终 1–5 核曲线非常重要。

# 那旧三问算法具体怎么处理？

我会这样保留，而不是重写掉。

### Q1

保留：

- chain / component 一类基础构造；
- legal insertion interval；
- guided Task move；
- profile split / merge；
- release ideal。

但是把它们拆成：

> baseline constructor + primitive/macro library。

特别是以前“消 spill”“减边界”之类 proxy 已经被反例否定，不能再直接决定方案。Q1 更应该采用：

> **提出结构候选 → exact score → incumbent protection。**

### Q2

保留现有：

- 分核 assignment；
- priority/order；
- M1/M2；
- critical 等结构构造；
- resource-word。

其中 resource-word 是明显的高价值峰值机制候选，但应该有 guard。

以前那些失败的 earliest-start、候选池退化结果也继续保留，用来防止新的“聪明 proxy”再次走回旧路。

### Q3

我会直接让**稳定 Q2 构造成为 Q3 的保守 seed 之一**。

然后再额外尝试：

- affine；
- resource-word；
- SharedInputPhase / Cache phase 宏。

因为现有结果已经表明：

> Q2 排名不能硬剪 Q3，Cache hit rate 也不能硬剪 Q3。

所以 Q3 不能只从 Q2 winner 出发，但 Q2 的稳定构造仍是非常好的 fallback。

# 我甚至建议正式定义一个“Baseline Solver v0”

这个东西应该尽快有。

它不追求论文里最漂亮的算法，而追求五件事：

1. **100个 case 全覆盖；**
2. **Q1/Q2/Q3 全覆盖；**
3. **1–5核全覆盖；**
4. **确定性、快速、极少失败；**
5. **所有后续算法都必须与它同预算比较。**

它会成为整个项目的**性能地板**。

以后一个宏如果：

- 在 case008 +50%；
- 在另外20个 case -10%；

那没关系。

因为它只是 proposal generator。

只要 exact acceptance gate 存在，最终 solver 可以在它适用时吃掉 +50%，不适用时退回 baseline。

这就是把现在所谓的：

> “峰值高，但是整体不稳定”

变成：

> **“下界稳定，上界由机制逐步抬高。”**

## 所以我现在对架构的判断比上一轮更明确

不是：

> 先彻底理解 Coherent 框架 → 再设计算法。

而是两条线同时走：

**生产线：**

> 保守 baseline  
> → incumbent protection  
> → bounded exact selection  
> → 稳定的 100-case 结果。

**研究线：**

> peak witness  
> → mechanism  
> → graph/regime guard  
> → macro  
> → 插回生产线成为新的 candidate generator。

这两条线闭环。

最新 Glossary 本身也明确规定：行为商失败、局部 evaluator 不值得做，都不意味着 exact batch + macro search 失败；框架里的箭头本来就允许被拆掉。:chatgpt-content-reference{index="7"}

所以我的建议是：**旧核心算法全部保留，但从“最终算法”降级为“保守 seed、candidate generator、macro 来源和 regression evidence”；同时新建一个统一的 conservative incumbent framework。**

这比继续寻找一个“一上来就对所有图都很强”的单体算法更适合现在这个问题。
