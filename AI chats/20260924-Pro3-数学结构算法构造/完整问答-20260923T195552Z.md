原始依赖可以用生产关联矩阵 $U\in\{0,1\}^{n\times t}$、消费关联矩阵 $W\in\{0,1\}^{t\times n}$ 表达。Boolean 乘积 $UW$ 表示“存在经 tensor 的依赖”，再按官方规则处理直接依赖和 COPY 收缩，得到逻辑依赖矩阵 $D$。

若分区矩阵为 $Z\in\{0,1\}^{n\times m}$，每行恰有一个 1，则

$$Q=\operatorname{offdiag}(Z^\top D Z)$$

是在 Boolean 半环上的商图邻接表示。

**实现不应真的建立稠密矩阵。** 保留双向 CSR 或 tensor 超边；矩阵只是明确运算含义。尤其不能把 tensor 扇出压成普通边权后丢掉生产者、消费者、大小、位置和 logical key：成员报告的场景 B 跨核搬运是按核心对生成 COPY，源端还要串行执行多次 COPY_OUT。

01_形式化阅读包

展开执行图则必须纳入数据依赖、内存复用依赖、Pipe 顺序和跨核连接。成员报告的 Step3 内存复用不仅改变容量记账，还会生成真正的 `MEMORY_REUSE` 依赖边。

01_形式化阅读包 +1

### 3. 三问的联系不能被一个简化调度器抹平

按阅读包报告，Q1 有 Task 级同核等待与真实跨核前驱等待；Q2/Q3 的场景 B 有核心间 COPY 连接；Q3 又增加 FIFO Cache，并把命中读取放进独立的 CACHE_READ 带宽池。**不能把 Q1 的 Task 等待公式原样套进 Q2/Q3，也不能把缓存命中仍计入 DDR 池。**

01_形式化阅读包 +1

一个保守的模拟状态至少包括：

$$s=
(\text{时钟},\text{Pipe 指针与在飞操作},
\text{依赖/门控状态},
\text{各池剩余工作},
\text{有序缓存与待插入},
\text{同刻规则状态}).$$

所以，**相同的拓扑前缀、相同的已完成集合、相同的缓存驻留集合，都不是通用充分状态。**

队首能否越过尤其需要保留缺口：成员报告了固定 FIFO 和单槽，但明确没有构造队首阻塞探针；本次也未读到运行循环。不能把这个缺口写成已经确认的“不允许越过”。

## 三、机制一：保留动态资源接口，消去固定计算事件

这是我认为最适合成为第三路主干的机制。

### 1. 数学观察：很多计算细节只通过少量时刻影响外部

考虑官方编译后的一段计算。内部可能有上千个固定时长操作，但对外只暴露：

- 几个输入何时就绪；

- 几个输出何时可用于 COPY；

- 若干 Pipe 与 Task 门控。

如果内部不再访问动态资源，外部没有必要逐个观察它的全部事件。

将操作拆成 start/finish 节点，固定时长写成边权。用

$$a\oplus b=\max(a,b),\qquad a\otimes b=a+b$$

表达最早时刻传播。Baccelli 等关于离散事件系统的教材给出了这类闭包与最小解的代数基础；下面是针对有限执行 DAG 的边界消元构造，而不是声称教材已经解决本题。[[图片：]Rocq](https://www.rocq.inria.fr/metalau/cohen/documents/BCOQ-book.pdf)

### 2. 严格守卫：哪些节点不能消

首先保留边界集合 $B$，至少包含：

**所有共享传输的 start 和 finish、缓存 query/insert、Task 门控、最终 makespan sink，以及穿过模块边界的数据/FIFO/内存接口。**

内部集合 $I$ 只能包含满足以下条件的事件：时长固定；没有未表示的运行时状态副作用；全部次序约束已经显式化；官方在该区域按约束许可的最早时刻运行。

这最后一条必须审计。不能从“原图是 DAG”直接推出。

### 3. 消元公式与证明

按内部/边界分块：

$$x_I=A_{II}\otimes x_I
\oplus A_{IB}\otimes x_B
\oplus u_I.$$

由于内部无环，闭包是有限路径和。消去 $x_I$ 后，边界之间的有效约束为

$$\boxed{
A_{BB}^{\rm eff}
=
A_{BB}
\oplus
A_{BI}\otimes A_{II}^{*}\otimes A_{IB}
}.$$

源项可同样处理，或者加入一个固定时刻为零的虚拟源。

**命题：在上述守卫成立时，对任意合法边界释放时刻，消元前后所有保留节点的最早时刻相同。**

证明并不复杂：两个相邻保留节点之间，全部内部路径的最强约束就是路径权重最大值。把这些路径换成该权重的一条边，不删除约束，也不增加更强约束。沿保留图拓扑序归纳即可。

与动态资源控制器连接时，再按真实资源事件归纳：相同的释放时刻和控制器状态产生相同的下一次资源请求、完成及缓存动作。**注意使用的是已确认的完成事件，而不是可能被后来传输改写的预测完成时刻。**

### 4. 可执行构造与复杂度

令接口矩阵

$$H\in\mathbb T^{b_{\rm out}\times b_{\rm in}},$$

其中 $H_{o,i}$ 表示输入端口 $i$ 到输出端口 $o$ 的最大内部路径权。

```
for 每个输入端口 s:
    dist[s] = 0，其余为 -∞
    按拓扑序扫描内部图
    遇到另一个保留边界:
        记录系数，不在本轮越过该边界
    否则:
        做整数 max-plus 松弛

返回 H、端口绑定、守卫、内部重建见证
```

用 CSR 实现，构建成本为

$$O\!\left(b_{\rm in}(|I|+|E_I|)\right),$$

空间为

$$O\!\left(|I|+|E_I|+b_{\rm in}b_{\rm out}\right).$$

这里不需要普通意义上的低秩。需要的是**内部大、接口小、消元填充不严重**。

若一串模块的接口维度固定为 $b$，组合具有结合律，可以用线段树维护矩阵乘积；一个模块变化后的稠密重合成成本为

$$O(b^3\log r),$$

而不是重新组合全部 $r$ 个模块。前提是其他模块的编译结果及接口守卫确实未变；生成 ID 引起的更早变化不能忽略。

### 5. 从“消元”到“候选等价类”

第一版不用通用 equality saturation 框架，先做**语义完整的编译指纹去重**：

保留 literal ID、核心号、Pipe 队列、内存边、logical key、时长，以及可能影响迭代的映射插入顺序和类型。哈希只作索引，命中后再核验完整内容。

第二版才允许把两个模块归并，条件是：

$$H_1=H_2,$$

并且端口绑定、资源动作、别名关系、外部可见 ID 比较和同刻规则均相同。

**相同 $H$ 本身不够。** 若其中一个模块少写一次 DDR，或者同刻插入次序不同，它们就不是本题的精确等价。

`egg` 提供了条件重写和 e-class analysis 的工程机制，但它通常使用的局部成本 extraction 不能直接替代全局资源竞争下的 makespan 优化。这里借用的是“带条件的等价管理”，不是把低局部成本当成全局最优。[[图片：]arXiv](https://arxiv.org/pdf/2004.03082)

### 6. 一个必须阻止错误剪枝的反例

连续等分服务池容量设为 1。关键请求 $Y$ 工作量为 1，在时刻 0 到达；完成后执行 100 单位计算。另一个请求 $X$ 工作量为 2。

| $X$ 的释放时刻 | $Y$ 完成 | 最终 makespan |
| --- | --- | --- |
| 0 | 2 | 102 |
| 1 | 1 | 101 |

**让 $X$ 更早就绪，整体反而更慢。**

这是本次用精确有理数检查过的连续模型反例，不是官方微图。它说明：在仍会访问共享资源的上下文里，即使 $H_1\le H_2$ 逐项成立，也不能通用地剪掉后者。只有未来已变成纯固定时长、资源封闭的上下文，才能利用 max-plus 的单调性作这种支配剪枝。

释放时刻差异只能通过合法分区/核序诱发，不能转化为“选手额外插入等待”的新自由度。

### 7. 最小官方验证与停用条件

先固定同一个 plan，比较原版 E0 与“官方编译结果＋消元评分”，不要同时改候选与评估器。

输入族应包括长计算链、M/V 菱形、内存复用、高扇出接口、同刻 COPY 完成与缓存查询、受阻队首。检查全部保留事件时刻，而不只检查最终 makespan。

**出现任一保留事件差异，就推翻对应守卫；接口填充或重编译成本抵消了节省，就停用。** 完整时间线可用内部见证重建，但未实现重建时只能声称内部评分等价，不能声称 full JSON 等价。

## 四、机制二：用合法分区语法构造方案，再在闭合特例中消去指数搜索

这条机制直接回答“怎样构造更好的候选”，而不只是加速评分。

### 1. 精确结构：无环商图等价于某个分块拓扑词

**命题：一个分区的商图无环，当且仅当原逻辑 DAG 存在一个拓扑序，使每个分区块占据连续区间。**

证明：

商图无环时，先拓扑排列各块，再在块内拓扑排列算子，拼起来即可。反向则由各区间先后次序给每条商图边一个严格递增的块序号，不可能形成环。

这给出合法候选语法：

$$\boxed{\text{拓扑词}+\text{区间切点}}$$

而不是任意给每个算子贴子图标签再大量碰撞非法方案。

Moreira–Popp–Schulz 的无环图分区论文也使用拓扑顺序与连续块构造；但其 cut/balance 目标不等于本题 makespan，所以这里只继承合法性机制，不继承目标函数。[[图片：]arXiv](https://arxiv.org/pdf/1704.00705)

**固定一个拓扑词只是一个受限子族。** 不能因为该子族容易求解，就声称所有优质分区都在其中。

### 2. “每个块都序凸”还不够

考虑原图仅有

$$a\to b,\qquad c\to d,$$

分组为

$$A=\{a,d\},\qquad B=\{b,c\}.$$

两个块分别都是序凸的，但商图出现

$$A\to B\to A.$$

所以不能为每个块独立发一个“凸性合格证”，就认为全部块组合一定合法。

更适合实现的规则是：

> **在当前无环商图上合并集合 $S$ 安全，当且仅当不存在“从 $S$ 出发，经外部节点，再返回 $S$”的路径。**

收缩后新出现的环必须经过新节点；展开这个环，正好得到上述离开—返回路径，反向同理。

从所有出界邻居进行一次外部 DFS 即可检查，成本 $O(|Q|+|E_Q|)$。**检查对象必须是当前商图，不是原图上的一次性旧证书。**

### 3. 核序也用同一个全局词生成，但仍检查展开图

把每核子图序列取为同一全局块拓扑序在该核上的限制，能够保证“商图依赖＋核内子图顺序”无环。

这只是约束合法提交序列，**不是往官方执行图中增加原本不存在的串行等待**。官方生成的 COPY、内存依赖和 Pipe 顺序仍须检查。

例如依赖 $A\to B,C\to D$，core0 排 $[B,C]$，core1 排 $[D,A]$，加入核序关系后会形成

$$A\to B\to C\to D\to A.$$

这是一个适合验证多层合法性差异的结构探针；本次没有把它声称为已成功运行的官方输入。

### 4. Q1 的精确特例：闭合 Task 分段

这里有一个真正的指数到多项式降维，但必须先写清条件。

固定拓扑词。假设所有 Task 在一个核上依次运行，没有其他核同时争用资源；Task 之间没有影响后续执行的缓存或其他持久动态状态；相邻 Task 只有固定等待 $w$。

更关键的是：

$$d(i,j)=\text{区间 }(i,j]\text{ 的准确局部执行时间}$$

必须只依赖这个区间及固定边界契约，**不依赖外围如何切分、生成 ID 的比较变化等上下文**。

Q1 是最值得验证这个条件的地方，但目前不能当作已经成立。

条件成立后，对于切点

$$0=i_0<i_1<\cdots<i_k=n,$$

有准确成本

$$T=\sum_{r=1}^{k}d(i_{r-1},i_r)+(k-1)w.$$

于是得到 min-plus 最短路：

$$\boxed{
F[0]=0,\qquad
F[j]=\min_{i<j}
\bigl\{F[i]+d(i,j)+w\mathbf1_{i>0}\bigr\}.
}$$

最后一段可以从前缀中剥离，成本可加，因此有最优子结构。内部 Task 即使包含复杂 spill，也不妨碍这个证明——前提是 $d(i,j)$ 真正准确且闭合。

固定词原本有 $2^{n-1}$ 种切分。限制区间最长为 $L$ 时，DP 为 $O(nL)$，回溯为 $O(n)$；但局部画像成本是

$$O(nL\,c_{\rm profile}),$$

**这个成本不能从复杂度和计时里消失。**

只有 E0 时，可先选少量候选切点或宏块，限制画像数 $M$，只在这个区间边集上精确求解。若画像过贵，就缩小范围，不用未经验证的估计值填成“精确局部成本”。

恢复切点后，直接给区间赋子图号，构造 `node_to_subgraph` 和单核 `core_schedules`，再用 E0 检查完整方案。

### 5. 一般多核怎么办？

闭合条件失效时，分段 DP 只能作候选生成代理。一般构造器保留以下主循环：

```
从少量不同结构优先级产生拓扑词和合法初始分区
保留一个已通过 E0 的 incumbent

预算允许时:
    根据执行见证选择小编辑区域
    提议 split / 安全 merge / core move / 可调核序变化
    检查映射覆盖、商图和核序
    官方兼容编译，检查展开图
    对语义完整的编译结果去重
    仅用已证明下界做硬剪枝
    E0 或已通过验收的 E1 评分
    只用官方确认的合法改进更新最终 incumbent
```

这里的编辑区域应由明确机制给出，例如关键同步边、源端 MTE3 扇出、内存复用导致的串行链，而不是将“搬运少”直接等价为“更快”。成员阅读包已有相同切图与搬运统计、仅核心归属不同而 makespan 不同的微图报告；它支持的正是这种不充分性，而非某个代理必然可用。

01_形式化阅读包

### 6. 从失败环学习，而不是盲目修复

若展开图报出一个环 $C$，给每条边附上来源，并找到保证该边存在的充分条件 $g_e(P)$，则

$$\boxed{\bigvee_{e\in C}\neg g_e(P)}$$

是一条安全禁配约束：所有条件同时成立时，环仍存在。

难点在于生成的 FIFO/内存边可能依赖远处 ID 和编译变化。因此：

**没有证明充分守卫时，只缓存这个确切失败计划，不把两个子图号推广成永久禁配。**

修复是改变产生边的合法决策，而不是删除官方数据或内存依赖。`egglog` 可管理已证明的事实和守卫；其半朴素增量推理结果不自动涵盖计划编辑引起的事实删除，失效范围仍需单独处理。[[图片：]arXiv](https://arxiv.org/pdf/2304.04332)

### 7. 下界与最优值的范围

在原始计算时长不变、每核每 Pipe 单槽等条件核对后，可用基础下界

$$LB_0=
\max\left\{
\operatorname{CP}_{D}(d),
\max_p\frac{\sum_{v:\operatorname{pipe}(v)=p}d_v}{K}
\right\}.$$

前者只保留必须执行的计算依赖链；后者是每类 Pipe 的固定工作量下界。

对已固定且成功编译的候选，可给操作赋不大于真实时长的乐观值，再计算展开图最长路。Q3 可以乐观地允许缓存读取走最快路径，作为放松，但必须核对时长口径。

**受限分段 DP 的最优值不是原问题下界。** 它产生的合法方案经过 E0 后，是原问题的一个上界候选。一般的 bytes/bandwidth 物理下界，在没有审计官方 duration、实际搬运和取整语义之前，也不应直接用于硬剪枝。

## 五、机制三：面向未来的 FIFO 状态商

这是本轮最有辨识度的状态压缩结果。

### 1. 从“缓存里有什么”改成“未来还能区分什么”

固定剩余编译程序，令 $L$ 包含所有未来可能**查询或插入**的 logical key。

特别要包含已发射 miss、尚未完成插入的 key。只有不在 $L$ 中的 resident key 才称为死键。

成员材料报告的规则是：FIFO 命中不晋升，已有 key 插入幂等，miss 完成时才插入，超大条目不缓存。下面的定理针对这个缓存自动机；与完整官方运行器的连接仍待源码与 E0 验证。

01_形式化阅读包

### 2. 一个可执行的规范化

对从老到新的队列 $S$，定义 $N_L(S)$：

**删除死前缀；保留活键的身份、大小和次序；将其余连续死条目合为一个记录总字节数的 gap。**

例如：

```
[dead(4), a(2), dead(3), dead(5), b(1), dead(7)]
                  ↓
[a(2), gap(8), b(1), gap(7)]
```

若有 $h$ 个未来相关的驻留活键，只需保留至多 $h$ 个活条目和 $h$ 个 gap，即 $O(h)$ 表示。

**最有用的特例：真实缓存可以仍然装满，但如果全部旧条目对未来都已死，那么它在评分状态中等价于空缓存。** 这不是允许提交 flush，而是求解器内部的观察等价。

### 3. 右同余命题

令 $\delta(S,a)$ 是一个键来自 $L$ 的 FIFO 查询或插入动作。容量固定、查询不晋升，插入遵循上述规则，则

$$\boxed{
N_L(\delta(S,a))
=
N_L(\delta(N_L(S),a)).
}$$

两边查询的 hit/miss 也相同。因此规范形相同的状态，对任意允许的未来动作词产生相同的命中序列。

**证明要点：**

查询只看活键是否存在，规范化没有改变。

插入新键时，FIFO 只淘汰前缀。队首死字节与空闲字节，对“是否必须继续淘汰下一个活键”具有相同作用。若原始执行停在一段死条目中途，剩余部分在规范化时又会被作为死前缀删除。因此内部死段只需保留总字节；两边留下相同的活键序列与后续 gap。

已有活键插入和超大条目跳过，两边也一致。对未来动作词长度归纳即可。

这给出一个**充分的行为商**，没有宣称它一定是最小自动机。

### 4. 两个最小反例限定了规则

**不能直接删掉内部死条目。**

容量为 2，状态为

$$[a(1),x_{\rm dead}(1)].$$

插入 $b(1)$，真正的 FIFO 淘汰 $a$；若先删除 $x$，则 $a$ 留下。后续访问 $a$ 的结果相反。

**不能只按“未来没有读取”判死。**

容量仍为 2，状态为 $[a(1),x(1)]$。虽然以后不再查询 $x$，但存在一次 pending insert(x)。真实插入是幂等的，不淘汰 $a$；若先把 $x$ 匿名化，它可能被当作新插入，错误淘汰 $a$。

所以未来字母表必须包括 **pending insert 与 logical alias**。阅读包只验证了 spill 重命名的 key 一致性，并未观察到 Q3 命中后果；这个数学定理不能替它补造端到端结果。

01_形式化阅读包

### 5. 实现与复杂度

可用双向链表交替存活条目和 gap，哈希表定位活键。

一个键的“剩余可能查询数＋待插入数”归零后，将其匿名化、合并相邻 gap、删除死前缀。未来计数必须来自已编译程序的保守分析，而不是某一次预测时间线。

链表增删和邻接合并为常数操作；逐条淘汰可以摊销计数。状态序列化与核验为 $O(h)$。如果每次都从头扫描完整缓存重新规范化，可能反而更慢。

**这首先是评分等价，不是 full JSON 等价。** 死键 ID、实际 used_bytes、evicted IDs、真实 final_entries 被隐藏了。完整诊断需要保留见证或按精确事件流重放原 FIFO，也可以整份回退 E0/E1。不能把压缩后的容量字段冒充官方结果。团队补充规范对此明确禁止伪造或混拼诊断。

### 6. 为什么不存在通用的小常数摘要？

若缓存容量为 $h$，里面 $h$ 个单位键全部可能再次使用，允许继续插入新键，那么不同 FIFO 排列可以被未来查询区分。

对两个不同排列，找到一个前缀长度，使它们的前缀集合不同；插入相应数量的新键，再查询前缀对称差中的旧键，命中结果就不同。

所以在允许这些未来动作的缓存自动机上，最坏存在至少 $h!$ 个可区分顺序状态。

这不是说每张正式图都会达到这个下界，而是说明：**总字节、驻留集合或命中率不可能成为通用精确状态。** 本文真正利用的是“未来相关键少”，不是假设 FIFO 天生低维。

### 7. 等分服务也可以换坐标，但不能立即叫作 E1

把请求工作量按独占服务单位表示，定义虚拟服务时钟：

$$V(t)=\int_0^t
\frac{\mathbf1_{N(s)>0}}{N(s)}\,ds.$$

请求 $i$ 在 $a_i$ 到达，工作量 $w_i$，存标签

$$f_i=V(a_i)+w_i.$$

其剩余工作量为 $f_i-V(t)$。没有新到达时，下一个连续完成时刻是

$$t+N(t)\bigl(\min_i f_i-V(t)\bigr).$$

因此，只维护一个时钟和标签最小堆，就不必在每次到达时改写全部在飞请求。Demers–Keshav–Shenker 的原文 §2.2 给出了 round number 与 finishing tag 的相关构造；这里只借用流体参考过程，**不把官方 processor-sharing 换成分组公平排队**。[[图片：]Stanford University](https://web.stanford.edu/class/cs244/papers/demers-queueing.pdf)

连续精确模型中，$m$ 个请求、最大并发 $a$，可做到

$$O(m\log a)$$

时间、$O(a)$ 状态。

但官方报告使用 float 剩余量、`ceil(cursor - 1e-9)` 和整数事件时刻。逐次减法与“标签减累计时钟”可能浮点不同；末尾统一 ceil 也不等价于逐事件整数退休。因此这条路径目前只能称为**流体模型精确、官方语义待验证**。

01_形式化阅读包

而且，如果完整日志要求每次到达都列出全部在飞请求的 projected_ends，输出规模本身就可能是 $\Omega(ma)$。不能用内部评分速度冒充完整 CLI 同倍加速。

### 8. 局部修改的正确失效范围

缓存规范形相同还不够。复用后缀需要同时满足：

$$\text{剩余编译程序、Pipe/门控、在飞工作、规范缓存、同刻控制}$$

全部一致。

编辑一个子图后，首先比较**重新编译结果的最早差异**，不是从那个子图原来的开始时刻重放。生成 ID、Step1、spill 和内存边可能使更早内容变化。随后传播范围包含数据依赖、Pipe、共享池重叠忙期和缓存淘汰，直到整个规范状态重新一致。

**最坏情况就是全局重跑。** 本路线提供安全停止条件，不承诺“只重算两个核”。这也符合成员材料对全局失效范围的警告。

## 六、抽象代数、低秩和张量方法的取舍

### 半环有用，但各司其职

| 工具 | 适用对象 | 不应越界到哪里 |
| --- | --- | --- |
| Boolean 半环 | 依赖、可达性、商图 | 不能表达时间与缓存 |
| max-plus | 固定事件的最早时刻 | 不能直接吞掉动态争用 |
| min-plus | 闭合候选的选择与组合 | 一般并发模块代价不可直接相加 |
| 偏序理想集 | 依赖意义下的合法完成前缀 | 不是完整资源状态 |
| 部分交换/并发迹 | 有严格独立守卫的动作 | 原图无依赖不代表资源独立 |
| 状态商 | 未来观察不能区分的历史 | 不能忽略 pending、ID 和有序缓存 |

Flanagan–Godefroid 的 DPOR 要求动作交换保持使能性、且两种顺序得到相同状态。这个要求比“两个算子没有数据边”强得多。官方事件过程本身固定，DPOR 更适合减少语义对抗测试的冗余，而不是再去搜索官方不允许的任意执行交错。[[图片：]UCSC Users](https://users.soe.ucsc.edu/~cormac/papers/popl05.pdf)

### 普通低秩不是这里的关键条件

若所有接口路径都经过 $r$ 个完整连接端口，可以得到

$$H=U\otimes V,$$

这是 max-plus 因子分解，成本从 $b_{\rm in}b_{\rm out}$ 降为

$r(b_{\rm in}+b_{\rm out})$。旁路必须全部计入。

但稀疏 DAG 不保证低秩。$b$ 条互不相连的输入输出链产生“对角有限、非对角 $-\infty$”的接口矩阵。一个 max-plus rank-one 因子若覆盖两个有限对角项，就会产生错误的有限交叉项，因此至少需要 $b$ 个这样的因子。

**重复分块反而可能比低秩更实用。** 对

$$\operatorname{diag}(H,\ldots,H),$$

可以只存一份系数 $H$，保留每个实例独立的端口、时刻和状态。这种块 Kronecker 表示可以是高秩的，却适合共享系数的 CPU SIMD/GPU 批处理；它没有把不同分支错误地归并成一个状态。

### 张量网络暂不应列入主线

Markov–Shi 将张量收缩复杂度联系到线图树宽。其低成本成立依赖相应宽度和局部维度条件，而不是仅凭原图稀疏。[[图片：]arXiv](https://arxiv.org/pdf/quant-ph/0511069)

本题共享带宽与 FIFO 可以形成全局因子。若用状态变量拆开这些因子，代价又进入状态域；缓存顺序可能仍然巨大。因此，除非实际测得小作用域和小状态域，否则不建议构造巨大张量再截断近似。

原文中某些“rank”指张量索引个数，也不能与普通矩阵 SVD 秩混用。这里的建模张量，更不能与题目中搬运的数据 Tensor 混为一谈。

## 八、CUDA、Apple M5 与 CPU 的共同设计

### 1. 不能从“游戏本”推断实际 GPU

已知的是三台游戏本与一台 Mac；实际 GPU、显存、功耗配置、CPU、系统与驱动，以及 M5 的具体型号和配置，本次均未检测。

官方 2026 年资料确认了 M5 Pro/Max 产品，以及 M5-series 对应 Apple10、支持 Metal 3/4 等能力。但这些是产品/SDK 信息，不是本队机器检测结果。[[图片：]Apple+1](https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/)

Apple 的 MPP 指南介绍了 Metal 4 tensor API、M5 GPU neural accelerator 与标准 GEMM；**标准乘加不是 max-plus 运算，不能因为写出了矩阵公式，就声称能直接使用这些矩阵加速器。**[[图片：]Apple Developer](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)

### 2. 最值得 GPU 化的是压缩后的规则内核，不是完整事件循环

| 计算部分 | 首选实现判断 |
| --- | --- |
| 相同 $H$ 对许多候选或重复模块的 max-plus matvec | 最值得测试 CUDA/Metal |
| 固定 DAG 的分层整数时间松弛 | 层宽足够时可测；深窄链不一定划算 |
| 小商图 bitset 检查 | CPU SIMD 是强竞争基线 |
| 区间 DP | 通常先 CPU；外层存在前缀依赖 |
| 单候选的事件堆、动态 FIFO、精细共享池 | 先 CPU |
| 完整 JSON/Trace | CPU；输出规模不能由张量核心消除 |

CPU 基线应使用 SoA、CSR、紧凑整数索引、缓存友好的短数组，以及独立候选之间的多核并行。不能把 Python 对象实现作为唯一 CPU 基线，再把全部改写收益归给 GPU。

GPU 可采用 `[port_or_event][candidate]` 布局，使相邻 lane 处理相邻候选的同类状态；相同 $H$ 的系数常驻共享，实例状态分开。不同编译骨架先分桶，桶形成和 padding 也计时。

这与 NVIDIA 官方文档对合并访存、减少传输、批量小传输的建议一致；但具体盈亏仍由本题内核实测决定。[[图片：]NVIDIA Docs+1](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

### 3. 盈亏点必须看端到端

设 CPU 有效并行度为 $p$，每个新候选成本为 $c_C$，GPU 每候选成本为 $c_G$，共享开销 $A$ 包含加载、打包、启动、传输、同步和回退：

$$T_C(B)\approx Bc_C/p,
\qquad
T_G(B)\approx A+Bc_G.$$

只有当 $c_C/p>c_G$ 时，才存在

$$B>\frac{A}{c_C/p-c_G}$$

这样的 GPU 盈亏点。

所有变量都要测。统一内存不代表打包和同步为零；开发期巨量 batch 的吞吐也不是最终单例速度。

若只能加速整条程序的 10%，即使该部分提速 10 倍，整体理论上限也约为 1.10 倍。这是代数算例，不是本队成绩。NVIDIA 官方 strong-scaling 文档同样强调这一限制。[[图片：]NVIDIA Docs](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

### 4. 精度与 CPU 回退

固定时长尽量使用带溢出检查的 int64；$-\infty$ 哨兵不能参与溢出。并列 witness 用固定 ID/序号，不由线程竞态决定。

动态带宽内核则需要镜像官方浮点与退休规则。CUDA 的浮点运算次序、FMA 等可能产生差异；禁用 fast-math 不等于已经满足 E1。[[图片：]NVIDIA Docs](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

本次没有成功读取当前完整 MSL 语言规格的 double 支持契约，所以不对 Apple GPU 的 FP64 细节作未经核实的承诺。**Metal 首先承担整数固定时序子问题，E1 动态资源部分先留 CPU。**

批量不足、接口太碎、守卫失败、设备不支持或端到端不降时，默认回退 CPU。GPU 应由测量决定是否开启，而不是成为论文必须出现的装饰。

## 九、官方实验应该怎样判定成功或否定

### 三条路线各自最小的判别实验

| 路线 | 输入族与对照 | 核心观测 | 否定条件 |

$$T_{\rm prepare}+T_{\rm construct}
+\sum T_{\rm compile+evaluate}
+T_{\rm final}
\le 5\text{–}10\text{ 分钟}.$$

最后一次官方完整确认要预留时间；未经确认的新候选不能覆盖旧的合法 incumbent。

$$\boxed{

\end{aligned}

## 二、真实源码推翻或收紧了哪些旧假设

### 1. 普通计算事件也会改变浮点结算历史

三个全局模拟器的 `retire` 都会调用共享池的剩余工作结算，并非只有搬运加入或退出时才结算。问题3是在每次 `retire` 中遍历两个带宽池进行结算。:chatgpt-content-reference{index="3"} :chatgpt-content-reference{index="4"}

因此，哪怕某个完成事件只是普通计算，它也可能使一次浮点减法拆成多次：

\[
\operatorname{fl}\!\left(
\operatorname{fl}(r-\Delta_1/n)-\Delta_2/n
\right)
\ne
\operatorname{fl}\!\left(r-(\Delta_1+\Delta_2)/n\right).
\tag{T3-201}
\]

随后 `ceil` 与容差会把微小差异变成整数时间差。

我构造了一个四核、全部使用正常 DDR 输入的二部图：前三条链有较大的 L1 输入搬运，第四条链有连续的单周期计算。错误变体只合并“普通计算完成导致的带宽结算”，没有更改固定配置。

| 第四条链的短计算数量 | 官方 E0 | 合并结算变体 | 完整结果 |
|---:|---:|---:|---|
| 64 | 24006 | 24006 | 一致 |
| 512 | 24006 | 24006 | 一致 |
| 1024 | 24006 | 24006 | 一致 |
| **2048** | **24007** | **24006** | **不一致** |

这是一个有界反例，**没有声称它最小**。之后又用新的 E0 调用与 S 比较，S 完整保留了 24007 的官方结果。

较早的常量根版本产生过 24006／24005；两份输入分别保留。上表使用的是每条链都有 DDR 输入的更严格版本，并不是把前一组数值改写了。

**结论：撤回通用的“消去纯计算退休事件即可构成 E1”判断。** Max-plus 在固定整数计算区域仍然有价值，但只有保留所有可观察的浮点结算点，或者证明该区域内相关共享池始终为空等更强条件，才可能继续构造精确快路径。

证据见包内 `results/counterexamples/float_epochs_with_input/`。

### 2. FIFO 队首不能越过：现在有源码与真实输入双重证据

全局 `queue_if_ready` 明确检查当前操作是否为 `order[cursor]`；不是队首就直接返回。等待跨核输入的队首会阻挡后续本来可以工作的操作。:chatgpt-content-reference{index="5"}

这给了我们一个合法优化手段：**改变提交的子图顺序，让官方自己生成更好的 FIFO**，而不是让替代模拟器擅自绕过队首。后文给出实际改善 32.24% 的微图。

### 3. FIFO 的“未来相关键”必须包括在飞 hit

源码在每个 COPY_IN 完成时调用 `insert_cache`，没有要求“该次访问必须是 miss”。:chatgpt-content-reference{index="6"}

本轮构造出了完整官方路径：

| 时刻 | 事件 |
|---:|---|
| 20001 | A 插入缓存 |
| 21669 | 另一核命中 A，开始读取 |
| 22169 | C 插入，淘汰仍在读取中的 A |
| 23269 | 对 A 的 hit 完成，**重新插入 A** |

“只在 miss 完成时插入”的错误实现，最终 FIFO 内容不同。**本例两种实现的 Makespan 都是 23271，但完整输出不同。**

所以，上轮缓存状态商需要再补一条条件：未来键集合必须包含所有未完成 COPY_IN 的潜在完成插入，**包括 hit**。原来的“活键次序＋死字节间隙”不是被这个例子整体否定，但它不能直接用于完整输出等价，更没有在本轮证明端到端性能收益。现在应降低它的工程优先级。

## 三、最值得作为第三路数学主线的机制：完整操作序列的精确商

下面把**包含官方生成 COPY 的完整算子 ID 序列**简称为“增广词”。它不是自然语言，也不对 ID 做重命名。

### 1. 一个重要发现：问题2／3的切分，部分只是编译顺序的表示

在问题2／3中，固定以下内容：

**原图、配置、问题编号、核数、逐算子的核心归属、mapping 的迭代顺序，以及官方版本和运行环境。**

此时，官方原始每核 Task 图中的算子、张量、跨核 COPY 数量、字面 ID 和边顺序保持不变。不同子图划分主要通过标签与稳定分桶，影响送入 Step2 的顺序。

官方将生成的 COPY_IN 归入该核最早的消费子图，将 COPY_OUT 归入最晚的生产子图；“最早／最晚”按核内顺序，而非子图编号大小。然后按子图顺序稳定排序，桶内保留原始 Step1 顺序。:chatgpt-content-reference{index="7"} :chatgpt-content-reference{index="8"}

设原始 Step1 序列为 \(\rho_c\)，操作子图标签为 \(\lambda\)，则实际送入后续编译过程的是：

\[
W_c(P)=
\operatorname{stable\_sort}_{\operatorname{rank}_{\sigma_c}(\lambda)}
(\rho_c).
\tag{T3-202}
\]

### 2. 精确等价命题

**在上述固定上下文中，若两个合法方案的每核完整增广词相同，它们的操作性编译结果与全局资源过程相同。**

证明链条是：

固定逐算子核心归属，使原始 Task 图和边界 COPY 相同；完整增广词相同，使 Step2 接收到完全相同的图和序列；于是 spill、重命名、Step3 内存边和 Pipe FIFO 都相同。全局模拟接收到同一个操作程序，逐事件使用相同顺序、相同浮点操作数，因此不是“实数结果差不多”，而是**不改变浮点程序本身**。

这里有一个输出层区别：两个方案的子图编号和子图时间跨度可能不同，所以**不能直接复制整份旧 JSON**。原型会按新方案重新生成子图标签、子图时间跨度和 Task 中的子图列表；spill 标签也按官方前后使用点的规则继承。

这也是它和普通的“图同构缓存”不同的地方：**不删除原始 ID，不交换核心，不忽略 COPY，不用近似分数。**

### 3. 抽象代数真正发挥作用的位置：单调合并与 min/max 交换

把同核相邻子图合并，等于对原来的子图顺序链施加一个单调映射 \(f\)。在链上：

\[
f(\min S)=\min f(S),
\qquad
f(\max S)=\max f(S).
\tag{T3-203}
\]

这恰好对应 COPY_IN／COPY_OUT 的标签规则。因此，合并后的 COPY 标签就是原标签的映射，不需要猜测。

但这还不够：合并可能改变稳定排序结果。令 \(r(o)\) 表示操作在原始 Step1 序列中的位置。相邻两个桶 \(A,B\) 满足：

\[
\max_{o\in A}r(o)<\min_{o\in B}r(o)
\tag{T3-204}
\]

时，合并后桶内按原始位置排序，仍得到原来的串接顺序。于是可执行规则是：

> **只合并增广词边界两侧原始位置仍递增的相邻桶；随后重新检查商图合法性与完整字面序列相等。**

不同核心上的同时粗化仍可能让商图成环，所以不能省去全局检查。

### 4. 还能得到“最少子图表示”的证书

任何稳定分桶内部，原始位置都必须递增。因此，完整增广词中的每个下降点，都强迫保留一个切点：

\[
m_c\ge
1+\#\left\{
i:r(W_{c,i+1})<r(W_{c,i})
\right\},
\qquad W_c\ne\varnothing.
\tag{T3-205}
\]

若合并所有可合并相邻桶之后仍满足全局合法性，就达到这个完整词的桶数下界。

**这是“同一个官方行为的最短表示”证书，不是原问题 Makespan 最优性证书。**

本轮 case_097／问题3的测试，从按原始核内顺序构造的 6592 个单算子子图压至 4 个子图，官方结果保持：

| 指标 | 粗化前后 |
|---|---:|
| Makespan | 2626908 |
| 调度 COPY 字节 | 19267584 |
| spill 新增字节 | 6553600 |

这是一个含真实 spill 的例子。它证明该等价关系不只适用于没有内存压力的玩具图，但**不证明任意 6592 子图方案都可以如此粗化**。

### 5. 原型与复杂度收益

`word_quotient.py` 与 `canonical_plan.py` 已实现：

```text
建立固定核心映射上下文：
    保存原始 Task 图、生成 COPY 的字面 ID、原始 Step1 序列
    保存各 COPY 的最早消费者／最晚生产者标签锚点

评价新方案：
    通过官方方案校验，确认上下文未改变
    生成完整增广词

    若完整词已见过：复用相同操作程序的结果

粗化：
    合并满足原始位置递增条件的相邻桶
```

每个新方案仍需校验、计算标签和稳定分桶。完整输出命中后，重新标注操作与子图仍有线性成本；不是常数时间“免费返回”。缓存空间也随唯一完整词的数量增长，当前研究原型还没有 LRU 上限。

真正减少的是：**多个不同切分方案对应同一完整词时，昂贵的 spill、Step3 和全局模拟只做一次。**

在 case_080／问题3上，使用八个不同 JSON 方案，它们是刻意构造的等价细分。每轮重新加载、解析并建立缓存，共五轮；比较完整输出：

### 7. 为什么必须包含 COPY：一个六算子的官方反例

一个分叉图中，A 产生中间数据，供同核 B 和异核 C 使用。只把 A、B 从一个子图拆成顺序两个子图：

- 逐算子核心归属不变；

## 四、S：不动资源语义，也能明显加速

### 1. 实际热点不是十元素带宽池，而是每次重扫大量历史状态

官方问题1的完成处理，每轮为活动 Task 构造完整操作列表，再检查这些操作是否全完成。:chatgpt-content-reference{index="9"}

本轮 case_003 的 profiling 显示，这类完成扫描及其 Python 对象分配占据了显著成本。因此先维护一个不变量：

\[
u_t
=
|O_t|-
\#\{o\in O_t:\operatorname{status}(o)=\mathrm{done}\},
\qquad
u_t=0
\iff
\text{Task }t\text{全部完成}.
\tag{T3-206}
\]

初始计数为操作总数；每个操作唯一一次完成时减一。原有状态仍保留，用于其他依赖查询。

**这不是把计数相同的两个全局状态视为等价。** 只是把一个反复计算的查询，改成维护其充分统计量。

为保持事件顺序，活动 Task 仍按原来的 Task ID 顺序检查。Step3 的整体完成检查也作同样处理。

### 2. 为什么这避开了浮点陷阱

## 五、构造算法：真实输入中确实存在可用的二维关系，但通信最优仍不等于时间最优

### 1. 从输入关联恢复坐标，而不是先假定低秩

对非 COPY 依赖的弱连通分量作为计算原子，记录每个共享输入被哪些原子消费。严格检测后，100 例中有 **10 例**满足完整的两轴乘积结构：

011、021、027、037、039、058、059、079、080、097。

在这种结构中，共享输入类可分为行类和列类，每个原子对应一个行列交点。关联矩阵的行是共享输入类，列是计算原子：

\[
H=
\begin{bmatrix}
I_R\otimes\mathbf 1_C^\top\\
\mathbf 1_R^\top\otimes I_C
\end{bmatrix}.
\tag{T3-207}
\]

私有输入和全局输入另外保留。**这是关联关系的坐标与分块表示，不是假设全部执行状态低秩。**

完整原子分核时，Task 输入 COPY 字节可以准确计算：

\[
V_{\mathrm{input}}(P)
=
\sum_t s_t
\left|
\{\operatorname{core}(a):a\text{ 消费输入 }t\}
\right|.
\tag{T3-208}
\]

这个量尚未包含 spill 和实际缓存服务路径，不能直接当 Makespan，更不能替代官方搬运统计。

由此产生少量矩形分核候选，再比较行优先、列优先的子图顺序。输入关系检测失败就不走这条特化路径。

### 2. 正式实验已经给出了收益和反例

六个正式用例、问题2／3、四核，共评估了 **80 个候选**，保存每个候选的官方完整结果。

对照是完整计算原子的单次 LPT 负载分核，不是官方随机 stub，也不是团队已知最强解。

| 用例 | 比较 | 官方结果 |
|---|---|---|
| **080／问题2** | 基线 → 2×2 行优先矩形 | **111314 → 107030，改善 3.85%** |
| **080／问题3** | 同一对方案 | **90584 → 106822，恶化 17.93%** |
| **037／问题2、3** | 基线 → 2×2 行优先矩形 | 输入字节减少 7.14%，Makespan 却恶化 19.40% |
| **027／问题2、3** | 相同矩形归属，行优先 → 列优先 | 559196 → 592532；spill 从 0 增至 270336 字节 |
| 011／问题2、3 | 多种划分 | 时间均为 46880，搬运差异没有变成时间收益 |
| 097／问题2、3 | 矩形候选 | 没有胜过基线 |

080／问题3的矩形方案虽然字节命中率下降，但其 `miss_bytes` 也比基线少。所以不能只凭“命中率低了”就把整个性能差异解释完。这里还有负载、操作词、spill 与共享资源时序的共同影响，尚未完成逐因素因果消融。

**矩形构造应保留为低成本候选生成器，不应升级成统一目标函数。**

### 3. 更直接的候选来源：队首阻塞与关键 COPY 导出

在另一个七算子的真实输入中，核心1先排等待跨核输入的 B，后排独立任务 U。只把该核子图顺序从 `[B,U]` 改成 `[U,B]`：

**问题2／3从 15511 降至 10511，改善 32.24%；搬运量不变。**

这不是让执行器越过 FIFO，而是改变合法方案，使官方产生不同的 FIFO。

结合前面的导出分叉反例，我现在更看好下一步的构造规则：

> 从官方执行见证找到“关键 COPY 被同桶计算拖后”或“跨核队首挡住独立后项”，只尝试少量能改变增广词的 split／顺序调整，再由官方确认。

微图生成器已实现；**通用的自动 trace 修复优化器尚未实现**，不能把这两个例子的收益外推为正式 100 例平均收益。

## 六、为什么当前优先 CPU，而不是马上上 CUDA／Metal

真实语义给出一个很有用的规模界：正式输入与官方生成的 COPY 使用 MTE2／MTE3，每条 Pipe 单槽。于是：

\[
N_{\mathrm{DDR}}\le 2K\le10,
\qquad
N_{\mathrm{CACHE\_READ}}\le K\le5.
\tag{T3-209}
\]

四条 Pipe 及单槽约束直接来自冻结源码。:chatgpt-content-reference{index="10"}

**数万算子的图，不代表动态带宽池里有数万个活跃请求。** 为最多十个请求引入复杂 GPU 堆或浮点虚拟时钟，优先级低于消除每个事件扫描数万历史状态的开销。

本轮没有 GPU、Mac 或 Windows 测试。实际环境是 Python 3.13.5、Linux x86_64、AMD EPYC 宿主、容器暴露五个逻辑 CPU；性能测量使用单 Python 线程。

我核对了当前 NVIDIA 官方 CUDA Best Practices Guide 中的数据传输成本、浮点不结合与 FMA 说明；这些同样要求不能把“数学等价”当成相同浮点输出。:chatgpt-content-reference{index="11"} Apple 的 WWDC26 Metal tensors 材料主要讨论矩阵乘法、卷积与 M5 neural accelerator；它并不意味着本题的 max-plus 或逐次 binary64 服务结算可以直接映射到矩阵加速器。:chatgpt-content-reference{index="12"}

可继续测试的 GPU 工作是**大批固定结构的整数特征、标签或分层图操作**。完整事件堆、FIFO 与小带宽池仍先留 CPU；准备、打包、传输、同步、回退全部计入。数学压缩使剩余问题变小后，GPU 的启动成本反而可能更难摊薄。

# 六、物理 ID、logical_tid、version、backing、内存复用各自扮演什么角色

这次勘误后，建议中间层把这几个概念彻底拆开：

| 对象 | 正确角色 | 不能做的简化 |
|---|---|---|
| **logical_tid** | 同一逻辑数据跨 incarnation 的稳定身份；也是 Q3 Cache key 的基础 | 不能拿 physical tid 替代 |
| **physical tid / incarnation tid** | 当前实际扩展图里的 tensor 节点身份，数据边和内存生命周期围绕它建立 | 不能因为 logical_tid 相同就把多个 incarnation 合成一个 tensor 节点 |
| **version** | 同一 logical tensor 每次 reload 后递增的 incarnation 序号 | 不能当布尔变量，也不能恒写 1 |
| **backing_tid** | 当前 logical tensor 在 DDR 中可复用的持久副本 | 不能假设每次 spill 都新建 |
| **spill_out_copies_data** | 决定本次 eviction 是否真的要写 DDR，是搬运成本与 MTE3 行为的关键分支 | 不能固定为 true |
| **pos** | 新 incarnation 恢复到原 `sp['pos']`，可 L1 或 UB | 不能统一写 UB |
| **Step3 MEMORY_REUSE 边** | 由物理 incarnation 的生命周期、容量额度和消费者/生产者关系形成执行依赖 | 不能仅靠 logical_tid 判断，也不能因为 backing 已存在就忽略 |

题面也强调：Step2 会更新 tensor 引用和空间复用依赖，Step3 再基于这些扩展结果排布。:chatgpt-content-reference{index="20"}

这意味着：

# 八、这三个错误有没有导致我“排除错误的候选方向”？

这是这次审计里比“已有分数还对不对”更重要的问题。

### F-EXEC-001：目前没有发现已造成搜索偏置

第三路没有实现一个使用错误 `any≤1` 的快速合法性剪枝器；第二轮实际候选最终都交官方 E0。因此**没有找到已经被错误剔除的候选集**。

但以后如果为了 Q1 提速写自有 legality prefilter，这个错误会造成**假合法**，主要不是错杀好解，而是放进本该继续检查的方案，浪费评估预算或导致 E1/E2 与 E0 不一致。

### 24/44：没有发现第三路因此偏向少核

第一轮我已经主动指出旧对照改变了工作量；第二轮也明确采用修正后的同图结论。因此没有找到“因为相信核越多越慢，而系统性少搜多核方案”的实现痕迹。

### F-TASK-006：**这里存在真实的潜在搜索偏置**

如果一个候选生成器把高 spill 风险理解成：

> “每次 spill 都需要写出 + 读回，两倍字节，而且都走 UB”

那么它会**过度惩罚**这样的方案：

- tensor 原本就有 DDR backing；
- 未来需要多次 reload；
- reload 落在 L1；
- 后续 physical incarnation version>1。

这类方案实际只需 COPY_IN 的某些 spill，可能比错误代理估计便宜很多。

反过来，如果错误代理忽略 version/physical incarnation，还可能**低估**内存复用依赖和生命周期复杂度。

所以这里应该标记：

> **已有官方成绩不需要作废；但凡候选筛选、代理代价或剪枝规则曾把 spill 固定成两次 DDR 搬运，都必须重新审。**

我第二轮交付的主要构造——W、结构矩形、E0确认——没有用这个固定两倍规则做硬剪枝；因此没有发现已交付候选池被这一假设直接删减的证据。

# 十、确实值得留到审核后第三轮再深想的 4 个问题

等中间层形式化文档审核稳定后，我认为只有下面四个问题值得真正重新深想。

**1. Q1 的“Task profile”到底最小需要什么状态。**  
原先若想把一个 Task 压成固定局部代价，新的 backing/version 分支说明 Task 成本可能依赖“进入 Task 前有什么持久 DDR backing”这类状态。情况 A 会清私有缓存，但 **DDR backing 并不会因此自动消失**。需要明确哪些 backing 属于 Task 内局部生成，哪些来源于 Task 边界构造，然后才能决定 min-plus DP 的闭合状态维数。

**2. spill-aware 低成本代理是否能做成小状态自动机。**  
现在最自然的最小状态不是“spilled/not spilled”，而至少涉及：

\[
(\text{logical id},\ \text{backing exists/source},\ \text{incarnation version},\ \text{pos}).
\tag{T3-213}
\]

但 version 本身未必需要进入代价状态，只可能作为物理 ID/输出诊断状态。这要等中间层明确哪些字段实际反馈到未来决策后再做状态最小化。

**3. W 是否能从 Q2/Q3 的固定-core specialization 扩展到 Q1。**  
Q1 每个子图一个 Task，切分本身改变边界 COPY 和 100/1000 等待，所以“同 word”远不够。可能存在更大的“Task transducer signature”，但现在不应急着猜。

**4. 搜索是否应该主动利用已有 backing 的 spill。**  
新反例揭示一种以前容易被看作纯损失的结构：如果 DDR 副本已经存在，临时 eviction 的成本可能只有 reload。是否存在“故意保留/制造 backing 以降低未来 spill 成本”的有用构造，需要正式 case 统计才能判断。现在只把它列作研究问题，不立刻升级为算法路线。
