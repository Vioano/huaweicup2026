# Multi-compute bucket direction lemma: source audit

This is a conditional proof review of frozen official code, not an independent official run. I read `schedule_step2.py`, `schedule_step3.py`, the P3 Task builder, [`convex-pilot-cut-20260925/ROOT_REVIEW.md`](../../../../results/a/q3-nikolastarx/convex-pilot-cut-20260925/ROOT_REVIEW.md), and the relevant [`layered_query_flow.py`](../../../../src/q3/layered_query_flow.py). No graph, toy, Task, Step, or evaluator was run for this note.

## Finding

The proposed **nondecreasing bucket direction** for Step3 `MEMORY_REUSE` edges is supported, including multi-compute buckets and zero-byte outputs, under the explicit Task-specific conditions below. The assumptions as worded should be strengthened from “each original compute has an on-chip output” to “in each built Task, every mapped compute operation has at least one *managed* L1/UB output and thus appears in `allocation_order`.” The official builder maps raw DDR locals to UB and supplies on-chip locals for cross-core direct edges, so this can be checked on actual Task output; do not infer it solely from a raw graph annotation. Output size may be zero: membership in `allocation_order` tests presence of a managed output, not positive bytes ([`schedule_step3.py:289`](../../../../data/raw/a/official/code/schedule_step3.py:289)).

Also require: (1) every managed tensor that can supply a free credit in a Task has its real unique on-chip producer, with no unmodeled initially resident tensor; (2) no Step2 spill or renamed incarnation is present for the claim about the *original* bucket mapping; (3) every Task op is either mapped compute, synthetic `COPY_IN`, or synthetic `COPY_OUT`, with COPY_IN assigned the earliest consumer bucket and COPY_OUT the producing compute bucket; (4) the complete prioritized sequence is a valid local topological order; (5) Step3 preparation actually succeeds. The P3 Task code implements the COPY placement ([`multicore_cut_evaluate_problem_3.py:166`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:166), [`:180`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:180), [`:189`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:189), [`:217`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:217)). It creates one per-core source COPY_IN for a raw input and preserves every mapped compute; a static guard should still check the stated properties on each built Task. The older singleton certificate's `all(ports.outputs[u])` is suggestive but does not by itself check a *new multi-op Task* ([`layered_query_flow.py:364`](../../../../src/q3/layered_query_flow.py:364)).

## Why every free-credit edge is nondecreasing

Let `b(x)` be an operation's bucket rank within its core, and `A` the Step3 `allocation_order`, the projection of complete `seq_ext` to operations with any managed output. Step3 allows these operations to issue only in `A` order, even across pipes ([`schedule_step3.py:281`](../../../../data/raw/a/official/code/schedule_step3.py:281), [`:458`](../../../../data/raw/a/official/code/schedule_step3.py:458)). Stable subgraph rebucketing makes `b` nondecreasing along `seq_ext` when there is no spill. Hence if allocation op `x` issues before allocation op `y`, then `b(x) <= b(y)`.

For a newly allocated managed tensor `T`, `consume_free_credit(T, y)` adds an edge from **each source** in a consumed old credit to producer `y` ([`schedule_step3.py:144`](../../../../data/raw/a/official/code/schedule_step3.py:144), [`:158`](../../../../data/raw/a/official/code/schedule_step3.py:158), [`:185`](../../../../data/raw/a/official/code/schedule_step3.py:185)). A credit is created only when its old managed tensor is released after its last consumer completes, or, for a dead output, after its producer completes ([`:202`](../../../../data/raw/a/official/code/schedule_step3.py:202), [`:261`](../../../../data/raw/a/official/code/schedule_step3.py:261), [`:276`](../../../../data/raw/a/official/code/schedule_step3.py:276)). Thus **all** sources, not only the final consumer, have completed before `y` issues. For every source type:

- `WAW`: the old tensor's unique producer is compute or COPY_IN. It belongs to `A`; it must have issued before `y`, so its bucket does not exceed `b(y)`.
- `WAR` compute consumer: the Task premise puts it in `A`; it completed before `y`, so its bucket does not exceed `b(y)`. This remains true for a managed zero-byte output because it is still included in `A`.
- `WAR` COPY_OUT consumer: COPY_OUT need not belong to `A`, but Task assigns it to the bucket of the old tensor's producing compute. That producer is in `A` and precedes `y`, so the COPY_OUT bucket does not exceed `b(y)`. For an input COPY_IN-produced tensor, inspect Task topology/placement rather than presuming a COPY_OUT: under the shown builder, source input with no eligible compute producer does not generate a COPY_OUT.

`VIRGIN` credits have no source, so produce no edge. Split/merged credits only change the number of edges, not the argument; the code iterates *all* `credit['sources']`. The resulting edge may stay **within** one multi-compute bucket, and no claim of strict forward direction inside that bucket follows. This is why local Step3 success is a separate premise. The official Step3 constructs and checks the memory-augmented execution graph ([`schedule_step3.py:583`](../../../../data/raw/a/official/code/schedule_step3.py:583), [`:611`](../../../../data/raw/a/official/code/schedule_step3.py:611)); its successful issue/retire trace also witnesses compatibility with the four actual pipe FIFOs, even if a same-bucket memory edge points backwards in `seq_ext`.

The Step2 closed-interval F<=capacity guard is a sufficient way to exclude spills in its allocate/check/execute/free scan ([`schedule_step2.py:224`](../../../../data/raw/a/official/code/schedule_step2.py:224)), provided intervals are built from **all Task tensor uses in the complete operation sequence**, per pool and incarnation, including generated COPYs. It is not the Step3 runtime peak and does not alone establish Step3 success. Do not reuse the singleton-bucket interval widths for a merged bucket.

## Global union-DAG condition

Form the quotient vertices from the actual proposed subgraphs. Add every original **mapped-compute dependency** (including the compute contraction of tensor and direct edges) and every adjacent bucket edge in each core's submitted schedule. Require this quotient DAG. Then add official Task and Step3 edges. Original local data dependencies and every per-core FIFO edge have nondecreasing bucket direction because the prioritized `seq_ext` is grouped by bucket and topological. The memory edges are nondecreasing by the argument above. Every P3 `cross_link` goes from a source COPY_OUT in the producer's bucket to a destination COPY_IN in the earliest consumer's bucket, and corresponds to one of the included original compute dependencies ([`multicore_cut_evaluate_problem_3.py:189`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:189), [`:217`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:217)). A global directed cycle would either use only same-bucket edges or project to a directed cycle in that quotient. The first case is excluded by successful local Step3 issue/retire execution; the second by the quotient DAG. This composition is valid for arbitrary bucket sizes, not only singleton buckets.

There are two important boundaries. First, a check of direct *same-core* compute arcs alone is insufficient: `a(core0)→b(core1)→c(core0)` creates a quotient cycle when `a,c` are merged, as the [convex-cut review](../../../../results/a/q3-nikolastarx/convex-pilot-cut-20260925/ROOT_REVIEW.md) warns. Check all original edges plus core bucket adjacency. Second, if “original compute DAG” omits a Task cross-link's actual source→destination compute relation (for example by failing to contract an original direct op-op edge), the quotient test is incomplete. A guard should enumerate every Task cross-link and confirm that its bucket pair is a quotient edge or quotient reachability; do not assume names alone establish coverage. None of this is a case-specific official acceptance, runtime-memory certificate, Cache-hit proof, or Makespan estimate.

The coordinator separately reports one frozen static envelope result for a specific convex pilot cut: the uncontracted all-original-op DAG plus five complete core-word adjacency sets is acyclic (4209 vertices/10319 edges), whereas its 201-op contraction has a cyclic quotient (4009 vertices/9859 edges; Kahn visits 165). I did not rerun or independently inspect that calculation here. It means this **sufficient all-word-adjacency criterion** cannot certify that cut. The envelope deliberately adds edges beyond official per-pipe FIFO, so a failed envelope is **not proof that the official candidate is illegal**. Actual Step1/Step3 prepared four-pipe and memory edges would be needed for the weaker instance check.
