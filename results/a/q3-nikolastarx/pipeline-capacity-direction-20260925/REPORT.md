The original `data/raw/a/official/data/case_044.json` has 550 CONV/PIPE_M, 550 RELU/PIPE_V, 264 ADD/PIPE_V, 61 COPY_IN and 11 COPY_OUT operations. The plan's `node_to_subgraph` and `core_schedules` assign the same contiguous position interval of each job to each core. Its intervals contain 21/24/25/27/27 original compute positions per job. The bound gap is `41205-14881=26324` cycles. At least `25412-14881=10531` of that gap is already explained by *this plan's* stage layout and cross-core latency relaxation; the remaining `41205-25412=15793` lies outside that relaxation. These components are not additive at the level of observed pipe events because computation and memory transfers overlap.

The largest visible local bottleneck is core 2, the interval `[45,70)`. The receipt gives `shared_input_bytes_by_stage=[5472,86400,645120,186368,7040]`; core 2's 645,120 B exceeds the frozen 524,288 B L1 capacity (`data/raw/a/official/data/config.txt`) by 120,832 B. Ten original L1 input tensors, IDs `1000000039`–`1000000057` (odd IDs), have sizes 18,432, 36,864, and eight at 73,728 B; each original COPY_IN feeds one position in all 11 jobs (positions 45, 48, 50, 52, 55, 57, 60, 62, 65, 67; consumer IDs differ by 125). The frozen Step2 (`data/raw/a/official/code/schedule_step2.py`) chooses a future-use victim when capacity overflows and inserts a reload from the existing COPY_IN backing for these tensors. The result reports `spill_added_copy_bytes=1585152`, all 24 cache-hit reloads on core 2; `cache_events[]` ties the hits to those input tensor IDs. Thus the extra spill is input reuse pressure, not evidence of new intermediate activation writes.

The saved `per_core_timeline[core_id=2].ops[]` records 18,977 cycles of COPY_IN occupancy: 12,633 DDR and 6,344 CACHE_READ; its PIPE_M occupancy is 15,708 cycles. Every other core has zero CACHE_READ, and its COPY_IN DDR occupancy is 1,044–4,364 cycles. Core 2's first job compute spans 4,410–16,447; subsequent jobs span about 2,100 cycles. Its original shared-input COPY_IN operations are spread from time 0 through 16,283. Core 4 begins at 19,613 and finishes at 41,205. This identifies a slow first wave through core 2 and later repeated input reloads; it does **not** prove that removing 6,344 reload cycles would remove 6,344 from Makespan, because the downstream critical path and DDR contention can change.

**Best next construction:** make the contiguous-stage partition account for each stage's distinct shared-input bytes and L1 margin, alongside per-stage compute load and interstage edges. A concrete static contrast is moving the core-1/core-2 cut from 45 to 53: four weights totaling 202,752 B move left, leaving core 2 with 442,368 B and core 1 with about 289,152 B of shared inputs. That moves 558 compute cycles per job into core 1, so it is only a candidate, not a predicted win. Compare both this cut and moving the core-2/core-3 cut from 70 to 62 (three 73,728 B weights move right, with 485 compute cycles/job) using *one frozen, structure-driven cut rule* and the same end-to-end/evaluator budget. First falsify statically: ensure valid plan and measure stage compute/input capacities and unavoidable crossing. Only a separately authorized official E0 comparison can decide Makespan and latency. A secondary schedule idea is position-major batching within a stage to shorten individual input lifetimes, but it can delay early jobs until upstream work arrives; avoid pursuing it before the cut test or a dependency-aware timing bound.
