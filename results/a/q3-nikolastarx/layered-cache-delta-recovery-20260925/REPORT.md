# Why fewer scheduled COPY bytes did not improve cache gain

This is a read-only comparison of the two saved official 005/K5 traces. The original analysis failed on a Counter/list programming error and is retained in `../layered-cache-delta-20260925/`. Root froze this separate corrected analysis, ran it once in 0.0908 seconds with exit 0, and retained stdout/stderr, claim and hashes. No constructor, Task, Step or evaluator was invoked in either analysis.

Scheduled COPY bytes fell from 2136798 to 1595646, but COPY_IN hit bytes fell from 674612 to 356084 and miss bytes rose from 795322 to 870442. The exact per-key difference reconciles: +397632 bytes over keys with increasing misses and -322512 over keys with decreasing misses, net +75120. Read bytes decrease 243408. There are 179 shared logical keys, 163 old-only and 12 new-only read keys. Each compared key and byte size was checked against the original graph tensor record; generated COPY operation IDs were deliberately not matched across plans.

The leading positive deltas are shared 9216-byte weights. For tensor `1000000048`, the old plan had one miss at cycle 7944, insert at 8176, then four hits. The R9 plan has five misses at 6100, 6136, 6155, 6623 and 6626, all before its first insert at 6735. No event evicts this key in either trace. Thus this key's extra misses are first-fill overlap, not eviction. Tensor `1000001471` similarly has five misses before its first insert at 14075; no eviction of that key is recorded. These two keys each contribute +36864 miss bytes; tensor `1000002894` contributes another +27648.

The original graph declares these tensors as read-only input weights, produced by original COPY_IN nodes and consumed by MATMULs on the five compute cores. For `1000000048`, those consumers are 1289, 1308, 1327, 1346 and 1365, on candidate cores 0–4 respectively. Their requests became clustered before the first load completed. Cache insertion occurs at completion under the frozen official source (`copy_tensor_info`, `insert_cache` and the COPY_IN issue branch); there is no implicit merging of an already in-flight miss in the checked membership rule.

This is evidence for a particular mechanism, not proof that the extra misses cause the full Makespan difference or that delaying followers improves performance. P3 is already 19.97% faster despite the extra misses. A useful next candidate must make the first load ready earlier through legal graph partition/order choices while retaining useful work on other cores; artificial waits, extra COPY operations or invented dependency edges are outside the submission interface. Task grouping and its capacity/FIFO consequences need verification before another official call.

Full per-key counts are in `key-deltas.json`, selected original event histories and recorded evictions in `top-key-events.json`, and source identities/call counts in `summary.json`. The earlier frozen first attempt and this explicitly approved correction are two analysis processes in total, with zero evaluations and no automatic retries.
