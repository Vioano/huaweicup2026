## Rule and observed obstruction

The general structural trial rule (no case-ID branch) was: for each selected repeated-cold input, take the first-missing pilot core; find the genuine compute consumer of its Task COPY_IN; scan backward through that core's singleton schedule to the nearest compute **not** an ancestor of the consumer in the original compute graph; merge that whole consecutive span into its earliest subgraph. The aim was to create a *possible* COPY-before-independent-compute change without inventing an operation or edge. This is an exploratory boundary, **not a necessary condition for earlier COPY issue**: an ancestor-only merge can still change the target COPY's order relative to another COPY in intervening buckets, and the input COPY itself has no compute predecessor. The two trace keys were fixed inputs to this audit, not an online selection rule. A future solver would need to select such keys from graph/cache-independent structure before its evaluation budget, or account for online profiling as solver work.

On the saved R9 plan, both first misses were core 0. For 0048, consumer MATMUL 1289 is at local rank 202, with immediate compute predecessor 1288. The nearest preceding non-ancestor is compute 4073 at rank 23, so the rule merges **180** compute singletons. For 1471, consumer MATMUL 2686 is at rank 395, immediate compute predecessor 2685, and the same rank-23 non-ancestor starts a **373**-singleton span. All earlier compute between rank 24 and either target rank are original ancestors of that target. The source uses a raw reverse DFS Step1 with COPY_IN given lower predecessor-sort key; since these per-core target COPYs have a single relevant consumer and the target has a direct compute predecessor, traversing the target visits that compute predecessor and its ancestors before its COPY ([`schedule_step1.py:104`](/Users/nikolastar/Projects/huaweicup2026/.worktrees/q3-core-nikolastarx/data/raw/a/official/code/schedule_step1.py:104), [`:175`](/Users/nikolastar/Projects/huaweicup2026/.worktrees/q3-core-nikolastarx/data/raw/a/official/code/schedule_step1.py:175)). This explains why merging only the immediately prior ancestor compute does not make the COPY precede that compute *inside the merged bucket*.

The script validated every one of the raw graph's 11187 typed edges, collapsed the graph to 6889 operation arcs, and checked its 4209-operation DAG. It then checked complete singleton compute coverage (4113 ops), mapped 6258 original compute arcs to the one proposed combined quotient, and ran Kahn's test over all resulting subgraphs. The proposed quotient is cyclic: only **482 of 3741** quotient vertices could be removed. Local schedule rank checks alone passed, which demonstrates why they are insufficient. The script therefore deliberately wrote no `STATIC_CANDIDATE_UNVALIDATED.json`. A typical structural failure is `a` on core 0 → `b` on another core → `c` on core 0: merging `a,c` creates a quotient cycle despite both local words being ordered. The JSON count proves this specific proposed quotient has a cycle; it does not identify a minimal cycle witness.

## What remains open

The archived `task_return[*].seq` is already Step1 stable-rebucketed, and `step2[*].seq_ext` is later still. Neither records the original pre-bucket `raw_seq`. Thus the known old local order (0048 COPY at index 300, consumer at 301; 1471 COPY at 543, consumer at 544) cannot determine whether a new merged bucket would place that COPY before or after any **independent** compute or other COPY inside the bucket. The official stable sort preserves raw Step1 order *within* each bucket ([`multicore_cut_evaluate_problem_3.py:51`](/Users/nikolastar/Projects/huaweicup2026/.worktrees/q3-core-nikolastarx/data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:51)). Even a shorter ancestor-only merge might move the target COPY ahead of a different input COPY assigned to an intervening bucket, changing its MTE2 FIFO and issue time without moving it ahead of ancestor compute. This audit did not resolve that possibility and **does not prove all pilot merges impossible**.

Any further candidate must first expose or independently certify the fixed Task's raw Step1 relative ordering of target COPY versus crossed COPYs; check all raw compute edges and the resulting quotient DAG; then prepare once to check zero Step2 spill, L1/UB closed-interval lifetimes, tensor incarnations, Step3 memory edges, four-pipe FIFO plus cross-links DAG, and actual MTE2 queue order. Pulling either 9216-B L1 input earlier extends its lifetime, so old capacity certificates cannot be reused. Finally, an actual P3 trace would have to show each follower sees the key resident when it issues. Equal-time pilot completion can suffice under official retire-before-issue semantics; strict earlier completion is merely a safe sufficient condition. None of these missing checks is supplied by this static result.
