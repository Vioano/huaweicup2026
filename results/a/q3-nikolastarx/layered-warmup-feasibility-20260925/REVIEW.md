# 005/K5 shared-parameter warmup: static feasibility review

Scope: read-only mechanism audit of saved 005 cache-event facts supplied by the coordinator, targeted raw-graph records, frozen official source, and the existing 044 prefix/preload reports. No candidate was built and no Task, Step1–3, E0, P2, or P3 call was made here. The times below are evidence supplied by the coordinator, not independently rerun measurements.

## Verdict

A legal plan can **influence** which genuine core's input COPY_IN is early by assigning and ordering compute subgraphs. It cannot express an extra COPY, sleep, cache prefetch primitive, or cross-core precedence from one parameter read to another. In particular, merely moving follower MATMULs to a later nominal subgraph/bucket does **not** imply that their MTE2 parameter reads wait for the pilot Cache fill. A conditional warmup is plausible only if each follower's actual issue-time Cache membership check sees the pilot's entry. Whether case 005 has enough useful independent work or genuine earlier MTE2 reads to achieve that is unverified.

The saved 005 result is a cold-fill race, on the reported evidence: key `1000000048`, 9216 B, misses at 6100/6136/6155/6623/6626 and first insert at 6735, without an eviction; `1000001471` likewise has five misses before first insert. The old plan reportedly had one 0048 miss at 7944, insert at 8176, then four hits. This comparison establishes the mechanism to target, not an attainable improvement for a new plan. The exact hit condition is that the key is resident when a follower issues. `pilot COPY_IN completion < every follower COPY_IN issue`, with no intervening eviction, is a conservative sufficient condition; equal-time completion may also hit because the official main loop retires completed operations before issuing at that time. For 0048, the earliest observed follower miss at 6136 precedes the first observed insert by 599 cycles; changing only consumer compute start time may leave that COPY issue unchanged.

## What the plan really controls

Official P3 builds one Task per core, strips original raw COPY ops from the compute mapping, and synthesizes **one input COPY_IN per consuming core** for a raw graph input. It places that COPY in the earliest subgraph of that core's eligible consumers: [`multicore_cut_evaluate_problem_3.py:69`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:69), [`:141`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:141), [`:166`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:166). Subgraph priority then stably rebuckets Step1's local raw sequence, preserving order within a bucket and checking local topology ([`:51`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:51)). Thus real consumer mapping/order can move its associated COPY relative to *other COPY_INs on that core*, subject to Step1 and data dependencies. It cannot choose an arbitrary COPY time or force the five cores to reach a common global frontier.

The Cache tests membership at **issue**, and inserts the key only when its COPY_IN completes ([`:493`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:493), [`:523`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:523)). There is no in-flight miss coalescing in these paths. P3 issues by `(core, pipe)` queues, not by waiting for all work in an earlier subgraph bucket across pipes. Therefore an earlier independent M or V operation, or a cross-core gate only on the MATMUL compute, need not hold its input COPY_IN. The relevant gates are an actual predecessor of that COPY_IN, a preceding MTE2 FIFO operation that cannot be bypassed, and any prepared memory dependency. DDR contention and runtime resource scheduling affect whether those gates delay enough.

These two raw inputs are physically L1, each 9216 B: 0048 is produced by original COPY_IN op 26 and 1471 by original COPY_IN op 1423 in [`case_005.json:244`](../../../../data/raw/a/official/data/case_005.json:244) and [`:7359`](../../../../data/raw/a/official/data/case_005.json:7359), with targeted source edges at lines 46969 and 61837. The raw file SHA-256 is `c2b378c882a3039e3d66bac6cbcba39317107339b6f38d5bce1b09379839799f`; the examined official P3 source SHA-256 is `eab1504dead881f4b67c0f0498cbc2dbbd9039dc3c9d198c6af58773c127eeb0`. The official Task makes a DDR backing tensor but retains the local tensor's L1 position, converting only raw `DDR` local tensors to `UB` ([`:111`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:111), [`:152`](../../../../data/raw/a/official/code/multicore_cut_evaluate_problem_3.py:152)). Pulling a COPY_IN earlier may lengthen L1 lifetime and destroy a Step2 no-spill certificate or alter Step3 memory-reuse edges. Recheck each tensor incarnation and its L1 pool, not a combined L1+UB total.

## Minimal timing counterexample and constructive condition

Toy counterexample (reasoning only): two cores consume the same raw L1 parameter `p`. Pilot core has `COPY_IN(p)` on MTE2 at time 0, completing at time 10. Follower has an independent compute op in an earlier subgraph, then the `p` consumer in a later subgraph, but its MTE2 FIFO begins with `COPY_IN(p)`. Because the earlier compute occupies a different pipe and is not a predecessor of the COPY, follower's COPY can issue at time 0; both accesses miss. The nominal bucket order gives no cache guarantee. This is a possible dependency pattern, not a claim about exact official timing under shared DDR.

Conversely, suppose a genuine independent input `q` is needed on the follower and official Task places `COPY_IN(q)` before `COPY_IN(p)` on the same MTE2 FIFO. If the pilot `p` fill completes before the follower's `p` issue after `q`, with no eviction, the follower must see a hit by the official membership test. This is a **conditional timing argument**; existence of such `q`, the prepared FIFO order, and actual service times must be checked for 005 and separately for 1471. No fake input or plan-only precedence can be invented to satisfy it.

## Existing mechanisms and a falsifiable next construction

[`pipeline_prefix.py:185`](../../../../src/q3/pipeline_prefix.py:185) requires 044-style real tensor-mediated Hamiltonian job chains and a complete singleton anchor. Its Task bucket model does place COPY_IN in the first actual consumer bucket ([`:268`](../../../../src/q3/pipeline_prefix.py:268)), then checks physical prefix COPYs, predecessors, L1/UB footprint, and Task matching ([`:335`](../../../../src/q3/pipeline_prefix.py:335)). Those checks are useful patterns; its 044 chain and gate assumptions have not been established for 005. [`partial_preload_prepare.py:1`](../../../../src/q3/partial_preload_prepare.py:1) is a 044/K5 frozen observer, not a reusable 005 constructor. The [044 partial-preload receipt](../../../../results/a/q3-nikolastarx/partial-preload-linux-20260925T0603Z/receipt-public/REPORT.md) reports a lower P3 Makespan than its full-prefix control but unchanged 11 hits and 1,012,064 miss bytes. It establishes that a related legitimate scheduling mechanism was tried; it does **not** demonstrate warmup of these 005 keys. The [044 build note](../../../../results/a/q3-nikolastarx/partial-preload-one-20260925/README.md) explicitly describes moving a last cold read into a pilot tail, a different temporal objective.

A bounded graph-driven proposal, if evaluation budget is later authorized: for each target key, identify the actual consuming compute ops and their raw predecessor/other-input structure; choose a pilot whose legal first consumer can bring its COPY forward; on each follower, use only existing independent work and legitimate other COPY_INs to place the target COPY behind enough actual MTE2 service. Preserve every compute op exactly once, legal dependency order, and original input identity. First reject statically when the follower MTE2 prefix has no real delaying operation and no COPY predecessor; a later M/V bucket alone is inadequate. Then verify Task's exact per-core synthesized COPY identity/order, Step1 ordering, **Step2 zero spill** with per-pool closed-interval frontier, and prepared Step3 local tensor/incarnation mapping, runtime pool peaks, memory-reuse edge directions, and the union of all four pipe FIFOs, operation dependencies, memory edges, and cross-links for acyclicity/crossing. Only an actual P3 event trace can check `pilot insert < follower issue` and residency; the same-plan P2/P3 pair plus end-to-end solver time would be needed before claiming any G or Pareto gain. If the needed genuine delay has no path through the follower's MTE2/dep structure, stop this warmup tactic for that key.
