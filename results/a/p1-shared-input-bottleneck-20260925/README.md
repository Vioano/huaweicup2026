# 044 shared-input bottleneck: saved-artifact diagnosis (2026-09-25)

Scope: read-only, fixed `9c5f87548cc7588465a638e032993969b5cac891` v4 `cells/044/k5/{plan.json,result.json.gz,trace.json.gz,run-derived.json}`, the original `data/raw/a/official-cases.zip:data/case_044.json`, and the earlier `results/a/p1-shared-full-core-probe-20260925/public/{plan.json,result.json.gz,trace.json.gz,diagnostics.json,README.md}`. Reproducible aggregate extraction and SHA-256 values are in [analyze_saved.py](analyze_saved.py) and [derived.json](derived.json). New constructor, compiler, solver, response, E0/E1/E2 calls: **0 each**. The prior K3 probe is historical evidence, not a new evaluation.

**Observed constraint.** The original compute graph has 11 disconnected 124-op components. Each contains 6,764 raw `PIPE_M` cycles and consumes a largely common external input set. V4 K5 assigns six whole components to core 0 and five to core 1; three cores are idle. It is therefore not cloning the whole graph onto both cores. Of 952,928 unique bytes of compute-external tensors, 930,400 bytes are read by two Tasks; that repeated set accounts for 930,400 of 1,051,488 added DDR bytes (88.5%). The remaining 121,088 added bytes have other boundary causes. No spill is reported; active-core L1 peaks are 264,192 B against 524,288 B capacity. The saved Task DAG has only same-core edges and four 100-cycle inter-Task gaps on each core, so no cross-core 1,000-cycle gate appears in this plan. Core 0 finishes at cycle 64,624, core 1 at 56,767, a 7,857-cycle tail. Task execution intervals total 64,224 and 56,367 cycles, respectively; these intervals include Task-internal waiting and are **not** Pipe utilization.

**COPY versus compute timing.** The two first Tasks start together at cycle 0; their `PIPE_MTE2` streams end around cycles 7,775 and 7,740, while both begin `PIPE_M` at cycle 80. This supports overlapping startup copies with DDR contention, not a claim that all duplicated input bytes serialize at startup. The shared reads occur in later Task windows too. In the saved trace, event-duration sums on cores 0/1 are `PIPE_M` 40,584/33,820 and `PIPE_MTE2` 23,902/24,145 cycles. These are per-Pipe event sums; overlap prevents adding them into a critical path. The final core-0 Task 5 runs 55,783–64,624 and contains 7,428 `PIPE_M` cycles but only 423 `PIPE_MTE2` cycles. Thus the *observed late tail* is compute-heavy, while the repeated shared input is a major cost of recruiting another core. The trace supports both mechanisms at different phases, not a single global DDR-only or M-only attribution.

The historical K3 full-core probe spreads components 4/4/3 and raises scheduled DDR from 2,026,944 to 2,957,344 B: exactly one additional 930,400-B shared-input copy. Its Makespan worsens from 64,624 to 68,109. Its first two cores each have `PIPE_M` event sum 27,056 but `PIPE_MTE2` 43,026 cycles, versus v4's 40,584/33,820 M and about 24,000 MTE2. This is strong evidence against **that** full-core replication strategy. Different Task cuts and ordering also changed, so the saved comparison does not isolate the extra copy as the sole cause.

**Narrow next structural test, if a new budget is granted.** Keep the two active cores and seek an upstream-closed M-heavy branch from one of core 0's six components that can move to core 1 while preserving the two-Task multiplicity of the 930,400-B input set. Statically compute its new boundary COPY bytes, Task dependencies and any cross-core 1,000-cycle gate before a single 044/K5 evaluation. Reject it if the move creates a third shared-input read or if cut/gate costs plausibly exceed the load relief. Splitting half of one 6,764-cycle M component offers only **3,382 raw M cycles** of simple load balance before boundary and gating costs; this is an illustrative work count, not a wall-clock improvement bound. The large `B=154,407` versus loose `L=14,925` gap does not imply that the difference is recoverable. Existing evidence does not yet establish a legal low-boundary branch or any positive score gain, so this is a falsifiable candidate, not a recommendation to expand a benchmark batch.
